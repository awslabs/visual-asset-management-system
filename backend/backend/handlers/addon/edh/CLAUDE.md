## Session keys

A desktop's VAMS credential is a temporary session key (`backend/CLAUDE.md`, Authorization System):

-   `edhSessionBootstrap.SESSION_KEY_NAME_PREFIX` is the core `TEMPORARY_SESSION_KEY_NAME_PREFIX` followed by `edh-`. A key is named `temporary-session-edh-<bootstrapId>` at launch and start, and a renewal's re-issue adds `-r<YYYYmmddHHMMSS>`, so the key it replaces keeps its name; `bootstrap_id_from_key_name` maps either name back. apiKeyService therefore refuses key create and update to a desktop holding one, and lets only the bootstrap's Lambda cross-call create a key under the prefix (`test_edh_session_key.py`).
-   The key is minted through a `lambdaCrossCall` invoke of apiKeyService on the admin create route as the launching user, carrying the user's real MFA state; the invoke is single-attempt and bounded by the request's deadline. The value reaches the desktop only through the Secrets Manager secret `<EDH_SESSION_SECRET_PREFIX><bootstrapId>`, whose read grant is bound to the desktop's EC2 instance once EDH places it (`test_edhSessionBootstrap_mint.py`, `test_edhSessionBootstrap_secrets.py`).
-   `revoke_session` deletes the key the row names and then every other key of the bootstrap it lists as `SYSTEM_USER`; `every_key=False` deletes only the named key. `delete_other_session_keys` is the listing half on its own, under the caller's deadline (`test_edhSessionBootstrap_secrets.py`).
-   `bootstrap_applies(row)` is the mint gate: false for a Windows row, which every mint answers `disabled`, while revoke and cleanup keep `is_enabled()` (`test_edhSessionBootstrap_windows.py`). The module loads with the feature's environment absent, and aborts the import when the feature is on and a variable is missing (`test_edhSessionBootstrap_mint.py`).
-   Launch, start, connect and the Windows sign-in answer `403` to a caller that authenticated with an API key (compared with `handlers.auth.AUTH_METHOD_API_KEY`), so a session key cannot start another desktop, obtain a DCV connection or read a Windows password (`test_edhWorkstationService_create.py`, `test_edhWorkstationService_session_create.py`, `test_edhWorkstationService_session_lifecycle.py`, `test_edhWorkstationService_connect.py`, `test_edhWorkstationService_windows_sign_in.py`). A renewal from an API-key caller renews the lease and re-issues nothing (`test_edhWorkstationService_renew.py`).
-   A renewal of an `ACTIVE` row with no start in progress re-issues the key under a credential claim (`credentialClaimedAt`, fresh for `CREDENTIAL_CLAIM_SECONDS`): it mints through `mint_reissue_key`, names the key on the row conditioned on the claim, `ACTIVE` and the `apiKeyId` read after the claim, writes the secret through `write_reissued_secret`, and releases the claim. A start is refused while a claim is fresh; it deletes the key the row names before the mint and, once EDH has accepted the start, the launch worker deletes every other key of the bootstrap, best effort within `START_KEY_CLEANUP_SECONDS`. A rollback takes back only the minted key (`test_edhWorkstationService_renew.py`, `test_edhWorkstationService_session_lifecycle.py`).

## Reads of EDH desktop state

-   List, get, the start pre-read and the read after a lost stop, start or delete answer read desktop state through `EdhClient.get_desktop_states`, EDH's token-free `session_state` route, for the session ids of the caller's own rows only. Connect and Windows sign-in read the per-user `list` narrowed to the row's session through `get_desktop_connection`, at most one connection token per request EDH answers, and match the answer to the row by session id. The one other reader of the per-user list is `get_desktop_failure`, the launch-failure read (see [Launch failures](#launch-failures)), which only the list and get routes' `_capture_launch_failures` and the sweep's `_capture_launch_failure` call, for an `ORPHANED` row's own session: a desktop that never ran has no DCV session, so EDH issues no connection token for it, and the client reads only the record's `recent_events`. No other route or handler module reads the per-user list (`test_edhWorkstationService_token_reads.py`).
-   `GET /addon/edh/workstations/{sessionId}/windows-sign-in` returns the user name and EDH's `session_local_admin_password` of the owner's running Windows desktop, a null password with `directoryAccount` for a domain-qualified name, audited as `workstationWindowsSignIn` and never logged (`test_edhWorkstationService_windows_sign_in.py`).

## Launch failures

EDH records why a desktop failed in its own events: its asynchronous placement emits `placement_failed`, and a desktop whose setup failed emits `session-failed` with a `checkpoint`. EDH's per-user listing carries a desktop's last four events under `recent_events`, for a deactivated desktop too when asked with `is_active=false` (EDH deactivates a desktop whose placement failed within minutes):

-   `EdhClient.get_desktop_failure(edh_uid, session_id)` asks the per-user listing for the one session, active first and inactive only when the first answers no record of it (at most two requests), keeps a record only when its `session_uuid` is the id asked and its `session_owner` is the caller, and returns `edh_failure_from_events` of its `recent_events`, or None. It never returns or logs the record's `connection_string`, tokens or password; EDH's `sub_status` text is logged cut to `EDH_FAILURE_TEXT_LOG_LIMIT` (300) characters and never stored or returned. It is audited as `workstationLaunchFailure` in `EDH_AUDIT_ROUTES` (`test_edhClient_desktop_failure.py`).
-   `edh_failure_from_events` takes the newest of the two event types and returns `event`, the `errorCode` and `operation` parsed with `EDH_FAILURE_AWS_ERROR_PATTERN` (absent when EDH's text names no AWS error in botocore's words) and, for `session-failed`, a `checkpoint` matching `EDH_FAILURE_CHECKPOINT_PATTERN`. `edh_failure_last_error` turns a generic `LAUNCH_ERROR`, or none, into `CAPACITY_UNAVAILABLE` for a code in `CAPACITY_ERROR_CODES`, `QUOTA_EXCEEDED` for one in `QUOTA_ERROR_CODES`, and `LAUNCH_ERROR` otherwise, and, on a row carrying `capacityReservationId`, into `RESERVATION_FULL` for a code in `RESERVATION_FULL_ERROR_CODES` (see [Capacity reservations](#capacity-reservations)); a specific code the launch worker recorded is kept (`test_edhSessionState_failure.py`, `test_edhSessionState_reservation_failure.py`).
-   The list and get routes, after merging EDH's state and recording `_record_failed_launches`, and the sweep (see [The reconciler sweep](#the-reconciler-sweep)) read each row `edh_failure_read_due` names: `ORPHANED`, with a session id, no `edhFailure`, and no `edhFailureReadAt` within `EDH_FAILURE_READ_INTERVAL_SECONDS` (300). `edh_failure_attributes` writes the stamp always and, when the read found a reason, `edhFailure` (the map plus `observedAt`) and the reclassified `lastError`; a read that fails is logged and writes the stamp alone, and a row deleted since it was read is not written (`test_edhWorkstationService_launch_failure.py`).
-   The workstation record (`WorkstationRecordModel`) and the admin instance item return `edhFailure` through `edh_failure_projection` (only the keys of `EDH_FAILURE_FIELDS`, null for a value that is not such a map) and never `edhFailureReadAt` (`test_edh_models.py`, `test_edhAdminService_launch_failure.py`).

## Launch checks

-   A launch whose instance type the image's own nested `profile` lists only under architectures of another family than the image's (`x86_64` and `i386` are one family) is refused after Tier 2 with `400` `instanceType does not match the image's architecture`, before any EDH call, row, mint or worker. It passes to EDH's own check when the stack has no `ami_arch`, no readable `profile`, or lists the type under no architecture. A launch of an image an AVAILABLE AMI recipe build registered, on a type its recipe's `launchInstanceTypes` leaves out, is refused after the architecture check with `400` `instanceType is not offered for this image`; the check reads `recipe_store.available_builds_by_stack_id` as the catalog does, not while `EDH_AMI_BUILDS_ENABLED` is not `true`, and a failed read is a warning that refuses nothing (`TestLaunchRecipeInstanceTypes`). A launch whose `rootSizeGb` is below the image's registered root size is refused after Tier 2. `models/addon/edh.py` `ARCHITECTURE_FAMILIES` and `architecture_family` are the family table this check and the AMI recipe checks share (`test_edhWorkstationService_create.py`).
-   The launch catalog's images carry `architecture` and its instance types `architectures`; `GET /addon/edh/catalog/images` adds `category` `amiRecipe` (with `recipeId`, `recipeDisplayName`, `recipeVersion`, and `launchInstanceTypes` only when the recipe lists any) for a stack an AVAILABLE AMI recipe build registered, else `baseline`. The recipe table is not read while `EDH_AMI_BUILDS_ENABLED` is not `true`, and a failed read lists every image `baseline` with a warning. Recipe images come first, each group in numeric-aware name order (`test_edhWorkstationService_catalog_images.py`, `test_edhWorkstationService_catalog_instance_types.py`).
-   `edhLaunchWorker` sends `session_type` `console` for a Windows row and `virtual` for any other, reads the session id back through `EdhClient.find_desktop_by_name` (owner-strict on `session_owner` and `session_name`), then sets the never-auto-start schedule as the row's EDH uid and stamps `scheduleAppliedAt`; a schedule failure is logged and left to the sweep, never orphaning or retrying the launch (`test_edhLaunchWorker.py`).

## The workstation image

A workstation keeps the image it was launched from after a newer AMI recipe build retires that image's EDH stack from the catalog, so its record names the image itself (in-dev D14):

-   **Snapshot at launch**: `create_workstation` stores `edhSessionState.launch_image_snapshot` on the row it creates: `imageName` (the catalog stack's `stack_name`) and, for a stack an AVAILABLE recipe build registered, `recipeId`, `recipeDisplayName` and `recipeVersion`, from the launch check's one `available_builds_by_stack_id` read; a value the stack or recipe does not state is left out. The snapshot is written once and never refreshed (`test_edhWorkstationService_image_name.py` `TestTheLaunchStoresTheImage`).
-   **At read**: `workstation_image` derives the six record fields. A row that names no `recipeId` (every row launched before the snapshot) takes the recipe, display name and version from the build that registered its `imageId`, and a row without `imageName` the build's `edhStackName`; `latestRecipeVersion` (the recipe's newest AVAILABLE version) and `imageLatest` (`true` when equal, `false` only when the newest is greater, else null) are derived on every read and never stored. The builds come from `edhAmiRecipeStore.registered_builds_by_stack_id`, one scan of AVAILABLE and RETIRED builds under `available_builds_by_stack_id`'s kind rules plus `latest_available_versions`, made once per request and not for an empty list (`test_edhAmiRecipeStore_registered_builds.py`).
-   **Switches and failures**: while `EDH_AMI_BUILDS_ENABLED` is not `true` the table is not read; a read that fails is a warning, as `_recipe_builds_by_stack`'s is. Either way the records are served with what their rows stored and `imageLatest` null. No catalog permission is checked for these fields.
-   **Admin**: the instance item (`_instance_item`) carries the same six fields, its `imageName` falling back to the name in EDH's `software_stack` label when the label names the item's image; `_with_recipe_images` resolves the list, stale and stop/deactivate answers from one scan. `edhAdminService` reads `EDH_AMI_BUILDS_ENABLED` at import and holds a read-only grant on the recipe table only with AMI builds on (`test_edhAdminService_image_name.py`, `test_edhAdminService_module_load.py`).

## Starting a stopped desktop

The start is asynchronous, like a launch (in-dev D10, D11):

-   **Route**: `start_workstation` keeps every check and the claim (`startRequestedAt`, held `START_IN_PROGRESS_SECONDS`, 420: the worker's 6-minute timeout plus a minute for the hand-over), mints the key, writes it with the start mark `activity: starting` (and clears `stopRequestedAt`), invokes the launch worker with `{"action": "start", "bootstrapId", "startRequestedAt"}` (`START_PAYLOAD_KEYS`) and answers `202` with the record. It never calls EDH's start. An invoke that fails takes the minted key back, releases the claim and the mark, and raises (`test_edhWorkstationService_start_async.py`).
-   **Worker**: `edhLaunchWorker._handle_start` acts only on the `STOPPED` row of that stamp and mark, and `_claim_start_send` writes `startSentFor` conditionally before EDH is called, so exactly one EDH start is sent per start request across deliveries and retries. The start goes out under the client's `start` profile (`EDH_START_BUDGET_SECONDS`, 240; the PUT is sent once and reads for 230 s) and only while the start's window, from its stamp, still holds that budget; a later delivery records `START_FAILED` unsent. Accepted: `CREATING`, `edhState` pending, the stamp, `lastError`, `startFailure`, `leaseStoppedAt` and `stopRequestedAt` cleared, the secret bound, the bootstrap's other keys deleted. `EdhCapacityError`: `CAPACITY_UNAVAILABLE`; a refusal of a reservation-bound row whose reservation is full: `RESERVATION_FULL`; any other refusal, an unsent request or a rejected credential: `START_FAILED`. Each refusal leaves the row `STOPPED` with `startFailure` (`start_failure`: the D8 `errorCode`, the instance's `availabilityZone` from `ec2:DescribeInstances`, `observedAt`), takes back the minted key and releases the claim; the desktop is never deleted, terminated or orphaned. A lost answer (`EdhOutcomeUnknownError`, `EdhContractError`, a `502`/`504` gateway answer, a non-EDH error) is followed by `get_desktop_states` every `START_POLL_INTERVAL_SECONDS` (15) until EDH reports the desktop past stopped (accepted) or the window less `START_FINISH_RESERVE_SECONDS` ends, which leaves the row `STOPPED`, marked, claimed and keyed for the sweep (`test_edhLaunchWorker_start.py`).
-   **Sweep**: `_start_resolution` records `START_FAILED` (mark and stamp cleared, `startFailure` with `observedAt` only) on a `STOPPED` row still marked whose stamp is `START_RESOLVE_SECONDS` (600) old and whose desktop EDH lists `stopped` (`start_resolve_due`); the key is then revoked as any stopped desktop's is, and the row is never deleted for it (`test_edhSessionReconciler_start_resolve.py`).
-   **Activity**: `workstation_activity` derives the record's `activity` on every read (the stored mark is never returned): `starting` for a `STOPPED` row marked with a stamp inside the window, a `CREATING` row with a session id, an `ACTIVE` row that is not connectable; `stopping` while `edhState` is `stopping`, or within `STOP_SETTLE_SECONDS` (300) of `stopRequestedAt` (written by the owner's and the admin stop) while `edhState` is `running`. The workstation record and the admin instance item carry `activity` and `startFailure` (`start_failure_projection`). `observed_row_attributes` keeps a `STOPPED_ROW_LAST_ERRORS` code (`LEASE_EXPIRED`, `CAPACITY_UNAVAILABLE`, `RESERVATION_FULL`, `START_FAILED`) and `startFailure` while the state stays stopped, and clears the mark once EDH reports the desktop running or failed (`test_edhSessionState_activity.py`, `test_edhAdminService_activity.py`).

## The reconciler sweep

`edhSessionReconciler` re-reads each row before deciding and writes conditionally (`test_edhSessionReconciler.py`):

-   It takes the lease decision for a row before the ordinary reconciliation of that row (see the next section).
-   It revokes the credentials of stopped, orphaned, deleted or expired sessions while the environment names the apiKeyService function; a credential it cannot revoke is counted `skipped`, and a revoke of a row under a fresh credential claim is held and counted `deferred`.
-   A row whose desktop EDH's listing leaves out is recorded `DELETED` only after EDH's token-free session-state read confirms the desktop is gone; a desktop that read still reports is reconciled from it, and when the read fails every unlisted row is left for the next sweep (counted `deferred`), so one empty or truncated listing cannot detach the workstations. A `CREATING` row with a session id whose desktop EDH no longer has is a failed launch, not a removed desktop: EDH deactivates a desktop whose placement failed, and a desktop that never ran is no Save and Resume, so the sweep records it `ORPHANED` with `LAUNCH_ERROR` (keeping a code the launch recorded) and no stamp, and the list and get routes do the same as soon as EDH's session-state read leaves the id out (`get_desktop_states`' `unanswered`, `_record_failed_launches`). EDH's Save and Resume continues a desktop under a new session uuid with the same session name and owner: a row whose session EDH no longer lists follows the desktop EDH lists under its owner and session name (`_resumed_desktop`), and a row the sweep recorded `DELETED` because EDH stopped listing its desktop carries `edhUnlistedAt`, so the resumed desktop re-adopts it; the sweep finds such a row, which it no longer scans, by the bootstrap id the listed desktop's session name encodes (`_resumed_rows`, at most `MAX_RESUMED_ROW_LOOKUPS_PER_SWEEP` reads). A row deleted through VAMS carries no stamp and is never re-adopted.
-   It removes the secrets of desktops that are gone and stamps `DELETED` rows that hold no credential with the `expiresAt` TTL.
-   A row a pass leaves `ORPHANED` with a session id is given the reason EDH recorded for its failed launch (see [Launch failures](#launch-failures)), read as the row's own `edhUid` since EDH's per-user listing is owner-scoped, under a write conditioned on the row as the pass left it, at most `MAX_FAILURE_READS_PER_SWEEP` (50) reads per sweep and none within the last `FAILURE_READ_TIME_FLOOR_SECONDS` (120) of the run; the summary counts `failuresCaptured`, and a read that fails counts `failed` (`test_edhSessionReconciler_launch_failure.py`).
-   It applies the never-auto-start schedule once to every non-`DELETED` row with a session id EDH lists and no `scheduleAppliedAt`, only on a pass with nothing else to write or revoke, at most 50 schedule calls per sweep and none after the first EDH error other than not-found or within the last 120 seconds of the run. A later schedule change made through EDH's API is left as it is.
-   While session bootstrap is on, it deletes expired or aged orphan `temporary-session-edh-*` keys, keeping every unexpired key of a live row's bootstrap, and audits an orphan deleted past its expiry as `expire` and any other as `revoke`.

## The lease settings row

The session table carries one row that is not a session: the workstation lease policy, under the reserved `bootstrapId` value `SETTINGS#lease` (`common/edhLeasePolicy.py` `LEASE_SETTINGS_KEY`). Two properties make that safe, and both must hold for any row of this kind: the literal cannot collide with a session row's partition key, which is the raw client-generated `bootstrapId`, always a 36-character UUID; and the row carries no `state`, so the state-filtered scans that read session rows never yield it. The catalog-registration custom resource writes it once at deploy (insert-if-absent) and the admin settings route thereafter (`test_edhLeasePolicy.py`).

The capacity-reservation registry rows, under `SETTINGS#capacityReservation#<cr-id>` (see [Capacity reservations](#capacity-reservations)), are rows of the same kind and hold both properties; they also carry no `userId` or `sessionId`, so neither session index holds them. The admin instance scan, the one scan of the table that reads every session row, leaves out every `SETTINGS#` key (`edhCapacityReservations.session_rows_only`). `test_edhCapacityReservations.py` `TestPrefixIsolation` runs each session-row read against registry rows and the lease row.

The reconciler reads the policy once per sweep. It stops a desktop past `leaseExpiresAt` and stamps `leaseStoppedAt`, deletes one whose grace window has elapsed, and skips the step entirely when the policy is disabled or could not be read: a lease action stops or deletes someone's desktop, so inaction is the safe direction on every failure (`test_edhSessionReconciler.py`).

## Capacity reservations

An administrator registers the EC2 capacity reservations VAMS may launch desktops into; `common/edhCapacityReservations.py` holds the registry and the live view (`test_edhCapacityReservations.py`):

-   **Registry**: one row per reservation under `SETTINGS#capacityReservation#<cr-id>` (`REGISTRY_KEY_PREFIX`; see [The lease settings row](#the-lease-settings-row)) with `capacityReservationId`, `label`, `fallbackToOnDemand` and `enabled` (both default true) and the create and update stamps, at most `MAX_REGISTERED_CAPACITY_RESERVATIONS` (100). `list_registrations` is a scan filtered on the prefix; `register` is a put conditioned on the key's absence, `update_registration` and `unregister` are conditioned on its presence. Unregistering never touches EC2, and rows launched into the reservation keep their `capacityReservationId`.
-   **Live view**: EC2's facts are never stored. `read_live` reads every id in one `DescribeCapacityReservations` call through the module-level `ec2` client, in the Lambda's own Region, where EDH runs. EC2 refuses a whole call naming an id it does not hold (`InvalidCapacityReservationId.NotFound`), so `read_live` then reads each id alone and marks the missing one `notFound`; any other failure is `CapacityReservationReadError`. `view` joins a registration and its facts into the `CapacityReservationView` (`CapacityReservationViewModel`), with `state` `unknown` when the read failed. `platform_suits` takes a platform starting `Linux/UNIX` for a Linux image and one starting `Windows` for a Windows image.
-   **Permission**: object type `edhCapacityReservation`, field `edhCapacityReservationId`; `GET` lists a reservation in the launch catalog and `POST` launches into it. `edh-admin.json` grants every reservation, `edh-user.json` none (`test_edh_permission_templates.py`).
-   **Catalog**: `GET /addon/edh/catalog/capacity-reservations` lists the registered, enabled, permitted, `active` reservations by label, narrowed by the optional `instanceType` and `osFamily` query parameters. EC2 is read only for the permitted ones, and a read that fails answers 200 with no items (`test_edhWorkstationService_capacity_reservations.py` `TestCatalog`).
-   **Launch**: a launch naming `capacityReservationId` runs `_launch_reservation` after the root-size check and before any row, mint, worker or further EDH call, in this order: registered and enabled (`400`), Tier-2 `POST` (`403`), the EC2 read (`503`, never a fallback), `active` (`400`), the instance type (`400`), the platform (`400`), a free slot. A full reservation with `fallbackToOnDemand` launches on-demand and the row records `capacityReservationFallback` and `capacityReservationRequested`; without it the answer is `409` with `code` `RESERVATION_FULL`. A launch naming none reads neither the registry nor EC2 and writes no reservation field (`TestLaunchChecks`, `TestLaunchWithoutAReservation`).
-   **Worker**: a row carrying `capacityReservationId` is created with `capacity_reservation_id` and `subnet_id` `auto`. When EDH definitely refuses that create (`EDH_REFUSALS`), the worker reads the reservation again: full, with its registration (read again) allowing a fallback, `_record_fallback` moves the row off the reservation (sets the fallback fields, removes `capacityReservationId`) and the create is made once more, on-demand; full without one, the row is `ORPHANED` with `RESERVATION_FULL`; anything else takes the existing refusal path. A create whose answer was lost (`EdhOutcomeUnknownError`) is never made again and reads no reservation (`test_edhLaunchWorker_capacity_reservations.py`).
-   **Start**: EDH keeps the reservation a stopped desktop was launched into, and VAMS does not move it to another. A start EDH definitely refuses on a row carrying `capacityReservationId` whose reservation, read again by the launch worker, is full leaves the row `STOPPED` with `lastError` `RESERVATION_FULL` (`edhLaunchWorker._start_refusal_code`); the start route reads no reservation and never answers `409` for it (`test_edhLaunchWorker_start.py` `TestAStartOfAReservationBoundDesktop`, `test_edhWorkstationService_capacity_reservations.py` `TestStartOfAReservationBoundDesktop`).
-   **Classification**: `edhSessionState` holds the rule every caller applies. `reservation_refusal_last_error` gives `RESERVATION_FULL` for a refused create or start whose reservation is full (active, no free slot); `edh_failure_last_error(..., reservation_bound=True)`, which `edh_failure_attributes` passes for a row carrying `capacityReservationId`, maps `RESERVATION_FULL_ERROR_CODES` to `RESERVATION_FULL` (`test_edhSessionState_reservation_failure.py`).
-   **Records**: the workstation record and the admin instance item carry `capacityReservationId`, `capacityReservationLabel` (joined from the registry at read time through `labels_for`, null once unregistered, and no read for rows without a reservation) and `capacityReservationFallback`; `capacityReservationRequested` stays on the row.
-   **Admin routes**: `GET|POST /addon/edh/admin/capacity-reservations` and `PUT|DELETE .../{capacityReservationId}`, API-tier only like the lease settings. Register needs EC2 to hold the reservation (`400` otherwise, `503` when EC2 cannot be read) in a state other than `expired`, `cancelled` or `failed` (`EC2_TERMINAL_STATES`, `400` `The capacity reservation is not active`; a `pending` or `scheduled` one registers); a duplicate is `409`, the 101st registration `400`, an unregistered id `404`. Audited as `edhCapacityReservationRegister`, `edhCapacityReservationUpdate` and `edhCapacityReservationDelete` (`test_edhAdminService_capacity_reservations.py`).

## AMI recipes

-   A recipe POST with `duplicateOf` runs Tier 2 `GET` on the source under its own OS family and copies its `assets` and `assetPrefix`; create and update refuse a `stackName` another recipe uses, compared trimmed and without case (`test_edhAmiRecipeService.py`).
-   A recipe PUT runs Tier 2 `PUT` on the stored recipe, and also on the OS family the body names when it differs, so an update cannot move a recipe into a family the caller's role does not cover (`test_edhAmiRecipeService.py`).
-   Create, update and duplicate refuse with `400` (`edhAmiRecipes.RecipeInvalid`) a recipe whose build instance types, or whose `ami-` or `ssm:` parent AMI, EC2 reports as another architecture family than its `architecture`, and pass a failed lookup, a type or image of no known family and an `edhStack:` parent. A build start refuses with `409`, before any Image Builder object, a parent EC2 does not find and a parent or build instance type of another family (`test_edhAmiRecipes.py`, `test_edhAmiRecipeService.py`).
-   `launchInstanceTypes` (`AmiRecipeRequestModel`, 1-64 distinct types of the build types' own pattern and length; absent, null or empty is None and is not stored) is metadata outside `HASHED_FIELDS`: seeding, create and update store it, an update without it clears it, and a changed list never changes `contentHash`. The duplicate clients copy it with the other request fields (`test_edh_ami_recipe_models.py`, `test_edhAmiRecipes.py` `TestLaunchInstanceTypes`).
-   `edhAmiRecipeStore.content_hash` folds the asset prefix, assets, parameters and the deployment values a recipe's documents name only when the recipe carries them, so a recipe without them keeps its hash. The table name resolves at import or, when that fails, on first use in `_table` (`test_edhAmiRecipeStore.py`).
-   `edhImageBuilder.substitute_component_data` resolves `${ASSET_<id>}`, `${PARAM_<key>}` and `${DEPLOY_<key>}` (from the closed `DEPLOYMENT_PARAMETERS` map) in one pass before `create_component`, and refuses a document with an unresolved placeholder; `component_documents` applies the 16000-character limit to the resolved documents (`test_edhImageBuilder.py`).
-   A recipe delete removes every build row, the sweep's only record of an AMI it still has to remove, so `delete_recipe` refuses with `409` `a build's AMI removal is pending` (`AMI_REMOVAL_PENDING`) while a build of its consistent listing holds an AMI not yet deregistered and is beyond `keepVersions` with a `PRUNABLE` status or `RETIRED` with `amiRemovalPending`, and releases its delete mark. `prune_amis` and `delete_recipe` pick those builds through the one helper `_ami_removal_candidates` (`test_edhAmiRecipes.py` `TestDeleteWhileAnAmiRemovalIsPending`, `test_edhAmiRecipeService.py` `TestDeleteRefusals`).
