# VAMS v2.5 to v2.6 Migration Guide

## Overview

This is the single consolidated migration for the VAMS v2.6 release. One script,
`v2.5_to_v2.6_migration.py`, runs six independent steps (select with `--steps`; default runs all):

| Step                            | `--steps` value               | What it does                                                                                                  |
| ------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------- |
| OpenSearch reindex              | `reindex`                     | Repopulates the new `vams-*-v3` indexes by invoking the deployed `crReindexer` Lambda.                        |
| Asset history backfill          | `assetHistory`                | Backfills the new AssetHistory table from existing asset + version records.                                   |
| Workflow executions overhaul    | `workflowExecutions`          | Reshapes legacy workflow execution rows into the V2 workflow-keyed DynamoDB data model.                       |
| Auxiliary preview relocation    | `auxPreviewRelocation`        | Moves aux-bucket preview data to the per-file `{databaseId}/{assetId}/…/preview` layout.                      |
| Pipeline + workflow definitions | `pipelineWorkflowDefinitions` | Migrates user-database pipeline + workflow DEFINITIONS from the V1 tables to the V2 tables.                   |
| Global-list partition backfill  | `globalListBackfill`          | Stamps `allListPartition` on V2 pipeline/workflow/execution rows so the by-date global-list GSIs return them. |

Running with no `--steps` (or `--steps all`) runs the steps in the order above. Any step can be run on its own.

### Step 1 — OpenSearch reindex (`vams-*-v2` -> `vams-*-v3`)

VAMS 2.6.0 introduces four changes that require an OpenSearch reindex:

1. **New `geo_MD_location` field** of type `geo_shape` on every asset and file document. The asset and file indexers derive this field from a `location` metadata key (GeoJSON or `{latitude, longitude, altitude}` payload) or from individual `latitude`/`longitude`/`altitude` metadata fields. This field is what powers the new geospatial search filter and the map view.
2. **New OpenSearch index names** -- `vams-assets-v3` and `vams-files-v3`. The CDK custom resource that defines the index mappings only runs on first creation, so changing the index name is the cleanest way to introduce the new mapping.
3. **(Provisioned only) OpenSearch engine upgrade from 2.7 to 3.5.** Major-version engine upgrades on Amazon OpenSearch Service require a reindex from source data, which this migration also covers.
4. **(Serverless only) OpenSearch Serverless upgraded to support next-generation (NextGen) collections.** The collection now deploys into a collection group with a configurable generation (`app.openSearch.useServerless.nextGen`, enabling scale-to-zero and configurable OCU capacity) and new network options. An existing Serverless collection cannot be updated in place — it must be removed, re-deployed, and reindexed. See [OpenSearch Serverless Next-Gen Upgrade](#opensearch-serverless-next-gen-upgrade-breaking-change) below.

After deploying the v2.6 CDK stack, the new v3 indexes exist but are empty. This step repopulates them from the authoritative source data (DynamoDB asset records and S3 file objects) by invoking the deployed `crReindexer` Lambda. It performs:

1. **Asset reindex** -- the reindexer Lambda scans the asset storage table and re-publishes each asset record onto the asset DynamoDB stream, which the asset indexer Lambda consumes and writes into `vams-assets-v3`. The new `geo_MD_location` field is derived automatically.
2. **File reindex** -- the reindexer Lambda lists each asset bucket and re-publishes file events that the file indexer Lambda consumes and writes into `vams-files-v3`.
3. **Reports counts and errors** for each phase.

### Step 2 — Asset history backfill

The script scans the asset storage table (live and archived partitions) and backfills the new AssetHistory table: a `create` record is inferred from each asset's v0 version record (`createdBy`/`dateCreated`) when one exists, and `archive`/`unarchive` records are inferred from the asset's `archivedAt`/`archivedBy` and `unarchivedAt`/`unarchivedBy` fields. Backfilled records carry `migratedRecord: true` and a deterministic record ID, so re-running the migration overwrites rather than duplicates them. Assets without a v0 version record get no `create` record (the data is not available). Table names are resolved from the SSM prefix, with explicit `asset_storage_table_name`/`asset_versions_table_name`/`asset_history_table_name` config overrides supported. Set `skip_asset_history_backfill: true` in the config (or run `--steps` without `assetHistory`) to skip it. The `dry_run` and `limit` options apply to this step as well.

The previous v2 indexes (`vams-assets-v2`, `vams-files-v2`) remain in OpenSearch but are no longer referenced by VAMS. Delete them manually after you have validated v3.

### Step 3 — Workflow executions storage overhaul (V1 -> V2)

See [Workflow Executions Storage Overhaul](#workflow-executions-storage-overhaul-step-2) below for the full description of this step.

### Step 4 — Auxiliary preview relocation (per-file preview layout)

The workflow-execution overhaul changes where pipelines write auxiliary preview/viewer data (e.g. the Potree octree viewer files). The old layout keyed preview data on the asset file key — `{assetLocationKey}{relativeFileKey}/preview/...` — while the new per-file layout is database-scoped: `{databaseId}/{assetLocationKey}{relativeFileKey}/preview/...`. (The asset location key may include a custom base prefix, so it is not necessarily the bare assetId.) This step relocates existing preview objects so the frontend viewers keep resolving after the v2.6 deploy.

The v2.6 frontend reads the new layout, so existing previews and viewer data are unavailable from the moment the CDK deploy completes until this step finishes. Run it promptly after the deploy, and schedule the deploy for a window where that gap is acceptable. No preview data is lost: the objects still exist at their old keys until the step relocates them, and a failed object is left in place and named in the step's summary so a re-run picks it up.

The script lists the auxiliary bucket, and for each preview object (any key containing a `preview` segment) matches the key against the known asset location-key bases (from each asset's `assetLocation.Key` in the asset storage table, longest match wins), looks up that asset's databaseId, and copies the object to the new key with the databaseId inserted in front, then deletes the old object. Reserved working prefixes (`pipeline`, `pipelines`, `temp-upload`, `temp-uploads`) are never touched. The step is idempotent: an object already in the new layout carries its databaseId in front of the location base, so it matches no base and is skipped, which makes re-running safe. The aux bucket name and asset table name resolve from the SSM prefix, with explicit `asset_auxiliary_bucket_name`/`asset_storage_table_name` config overrides supported. `dry_run` logs each planned move without copying, and `limit` caps the number of objects scanned.

Asset-location uniqueness is enforced per source bucket, so two assets in different buckets can share a location key. The shared auxiliary bucket keys previews on the location key alone, which already conflates such assets in the old layout. The location index keeps the first databaseId it sees and logs a warning naming both databases and the shared key; copy the losing database's previews by hand after the step completes.

### Step 5 — Pipeline + workflow definition migration (V1 -> V2)

The v2.6 pipeline/workflow overhaul introduces new pipeline and workflow **definition** tables (`PipelineStorageTableV2` / `WorkflowStorageTableV2`, plus per-pipeline templates). Step 3 above migrates execution **history**; this step migrates the pipeline and workflow **definitions** themselves so a deployment's existing user-created pipelines and workflows keep working under the V2 data model.

**Shipped `GLOBAL` built-ins are skipped.** They are (re-)created by the CDK `vamsSchema` importer at deploy time — often with **new consolidated ids** (e.g. the four `conversion-3d-basic-to-{obj,stl,gltf,glb}` built-ins collapse to a single `conversion-3d-basic` pipeline with per-format templates). Migrating the old `GLOBAL` rows would clobber those freshly-registered built-ins, so a `GLOBAL` definition whose id is a shipped built-in id is skipped — this is the "don't-clobber-built-ins" rule. A `GLOBAL` pipeline or workflow that a user created (v2.5 accepted the `GLOBAL` keyword on create) is not a built-in and is migrated like a user-database definition. Every skipped `GLOBAL` id is logged so the classification is auditable. Soft-deleted rows (databaseId ending in `#deleted`) are also skipped.

For each migrated **pipeline**, the loose V1 fields map onto the typed V2 shape: `pipelineExecutionType` + `waitForCallback` + `taskTimeout` + the `userProvidedResource` JSON become the typed `executionConfig` (the Lambda function name / SQS url / EventBridge bus arn lands in the matching sub-block); `assetType` folds into `systemConfig.inputFileFilters.allow` (`.all` → allow-all); and the old per-pipeline `inputParameters` JSON is preserved as a single migrated template (`migrated-default`) so the pipeline keeps its default parameters as a selectable template. For each migrated **workflow**, the `specifiedPipelines.functions` list becomes the V2 `specifiedPipelines` reference list; a reference to a consolidated `GLOBAL` built-in is rewritten to its new id (a user's own pipelines are never remapped).

Migrated definitions carry the same capabilities their V1 form had: `systemConfig.allowCustomTemplateOverride` on a pipeline and `systemConfig.outputTarget.allowOverride` on a workflow are both `false`, matching the V2 defaults, so a migrated workflow writes back to its input asset and its pipelines take no inline configuration override. Enable either flag per definition to opt in.

The step is idempotent — V2 rows are keyed by the same `(databaseId, pipelineId/workflowId)`, migrated rows carry `migratedRecord: true`, and the V1 tables are never modified — so re-running overwrites rather than duplicates. Overwriting is unconditional: a re-run replaces the V2 row with the V1-derived one, discarding any edit made to the migrated pipeline, workflow, or `migrated-default` template after the first run (renames, archive flags, and template bodies included). Run the step once per upgrade, and after operators begin editing migrated definitions restrict any further run to the specific rows you intend to reset. All five table names (`pipeline_storage_table_name_v1`, `pipeline_storage_table_name_v2`, `pipeline_templates_storage_table_name`, `workflow_storage_table_name`, `workflow_storage_table_name_v2`) resolve automatically from the SSM prefix, with explicit config overrides supported. `dry_run` computes the rows without writing them, and `limit` caps the number of V1 rows scanned per table.

### Step 6 — Global-list partition backfill

The V2 pipeline, workflow, and workflow-execution tables each expose a by-date global-list GSI (`PipelinesByDateGSI`, `WorkflowsByDateGSI`, `WorkflowExecutionsByDateGSI`) keyed on a constant `allListPartition` attribute, so the cross-database "all pipelines / workflows / executions" lists resolve as a single newest-first query instead of a table scan. A row written before this attribute existed is absent from those GSIs and therefore omitted from the global lists. This step stamps the constant value (`pipeline` / `workflow` / `execution`) on any V2 row missing it.

The step is idempotent: each row is updated with a `ConditionExpression` of `attribute_not_exists(allListPartition)`, so rows that already carry the attribute are skipped and re-runs are no-ops. The `workflowExecutions` and `pipelineWorkflowDefinitions` steps already set `allListPartition` on the rows they write, so this step only matters for deployments whose V2 rows predate the GSI. The three V2 table names resolve automatically from the SSM prefix, with explicit config overrides supported. `dry_run` reports the counts without writing, and `limit` caps the number of rows scanned per table.

## Prerequisites

### Required AWS Resources

1. **v2.6 CDK stack deployed.** The stack creates the new v3 indexes (empty), publishes the deployment's resource names to SSM Parameter Store (base prefix exposed as the CloudFormation output `ResourceNamesSSMParamPrefixOutput`), and exposes the reindexer Lambda function name directly as the output `OpenSearchReindexerFunctionNameOutput`.
2. **For provisioned OpenSearch:** the OpenSearch domain must be running engine version 3.5 (the v2.6 CDK switches `OPENSEARCH_VERSION` to `OPENSEARCH_3_5`). See [OpenSearch 3.5 Upgrade for Provisioned Deployments](#opensearch-35-upgrade-for-provisioned-deployments) below if the upgrade fails on an existing domain.

### Required IAM Permissions

The principal running this migration needs (reindex step: `lambda:InvokeFunction`; assetHistory step: DynamoDB `Scan`/`GetItem` on the source tables and `PutItem` on the asset history table; workflowExecutions and pipelineWorkflowDefinitions steps: DynamoDB `Scan`/`GetItem` on the source tables and `BatchWriteItem`/`PutItem` on the destination tables; auxPreviewRelocation step: S3 list/copy/delete on the auxiliary bucket plus DynamoDB `Scan` on the asset storage table; globalListBackfill step: DynamoDB `Scan` and `UpdateItem` on the three V2 tables):

> The DynamoDB statement covers the asset-history backfill (scan of the asset storage table, v0 lookups on the asset versions table, writes to the asset history table), the `workflowExecutions` step (scan of the source tables, `BatchWriteItem` on the four destination tables, with a per-row `PutItem` fallback when a batch is rejected), the `pipelineWorkflowDefinitions` step (scan of the V1 pipeline and workflow tables, `GetItem` on the V2 pipeline table, `BatchWriteItem` on the V2 definition and template tables), the `globalListBackfill` step (scan plus conditional `UpdateItem` on the three V2 tables), and the `auxPreviewRelocation` step's assetId->databaseId lookup (scan of the asset storage table). ## Usage

### Step 1: Find the SSM Resource-Name Prefix

The deployment publishes its resource names (tables, buckets, Lambda function names used by
migration tooling) as SSM parameters under a deployment-unique prefix. Get the prefix from
the core stack output:

```bash
aws cloudformation describe-stacks --stack-name your-vams-stack \
  --query 'Stacks[0].Outputs[?OutputKey==`ResourceNamesSSMParamPrefixOutput`].OutputValue' \
  --output text
```

### Step 2: Configure Migration

Edit `v2.5_to_v2.6_migration_config.json`:

```json
{
    "resource_names_ssm_param_prefix": "/your-config-name-basestack/resourceNames",
    "reindexer_function_name": null,
    "operation": "both",
    "dry_run": false,
    "limit": null,
    "clear_indexes": false,
    "aws_profile": null,
    "aws_region": "us-east-1",
    "log_level": "INFO"
}
```

The reindexer Lambda function name is resolved automatically from SSM Parameter Store
(requires `ssm:GetParametersByPath` on the prefix). To skip or override the lookup, set
`reindexer_function_name` explicitly instead — its value comes from the CloudFormation
output `OpenSearchReindexerFunctionNameOutput`.

### Step 3: Run Migration

#### Dry Run (Recommended First Step)

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --dry-run
```

#### Test with Limited Items

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --limit 100 \
    --dry-run
```

#### Production Migration

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json
```

#### Asynchronous Invocation (Large Datasets)

For deployments with hundreds of thousands or millions of objects, use asynchronous invocation and monitor the reindexer Lambda's CloudWatch log group:

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --async
```

### Step 4: Verify Migration

1. Open the VAMS web UI and run an asset search; confirm results match expectations.
2. Switch to file mode and run a file search; confirm results.
3. For assets/files with `location` metadata, confirm the new geospatial filter panel returns expected results and the map view plots them correctly.
4. Open a point-cloud asset and confirm the Potree viewer loads its preview data, and open an asset with a file preview and confirm the thumbnail renders — both read the relocated auxiliary keys.
5. Open a migrated workflow execution's detail view and confirm its pipelines, input files, and output target are present.
6. Monitor CloudWatch logs for the asset and file indexer Lambdas for any per-record failures.

## Why `--clear-indexes` Defaults to False

After the v2.6 CDK deploy the v3 indexes are created empty by the schema-deploy custom resource. Clearing them on first run is unnecessary and wastes API calls. `--clear-indexes` is provided for the case where a previous reindex run partially populated v3 and you want a clean slate before retrying.

## OpenSearch 3.5 Upgrade for Provisioned Deployments (Breaking Change)

VAMS 2.6 sets `OPENSEARCH_VERSION = OPENSEARCH_3_5` (was 2.7). This affects only `app.openSearch.useProvisioned.enabled = true` deployments; serverless collections (`useServerless.enabled = true`) are unaffected.

Amazon OpenSearch Service supports in-place version upgrades, but a major-version jump on a long-running domain can occasionally fail or take longer than the CloudFormation custom-resource timeout. If your CDK deploy of the OpenSearch domain stack fails on the version upgrade, the recommended recovery path is:

1. Edit `infra/config/config.json` and temporarily set:
    ```json
    "openSearch": {
        "useServerless": { "enabled": false },
        "useProvisioned": { "enabled": false },
        "reindexOnCdkDeploy": false
    }
    ```
2. Run `cdk deploy --all --require-approval never`. CDK will tear down the v2.7 OpenSearch domain.
3. Restore the original `useProvisioned` configuration in `config.json`.
4. Run `cdk deploy --all --require-approval never` again. CDK creates a fresh OpenSearch 3.5 domain and the new empty v3 indexes.
5. Run this migration to repopulate the v3 indexes.

**Important:** Tearing down the OpenSearch domain deletes the indexes. Only the OpenSearch indexes are lost; all source data lives in DynamoDB and S3, so the reindex restores the full search corpus.

## OpenSearch Serverless Next-Gen Upgrade (Breaking Change)

VAMS 2.6 reworks the OpenSearch Serverless collection and adds new `app.openSearch.useServerless` config fields:

-   `nextGen` (boolean; default `true` on commercial, `false` on GovCloud/EU) -- sets the collection group generation to `NEXTGEN` (`true`) or `CLASSIC` (`false`). The collection is placed in a collection group either way; `NEXTGEN` adds scale-to-zero support. **GovCloud and EU Sovereign Cloud deployments must keep `nextGen = false`.**
-   `allowPublic` (boolean; default `true`) -- when `false`, the collection is reachable only through a VPC endpoint and requires `app.useGlobalVpc.enabled` to be `true` (built across 2 Availability Zones). As with provisioned OpenSearch, only the OpenSearch-facing Lambdas are placed in the VPC, so `app.useGlobalVpc.useForAllLambdas` is not required. A fully network-isolated deployment (`app.useGlobalVpc.enabled` + `app.useGlobalVpc.useForAllLambdas` both `true`) must set `allowPublic = false`.
-   `enableStandbyReplicas` (boolean; defaults to the value of `nextGen`). Required for `NEXTGEN` (must be `true` when `nextGen` is `true` — OpenSearch Serverless rejects a `NEXTGEN` collection group with standby replicas disabled); optional for `CLASSIC`.
-   `minIndexingOcu` / `maxIndexingOcu` / `minSearchOcu` / `maxSearchOcu` (defaults `2` / `16` / `2` / `16`). Each must be one of `0`, `2`, `4`, `8`, `16`, or any multiple of `16`. A minimum of `0` (scale-to-zero) requires `nextGen = true`.

This is a **breaking change**: placing the collection in a collection group, the `allowPublic` network-policy change, and the group generation setting all reshape the Serverless collection, so an existing Serverless deployment cannot be updated in place. Re-deploy the collection and reindex:

1. Set `app.openSearch.useServerless.enabled = false` in `infra/config/config.json` and deploy. This removes the existing collection.

    ```bash
    cdk deploy --all --require-approval never
    ```

2. Set `app.openSearch.useServerless.enabled = true` again with the desired settings (`nextGen` / `allowPublic` / OCU values) and deploy. This creates the new collection group and collection.

    ```bash
    cdk deploy --all --require-approval never
    ```

3. Reindex to repopulate the new collection, using either of:
    - Run the reindex utility (`infra/deploymentDataMigration/v2.5_to_v2.6/upgrade` or `tools/reindex_utility.py`).
    - Set `app.openSearch.reindexOnCdkDeploy = true` for one deployment, then set it back to `false`.

**Important:** Tearing down the Serverless collection deletes the indexes, but all source data lives in DynamoDB and S3, so the reindex restores the full search corpus.

**Private-collection reindex caveat:** A private collection (`allowPublic = false`) is reachable only from inside the VPC and not from a local machine, so the reindex utility's `direct` mode cannot reach it. For private collections, reindex via the deployed Lambda (`lambda` mode) or set `app.openSearch.reindexOnCdkDeploy = true`.

## Migration Process Details

The reindexer Lambda is the same component used by the existing `tools/reindex_utility.py` script. This migration script wraps it with version-specific defaults (such as `--clear-indexes=false`) and migration-specific logging.

### Asset Reindex

For each asset record in the asset storage DynamoDB table, the reindexer Lambda re-publishes a synthetic stream event so that the asset indexer (`handlers.indexing.assetIndexer.lambda_handler`) writes the asset document into `vams-assets-v3`. The asset indexer derives `geo_MD_location` from the asset's metadata using:

1. A `location` metadata key (case-insensitive). Accepts:
    - GeoJSON Geometry, Feature, or FeatureCollection (Point, Polygon, MultiPolygon, etc.)
    - JSON object with `latitude` / `longitude` / optional `altitude`
    - String of the form `"lat,lon"` or `"lat,lon,altitude"`
2. Individual `latitude`, `longitude`, optional `altitude` metadata fields.

Records with no usable location metadata are written without `geo_MD_location` and are simply excluded from geospatial filters.

### File Reindex

The reindexer enumerates each asset bucket via S3 `ListObjects`, re-publishes events that the file indexer consumes, and writes each file document to `vams-files-v3`. File metadata and per-file attributes are honored when deriving `geo_MD_location`.

### Verification

The Lambda returns aggregate success/failure counts. Inspect the CloudWatch log group for the reindexer Lambda for per-record diagnostics.

## Troubleshooting

### Lambda Function Not Found

**Symptom:** `ResourceNotFoundException: Function not found`

**Solution:** When using the SSM prefix lookup, confirm `resource_names_ssm_param_prefix` matches the core stack output `ResourceNamesSSMParamPrefixOutput` and that the v2.6 stack deployed successfully (the `lambdaFunctions/crOsReindexer` parameter is published by the `SearchBuilderNestedStack`). When using an explicit override, confirm `reindexer_function_name` matches the CloudFormation output `OpenSearchReindexerFunctionNameOutput`.

### SSM Parameter Not Found

**Symptom:** `Resource name parameter not found under /...: lambdaFunctions/crOsReindexer`

**Solution:** The prefix is wrong, points to a different deployment, or the deployment predates the resource-name parameters (v2.6+). Verify the prefix against the `ResourceNamesSSMParamPrefixOutput` stack output and check the region matches. As a fallback, set `reindexer_function_name` explicitly.

### Permission Errors

**Symptom:** `AccessDeniedException: User is not authorized to perform: lambda:InvokeFunction`

**Solution:** Add `lambda:InvokeFunction` for the reindexer Lambda's ARN to your IAM principal. The SSM prefix lookup additionally requires `ssm:GetParametersByPath` on the deployment's resource-name prefix.

### Reindex Lambda Timeout

**Symptom:** Synchronous invocation returns a timeout warning while the Lambda continues running in the background.

**Solution:** This is expected for very large deployments. Re-run with `--async` and monitor the reindexer Lambda's CloudWatch log group; the function will continue to completion (subject to the 15-minute Lambda timeout). For deployments larger than the 15-minute window, run the reindex repeatedly with `--limit` or split by `--operation assets` / `--operation files`.

### Provisioned OpenSearch Domain Upgrade Fails

**Symptom:** `cdk deploy` fails on the OpenSearch domain CloudFormation update with a version-upgrade error.

**Solution:** See [OpenSearch 3.5 Upgrade for Provisioned Deployments](#opensearch-35-upgrade-for-provisioned-deployments). Disable OpenSearch in `config.json`, redeploy to delete the domain, re-enable, redeploy again, then run this migration.

### Geospatial Filter Returns No Results After Migration

**Symptom:** The web UI's geospatial filter returns zero results even though map view shows points.

**Explanation:** Map view falls back to legacy `MD_.location` and `MD_.latitude`/`longitude` parsing for assets/files that lack `geo_MD_location`. The geospatial filter, however, queries `geo_MD_location` directly. Confirm the asset/file actually has location metadata in a recognized form, then run this migration to populate the field.

### Old v2 Indexes Still Visible

**Symptom:** `vams-assets-v2` and `vams-files-v2` are still listed in OpenSearch after migration.

**Action:** This is expected -- v2.6 does not delete the old indexes automatically. After validating v3, delete them manually via the OpenSearch Dashboards Dev Tools console or the AWS CLI:

```bash
aws opensearch describe-domain --domain-name your-domain
# then via curl + SigV4 or OpenSearch Dashboards:
DELETE vams-assets-v2
DELETE vams-files-v2
```

### Rollback

This migration only writes to the new v3 indexes. To roll back:

1. Set `config.openSearchAssetIndexName = "vams-assets-v2"` and `config.openSearchFileIndexName = "vams-files-v2"` in `infra/config/config.ts`.
2. Redeploy v2.5 (or revert the OpenSearch engine version if you upgraded a provisioned domain).
3. The v2 indexes are still populated, so search continues to work without a reindex.

## Workflow Executions Storage Overhaul (Step 2)

Reshapes legacy workflow execution rows into the new workflow-keyed data model. Run via the consolidated script with `--steps workflowExecutions` (or as part of `--steps all`).

### What it does

For every row in the legacy `WorkflowExecutionsStorageTable`:

1. Writes a `WorkflowExecutionsStorageTableV2` row — the legacy `executionId` becomes the `workflowExecutionId` PK, composite keys are cleaned (legacy `$` prefix removed), dates become ISO-8601, `execution_arn` → `workflow_execution_arn`, and `triggeredByUserId='SYSTEM_USER'` / `triggerType='Manual'` are backfilled (original trigger/user is not recoverable). Every migrated row lands terminal: the V1 `COMPLETE` success label maps to `SUCCEEDED`, and a row whose V1 status is not one of `SUCCEEDED`/`FAILED`/`ABORTED`/`TIMED_OUT` is recorded as `TIMED_OUT` with a stop date (its start date, or the migration timestamp). A migrated row's Step Functions execution history has long since expired, so a non-terminal row would be re-polled on every list call, never converge, and be refused by permanent delete. The step's summary reports how many rows were recorded this way.

    A legacy row whose `startDate` is empty (observed only on rows that never started — those
    still carry V1 status `NEW`) has no recorded start instant anywhere, and the V1 state machines
    and their Step Functions history are long gone. `executionStartDate` is the sort key of the
    by-workflow, by-group and by-date execution indexes and of the by-asset inputs index, so
    leaving it unset keeps such a row out of every date-ordered listing (readable by id, invisible
    in the UI). The migration therefore dates those rows from the creation date of the workflow they
    referenced — a bound the execution cannot predate — and marks each one `startDateEstimated=true`
    so a derived date is never mistaken for a recorded one. When the workflow itself carries no
    parseable creation date, the attribute stays unset rather than being given a fabricated value.
    The summary reports both counts separately.

2. Writes a `WorkflowExecutionInputsStorageTable` row from the legacy `assetId` / `databaseId` / `inputAssetFileKey` (so the asset-scoped GET keeps working).
3. Writes one `PipelineExecutionsStorageTable` stub per pipeline in the workflow's `specifiedPipelines` (chained via `from_pipeline_execution_id`, `endStatePipeline='true'` on the last), attaching `PipelineExecutionInputFilesStorageTable` rows to the first pipeline. A reference to a built-in pipeline whose id was consolidated in v2.6 is rewritten to the new id, so the stub resolves against the V2 pipeline table and matches the id the migrated workflow definition carries.
4. If the workflow or a pipeline no longer exists, the stub uses `pipelineId='DELETED'` so the file linkage is preserved for history.
5. Writes a `WorkflowExecutionConfigurationStorageTable` row recording the execution's output target. A V1 execution always wrote back to its single input asset at the asset root, so the target is that asset with an output path extension of `/`. The detail view reads this row, and re-run reconstructs its output ids from it.
6. Writes one `PipelineExecutionInputConfigurationStorageTable` row per pipeline stub. A V1 execution recorded no template, so the snapshot carries no tags or rendered config; it does carry the effective template of a consolidated built-in, which lets a re-run resolve a pipeline that now requires a template.

Output/results/log tables remain empty for historical executions (only new executions populate them, via the runtime handlers).

### Prerequisites

-   The v2.6 CDK stack is deployed (the new workflow-execution tables exist).
-   The legacy `WorkflowExecutionsStorageTable` is intact (it is the read source and is never modified by this step).

### Configure

Set the six `*_storage_table_name*` fields in `v2.5_to_v2.6_migration_config.json` to your stack's DynamoDB table names (from the CloudFormation stack outputs or the DynamoDB console). The two configuration-snapshot tables (`workflow_execution_configuration_storage_table_name`, `pipeline_execution_input_configuration_storage_table_name`) resolve from the SSM prefix; set them explicitly when no prefix is configured. When neither is available the step logs a warning and skips the snapshot rows — migrated executions then show an empty output target in the detail view and cannot be re-run through a pipeline that requires a template.

### Run

```bash
# Dry run first (both steps), then production:
python v2.5_to_v2.6_migration.py --config v2.5_to_v2.6_migration_config.json --steps workflowExecutions --dry-run
python v2.5_to_v2.6_migration.py --config v2.5_to_v2.6_migration_config.json --steps workflowExecutions
```

Idempotent — GUIDs are derived deterministically from the legacy `executionId`, so re-running overwrites the same rows.
