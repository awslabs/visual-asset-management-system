# VAMS v2.5 to v2.6 Migration Guide

## Overview

VAMS 2.6.0 introduces four changes that require an OpenSearch reindex:

1. **New `geo_MD_location` field** of type `geo_shape` on every asset and file document. The asset and file indexers derive this field from a `location` metadata key (GeoJSON or `{latitude, longitude, altitude}` payload) or from individual `latitude`/`longitude`/`altitude` metadata fields. This field is what powers the new geospatial search filter and the map view.
2. **New OpenSearch index names** -- `vams-assets-v3` and `vams-files-v3`. The CDK custom resource that defines the index mappings only runs on first creation, so changing the index name is the cleanest way to introduce the new mapping.
3. **(Provisioned only) OpenSearch engine upgrade from 2.7 to 3.5.** Major-version engine upgrades on Amazon OpenSearch Service require a reindex from source data, which this migration also covers.
4. **(Serverless only) OpenSearch Serverless upgraded to support next-generation (NextGen) collections.** The collection now deploys into a collection group with a configurable generation (`app.openSearch.useServerless.nextGen`, enabling scale-to-zero and configurable OCU capacity) and new network options. An existing Serverless collection cannot be updated in place — it must be removed, re-deployed, and reindexed. See [OpenSearch Serverless Next-Gen Upgrade](#opensearch-serverless-next-gen-upgrade-breaking-change) below.

After deploying the v2.6 CDK stack, the new v3 indexes exist but are empty. This migration repopulates them from the authoritative source data (DynamoDB asset records and S3 file objects) by invoking the deployed `crReindexer` Lambda.

### What This Migration Does

1. **Asset reindex** -- the reindexer Lambda scans the asset storage table and re-publishes each asset record onto the asset DynamoDB stream, which the asset indexer Lambda consumes and writes into `vams-assets-v3`. The new `geo_MD_location` field is derived automatically.
2. **File reindex** -- the reindexer Lambda lists each asset bucket and re-publishes file events that the file indexer Lambda consumes and writes into `vams-files-v3`.
3. **Asset history backfill** -- after the reindex, the script scans the asset storage table (live and archived partitions) and backfills the new AssetHistory table: a `create` record is inferred from each asset's v0 version record (`createdBy`/`dateCreated`) when one exists, and `archive`/`unarchive` records are inferred from the asset's `archivedAt`/`archivedBy` and `unarchivedAt`/`unarchivedBy` fields. Backfilled records carry `migratedRecord: true` and a deterministic record ID, so re-running the migration overwrites rather than duplicates them. Assets without a v0 version record get no `create` record (the data is not available). Table names are resolved from the SSM prefix, with explicit `asset_storage_table_name`/`asset_versions_table_name`/`asset_history_table_name` config overrides supported. Set `skip_asset_history_backfill: true` in the config to run the reindex only. The `dry_run` and `limit` options apply to this phase as well.
4. **Reports counts and errors** for each phase.

The previous v2 indexes (`vams-assets-v2`, `vams-files-v2`) remain in OpenSearch but are no longer referenced by VAMS. Delete them manually after you have validated v3.

## Prerequisites

### Required AWS Resources

1. **v2.6 CDK stack deployed.** The stack creates the new v3 indexes (empty), publishes the deployment's resource names to SSM Parameter Store (base prefix exposed as the CloudFormation output `ResourceNamesSSMParamPrefixOutput`), and exposes the reindexer Lambda function name directly as the output `ReindexerFunctionNameOutput`.
2. **For provisioned OpenSearch:** the OpenSearch domain must be running engine version 3.5 (the v2.6 CDK switches `OPENSEARCH_VERSION` to `OPENSEARCH_3_5`). See [OpenSearch 3.5 Upgrade for Provisioned Deployments](#opensearch-35-upgrade-for-provisioned-deployments) below if the upgrade fails on an existing domain.

### Required IAM Permissions

The principal running this migration needs:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": ["lambda:InvokeFunction"],
            "Resource": "arn:aws:lambda:*:*:function:*ReindexerFunction*"
        },
        {
            "Effect": "Allow",

            "Resource": "arn:aws:ssm:*:*:parameter/*/resourceNames*"

        {
            "Effect": "Allow",

            "Effect": "Allow",

    ]

```

The DynamoDB permissions cover the asset history backfill phase (scan of the asset storage table, v0 lookups on the asset versions table, and writes to the asset history table). Scope the resource ARNs to the deployment's tables where required.

## Usage

### Step 1: Find the SSM Resource-Name Prefix

The deployment publishes its resource names (tables, buckets, Lambda function names used by
migration tooling) as SSM parameters under a deployment-unique prefix. Get the prefix from
the core stack output:

```bash
aws cloudformation describe-stacks --stack-name your-vams-stack \
  --query 'Stacks[0].Outputs[?OutputKey==`ResourceNamesSSMParamPrefixOutput`].OutputValue' \
  --output text
```

### Step 2: Configure Migration

Edit `v2.5_to_v2.6_migration_config.json`:

```json
{
    "resource_names_ssm_param_prefix": "/your-config-name-basestack/resourceNames",
    "reindexer_function_name": null,
    "operation": "both",
    "dry_run": false,
    "limit": null,
    "clear_indexes": false,
    "aws_profile": null,
    "aws_region": "us-east-1",
    "log_level": "INFO"
}
```

The reindexer Lambda function name is resolved automatically from SSM Parameter Store
(requires `ssm:GetParametersByPath` on the prefix). To skip or override the lookup, set
`reindexer_function_name` explicitly instead — its value comes from the CloudFormation
output `ReindexerFunctionNameOutput`.

### Step 3: Run Migration

#### Dry Run (Recommended First Step)

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --dry-run
```

#### Test with Limited Items

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --limit 100 \
    --dry-run
```

#### Production Migration

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json
```

#### Asynchronous Invocation (Large Datasets)

For deployments with hundreds of thousands or millions of objects, use asynchronous invocation and monitor the reindexer Lambda's CloudWatch log group:

```bash
python v2.5_to_v2.6_migration.py \
    --config v2.5_to_v2.6_migration_config.json \
    --async
```

#### Using Shell Scripts

Linux/macOS:

```bash
chmod +x run_migration.sh
./run_migration.sh                                # Default config
./run_migration.sh --dry-run                      # Dry run
./run_migration.sh my_config.json --dry-run       # Custom config + dry run
./run_migration.sh --clear-indexes                # Clear v3 first (re-run only)
./run_migration.sh --async                        # Asynchronous
```

Windows PowerShell:

```powershell
.\run_migration.ps1                               # Default config
.\run_migration.ps1 -DryRun                       # Dry run
.\run_migration.ps1 -ConfigFile my_config.json -DryRun
.\run_migration.ps1 -ClearIndexes                 # Clear v3 first (re-run only)
.\run_migration.ps1 -Async                        # Asynchronous
```

### Step 4: Verify Migration

1. Open the VAMS web UI and run an asset search; confirm results match expectations.
2. Switch to file mode and run a file search; confirm results.
3. For assets/files with `location` metadata, confirm the new geospatial filter panel returns expected results and the map view plots them correctly.
4. Monitor CloudWatch logs for the asset and file indexer Lambdas for any per-record failures.

### Command Line Options

```
--config              Path to configuration JSON file (required)
--operation           assets | files | both (default: both)
--dry-run             Test without writing to OpenSearch
--limit               Maximum number of items per category to reindex (testing)
--clear-indexes       Delete existing v3 documents before reindexing (default: false)
--profile             AWS profile name
--region              AWS region
--async               Asynchronous Lambda invocation (results in CloudWatch Logs)
--log-level           DEBUG | INFO | WARNING | ERROR (default: INFO)
```

## Why `--clear-indexes` Defaults to False

After the v2.6 CDK deploy the v3 indexes are created empty by the schema-deploy custom resource. Clearing them on first run is unnecessary and wastes API calls. `--clear-indexes` is provided for the case where a previous reindex run partially populated v3 and you want a clean slate before retrying.

## OpenSearch 3.5 Upgrade for Provisioned Deployments (Breaking Change)

VAMS 2.6 sets `OPENSEARCH_VERSION = OPENSEARCH_3_5` (was 2.7). This affects only `app.openSearch.useProvisioned.enabled = true` deployments; serverless collections (`useServerless.enabled = true`) are unaffected.

Amazon OpenSearch Service supports in-place version upgrades, but a major-version jump on a long-running domain can occasionally fail or take longer than the CloudFormation custom-resource timeout. If your CDK deploy of the OpenSearch domain stack fails on the version upgrade, the recommended recovery path is:

1. Edit `infra/config/config.json` and temporarily set:
    ```json
    "openSearch": {
        "useServerless": { "enabled": false },
        "useProvisioned": { "enabled": false },
        "reindexOnCdkDeploy": false
    }
    ```
2. Run `cdk deploy --all --require-approval never`. CDK will tear down the v2.7 OpenSearch domain.
3. Restore the original `useProvisioned` configuration in `config.json`.
4. Run `cdk deploy --all --require-approval never` again. CDK creates a fresh OpenSearch 3.5 domain and the new empty v3 indexes.
5. Run this migration to repopulate the v3 indexes.

**Important:** Tearing down the OpenSearch domain deletes the indexes. Only the OpenSearch indexes are lost; all source data lives in DynamoDB and S3, so the reindex restores the full search corpus.

## OpenSearch Serverless Next-Gen Upgrade (Breaking Change)

VAMS 2.6 reworks the OpenSearch Serverless collection and adds new `app.openSearch.useServerless` config fields:

-   `nextGen` (boolean; default `true` on commercial, `false` on GovCloud/EU) -- sets the collection group generation to `NEXTGEN` (`true`) or `CLASSIC` (`false`). The collection is placed in a collection group either way; `NEXTGEN` adds scale-to-zero support. **GovCloud and EU Sovereign Cloud deployments must keep `nextGen = false`.**
-   `allowPublic` (boolean; default `true`) -- when `false`, the collection is reachable only through a VPC endpoint and requires `app.useGlobalVpc.enabled` to be `true` (built across 2 Availability Zones). As with provisioned OpenSearch, only the OpenSearch-facing Lambdas are placed in the VPC, so `app.useGlobalVpc.useForAllLambdas` is not required. A fully network-isolated deployment (`app.useGlobalVpc.enabled` + `app.useGlobalVpc.useForAllLambdas` both `true`) must set `allowPublic = false`.
-   `enableStandbyReplicas` (boolean; defaults to the value of `nextGen`). Required for `NEXTGEN` (must be `true` when `nextGen` is `true` — OpenSearch Serverless rejects a `NEXTGEN` collection group with standby replicas disabled); optional for `CLASSIC`.
-   `minIndexingOcu` / `maxIndexingOcu` / `minSearchOcu` / `maxSearchOcu` (defaults `2` / `16` / `2` / `16`). Each must be one of `0`, `2`, `4`, `8`, `16`, or any multiple of `16`. A minimum of `0` (scale-to-zero) requires `nextGen = true`.

This is a **breaking change**: placing the collection in a collection group, the `allowPublic` network-policy change, and the group generation setting all reshape the Serverless collection, so an existing Serverless deployment cannot be updated in place. Re-deploy the collection and reindex:

1. Set `app.openSearch.useServerless.enabled = false` in `infra/config/config.json` and deploy. This removes the existing collection.

    ```bash
    cdk deploy --all --require-approval never
    ```

2. Set `app.openSearch.useServerless.enabled = true` again with the desired settings (`nextGen` / `allowPublic` / OCU values) and deploy. This creates the new collection group and collection.

    ```bash
    cdk deploy --all --require-approval never
    ```

3. Reindex to repopulate the new collection, using either of:
    - Run the reindex utility (`infra/deploymentDataMigration/v2.5_to_v2.6/upgrade` or `tools/reindex_utility.py`).
    - Set `app.openSearch.reindexOnCdkDeploy = true` for one deployment, then set it back to `false`.

**Important:** Tearing down the Serverless collection deletes the indexes, but all source data lives in DynamoDB and S3, so the reindex restores the full search corpus.

**Private-collection reindex caveat:** A private collection (`allowPublic = false`) is reachable only from inside the VPC and not from a local machine, so the reindex utility's `direct` mode cannot reach it. For private collections, reindex via the deployed Lambda (`lambda` mode) or set `app.openSearch.reindexOnCdkDeploy = true`.

## Migration Process Details

The reindexer Lambda is the same component used by the existing `tools/reindex_utility.py` script. This migration script wraps it with version-specific defaults (such as `--clear-indexes=false`) and migration-specific logging.

### Asset Reindex

For each asset record in the asset storage DynamoDB table, the reindexer Lambda re-publishes a synthetic stream event so that the asset indexer (`handlers.indexing.assetIndexer.lambda_handler`) writes the asset document into `vams-assets-v3`. The asset indexer derives `geo_MD_location` from the asset's metadata using:

1. A `location` metadata key (case-insensitive). Accepts:
    - GeoJSON Geometry, Feature, or FeatureCollection (Point, Polygon, MultiPolygon, etc.)
    - JSON object with `latitude` / `longitude` / optional `altitude`
    - String of the form `"lat,lon"` or `"lat,lon,altitude"`
2. Individual `latitude`, `longitude`, optional `altitude` metadata fields.

Records with no usable location metadata are written without `geo_MD_location` and are simply excluded from geospatial filters.

### File Reindex

The reindexer enumerates each asset bucket via S3 `ListObjects`, re-publishes events that the file indexer consumes, and writes each file document to `vams-files-v3`. File metadata and per-file attributes are honored when deriving `geo_MD_location`.

### Verification

The Lambda returns aggregate success/failure counts. Inspect the CloudWatch log group for the reindexer Lambda for per-record diagnostics.

## Troubleshooting

### Lambda Function Not Found

**Symptom:** `ResourceNotFoundException: Function not found`

**Solution:** When using the SSM prefix lookup, confirm `resource_names_ssm_param_prefix` matches the core stack output `ResourceNamesSSMParamPrefixOutput` and that the v2.6 stack deployed successfully (the `lambdaFunctions/crOsReindexer` parameter is published by the `SearchBuilderNestedStack`). When using an explicit override, confirm `reindexer_function_name` matches the CloudFormation output `ReindexerFunctionNameOutput`.

### SSM Parameter Not Found

**Symptom:** `Resource name parameter not found under /...: lambdaFunctions/crOsReindexer`

**Solution:** The prefix is wrong, points to a different deployment, or the deployment predates the resource-name parameters (v2.6+). Verify the prefix against the `ResourceNamesSSMParamPrefixOutput` stack output and check the region matches. As a fallback, set `reindexer_function_name` explicitly.

### Permission Errors

**Symptom:** `AccessDeniedException: User is not authorized to perform: lambda:InvokeFunction`

**Solution:** Add `lambda:InvokeFunction` for the reindexer Lambda's ARN to your IAM principal. The SSM prefix lookup additionally requires `ssm:GetParametersByPath` on the deployment's resource-name prefix.

### Reindex Lambda Timeout

**Symptom:** Synchronous invocation returns a timeout warning while the Lambda continues running in the background.

**Solution:** This is expected for very large deployments. Re-run with `--async` and monitor the reindexer Lambda's CloudWatch log group; the function will continue to completion (subject to the 15-minute Lambda timeout). For deployments larger than the 15-minute window, run the reindex repeatedly with `--limit` or split by `--operation assets` / `--operation files`.

### Provisioned OpenSearch Domain Upgrade Fails

**Symptom:** `cdk deploy` fails on the OpenSearch domain CloudFormation update with a version-upgrade error.

**Solution:** See [OpenSearch 3.5 Upgrade for Provisioned Deployments](#opensearch-35-upgrade-for-provisioned-deployments). Disable OpenSearch in `config.json`, redeploy to delete the domain, re-enable, redeploy again, then run this migration.

### Geospatial Filter Returns No Results After Migration

**Symptom:** The web UI's geospatial filter returns zero results even though map view shows points.

**Explanation:** Map view falls back to legacy `MD_.location` and `MD_.latitude`/`longitude` parsing for assets/files that lack `geo_MD_location`. The geospatial filter, however, queries `geo_MD_location` directly. Confirm the asset/file actually has location metadata in a recognized form, then run this migration to populate the field.

### Old v2 Indexes Still Visible

**Symptom:** `vams-assets-v2` and `vams-files-v2` are still listed in OpenSearch after migration.

**Action:** This is expected -- v2.6 does not delete the old indexes automatically. After validating v3, delete them manually via the OpenSearch Dashboards Dev Tools console or the AWS CLI:

```bash
aws opensearch describe-domain --domain-name your-domain
# then via curl + SigV4 or OpenSearch Dashboards:
DELETE vams-assets-v2
DELETE vams-files-v2
```

### Rollback

This migration only writes to the new v3 indexes. To roll back:

1. Set `config.openSearchAssetIndexName = "vams-assets-v2"` and `config.openSearchFileIndexName = "vams-files-v2"` in `infra/config/config.ts`.
2. Redeploy v2.5 (or revert the OpenSearch engine version if you upgraded a provisioned domain).
3. The v2 indexes are still populated, so search continues to work without a reindex.

## Performance Considerations

| Deployment Size | Total Records  | Expected Duration                                                  | Recommended Mode                                               |
| --------------- | -------------- | ------------------------------------------------------------------ | -------------------------------------------------------------- |
| Small           | < 1,000        | Under a minute                                                     | Synchronous                                                    |
| Medium          | 1,000 - 10,000 | 1 - 10 minutes                                                     | Synchronous                                                    |
| Large           | 10,000 - 100K  | 10 minutes - 2 hours                                               | Asynchronous                                                   |
| Very Large      | > 100K         | Multiple hours, may exceed Lambda 15-minute timeout per invocation | Asynchronous, may need splitting via `--operation` / `--limit` |
