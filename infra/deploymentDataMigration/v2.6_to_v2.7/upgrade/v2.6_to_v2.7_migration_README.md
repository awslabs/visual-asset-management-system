# VAMS v2.6 to v2.7 Migration Guide

## Overview

This is the single consolidated migration for the VAMS v2.7 release. One script,
`v2.6_to_v2.7_migration.py`, runs three independent steps (select with `--steps`; default runs all):

| Step                              | `--steps` value            | What it does                                                                                                                                                   |
| --------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Orphaned trigger cleanup          | `orphanedTriggers`         | Deletes `WorkflowTriggersStorageTable` rows whose workflow is archived or missing — including the two retired built-ins' `fileUpload` triggers.                |
| Vector index backfill             | `vectorBackfill`           | Invokes the deployed `vectorReindexer` Lambda so every latest live file is analysed by the system GenAI pipeline and receives a vector.                        |
| System-pipeline retirement report | `systemPipelineRetirement` | Lists executions of the two retired workflows that are still in flight and user workflows that reference a retired pipeline id, with guidance. Writes nothing. |

Running with no `--steps` (or `--steps all`) runs the steps in the order above. Any step can be run on its own.

### Step 1 — Orphaned trigger cleanup (`orphanedTriggers`)

v2.7 retires the GenAI 3D Metadata Labeling and CAD/Mesh Metadata Extraction built-ins in favour of the
single `system-genai-metadata` pipeline. The v2.7 deploy removes their nested stacks, and the schema
importer archives their `GLOBAL` pipeline and workflow rows
(`genai-metadata-3d-labeling-obj-glb-fbx-ply-stl-usd`, `metadata-extraction-cad-mesh`). Archiving a
workflow leaves its `fileUpload` trigger rows in place, and the v2.6 upload dispatcher kept matching them:
every matching upload paid one `executeWorkflow` invocation that ended `400 Workflow is archived and cannot
be executed.` — no execution row, no dead-letter entry, no alarm. The same happened to any workflow of your
own that was archived through the API before v2.7.

The step enumerates every `fileUpload` trigger row through the `TriggersByBaseTypeGSI` index, looks up the
workflow row in `WorkflowStorageTableV2` (one `GetItem` per distinct workflow), and deletes a trigger row
when:

-   its workflow is one of the two retired built-ins under `GLOBAL` — deleted whether or not the deploy-time
    archive reached the workflow row (that archive is best-effort, and the pipeline resources are gone either
    way);
-   its workflow row is missing; or
-   its workflow row carries `archived: true`.

Rows whose workflow is live are kept. Both the bare `fileUpload` sort key and the `fileUpload#<triggerId>`
form of an additional trigger are handled. Every deleted row is logged with its composite key and reason,
and the summary counts each reason separately. `dry_run` names each row it would delete without deleting;
`limit` caps the number of trigger rows examined.

The step is idempotent: the rows it deletes belong to workflows that cannot fire, so a second run finds
nothing to delete. It **deletes rows**, so the account-id confirmation described under
[Confirming the target](#confirming-the-target) applies.

To confirm a real run took effect, observe the step's own result: re-run it with
`--steps orphanedTriggers --dry-run` and check that the summary reads `Rows that would be deleted` = 0
while `Trigger rows examined` is still > 0 (the live workflows' triggers — at least the system workflow's
own `fileUpload` trigger when the system pipeline is registered with it), or list the trigger keys that
remain and confirm no `GLOBAL:<retired id>` key is among them:

```bash
aws dynamodb query --table-name <triggers table> --index-name TriggersByBaseTypeGSI \
  --key-condition-expression 'triggerBaseType = :t' \
  --expression-attribute-values '{":t":{"S":"fileUpload"}}' \
  --projection-expression '#k' --expression-attribute-names '{"#k":"workflowDatabaseId:workflowId"}'
```

An upload does not verify this step: after the v2.7 deploy the dispatcher skips archived and disabled
workflows on its own, so no `400` is recorded whether or not a trigger row was deleted.

### Step 2 — Vector index backfill (`vectorBackfill`)

Natural-language search (`app.vectorSearch.enabled`) is served from a DynamoDB vector index that the
system GenAI pipeline populates through its upload trigger: each execution embeds one file version and
publishes a `vector.embedding.ready` event that the vector indexer writes to the table. A file that existed
before the upgrade therefore has no vector until it is re-processed.

The step invokes the deployed `vectorReindexer` Lambda (function name resolved from the SSM parameter
`lambdaFunctions/vectorReindexer`, which the search stack publishes only when vector search is enabled)
with the payload:

```json
{ "operation": "enqueue", "dryRun": false }
```

`--clear-vectors` sends `"operation": "both"`, which deletes every stored vector before enqueueing.
`--dry-run` sends `"dryRun": true` (the reindexer counts instead of enqueueing) and `--limit N` sends
`"limit": N`. The reindexer enumerates the latest live version of every file in every asset bucket
(archived assets excluded), filters them by the system workflow's input-file filters, and enqueues one
system-workflow execution per file onto the `SystemWorkflowLaunchQueue`; the launcher starts them at most
`app.vectorSearch.indexingConcurrency` at a time. The reindexer re-invokes itself when it nears its own
15-minute cap, so a synchronous invocation that outlives the client read timeout is reported as
"continues in the background", not as a failure.

The step returns when the work is **enqueued**. Its summary prints the reindexer's response —
`reindexRunId`, `phase`, `deleted`, `enqueued`, `chunks`, `continued` (the reindexer re-invoked itself to
finish), `invocations`, and `tableEmpty` once a clear has finished — and the run id as the executions-list
filter value. Reindex executions are stored with trigger type `System-Reindex` and an execution group id of
the form `vec-<runId>-<chunk>` (chunks numbered from 0, one per 1,000 files), so one chunk of the run is
listed by group id and every reindex run by trigger type:

```bash
vamscli execution list --group-id vec-<runId>-0 --auto-paginate
vamscli execution list --workflow-database-id GLOBAL --workflow-id system-genai-metadata --trigger-type System-Reindex --status RUNNING
```

A chunk can be aborted with `vamscli execution abort <executionId> --group-id vec-<runId>-<chunk> --yes`.
Each execution renders or extracts its file, calls the Bedrock analysis model, and calls the Bedrock
embedding model, so a large deployment bills accordingly; a first run with `--limit 25` shows the per-file
cost before the full run. `--async` invokes the reindexer with `InvocationType=Event` and returns
immediately.

Under `--steps all`, a deployment that does not publish the `vectorReindexer` function (vector search
disabled) — or a config that sets neither `resource_names_ssm_param_prefix` nor
`vector_reindexer_function_name`, so nothing can resolve the name — skips this step with a warning; under
`--steps vectorBackfill` that is an error, because the operator asked for the step by name.

Repeat-safety: `enqueue` re-embeds files in place — each vector item is keyed on the file path and S3
version id, so a repeat overwrites the same items — and the system workflow's `perInputFileVersion` lock
drops a duplicate launch for a version whose execution is still running. `both` is safe to repeat as well,
but every repeat empties the index until the executions finish.

### Step 3 — System-pipeline retirement report (`systemPipelineRetirement`)

Read-only. Prints three listings:

1. **Retired built-in definitions** — for each retired id, whether the `GLOBAL` pipeline and workflow rows
   are absent, archived (expected after the deploy), or present and **not** archived (the deploy-time
   archive did not run; the report prints the `vamscli pipeline delete` / `vamscli workflow delete` command
   that archives it).
2. **In-flight executions of retired workflows** — rows of `WorkflowExecutionsStorageTableV2` under
   `GLOBAL:<retired workflow id>` whose `executionStatus` is not terminal (`SUCCEEDED`, `FAILED`, `ABORTED`,
   `TIMED_OUT`). Their inner state machines were deleted with the retired nested stacks, so no result will
   arrive; the workflow records each one `FAILED` when its task times out (18,000 s for GenAI labeling,
   900 s for CAD/Mesh extraction). Abort them with `vamscli execution abort <executionId>` or wait.
3. **User workflows referencing a retired pipeline** — every `WorkflowStorageTableV2` row (other than the
   retired workflows themselves) whose `specifiedPipelines` name `GLOBAL:genai-metadata-3d-labeling-obj-glb-fbx-ply-stl-usd`
   or `GLOBAL:metadata-extraction-cad-mesh`. They fail at execute because the pipeline is archived; edit
   each one to replace the step with `GLOBAL:system-genai-metadata` (template
   `system-genai-metadata-default`) or remove the step. Archived rows are listed too (an unarchive would
   revive the problem).

`limit` caps the executions listed per retired workflow and the workflow rows scanned. `dry_run` changes
nothing about this step. The step exits 0 whenever its reads succeed; findings are printed under an
`ACTION REQUIRED` line.

## Prerequisites

### Required AWS Resources

1. **v2.7 CDK stack deployed.** The deploy archives the retired built-ins (step 1 relies on it), creates
   `VectorEmbeddingsStorageTable` and — when `app.vectorSearch.enabled` — its vector index, registers the
   system pipeline and its trigger, and publishes the deployment's resource names to SSM Parameter Store
   (base prefix exposed as the CloudFormation output `ResourceNamesSSMParamPrefixOutput`).
2. **For the `vectorBackfill` step:** `app.vectorSearch.enabled: true` in the deployed configuration, so
   the `vectorReindexer` function exists and its name is published under
   `<prefix>/lambdaFunctions/vectorReindexer`.

### Required IAM Permissions

The principal running this migration needs (orphanedTriggers step: DynamoDB `Query` on the triggers
table's `TriggersByBaseTypeGSI`, `GetItem` on the workflow V2 table, and `DeleteItem` on the triggers
table; vectorBackfill step: `lambda:InvokeFunction` on the `vectorReindexer` function;
systemPipelineRetirement step: DynamoDB `Query` on the executions V2 table's
`WorkflowExecutionsByWorkflowGSI`, `Scan` on the workflow V2 table, and `GetItem` on the workflow and
pipeline V2 tables):

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": ["ssm:GetParametersByPath"],
            "Resource": "arn:*:ssm:*:*:parameter/*/resourceNames*"
        },
        {
            "Effect": "Allow",
            "Action": ["cloudformation:DescribeStacks", "sts:GetCallerIdentity"],
            "Resource": "*"
        },
        {
            "Effect": "Allow",
            "Action": [
                "dynamodb:Query",
                "dynamodb:Scan",
                "dynamodb:GetItem",
                "dynamodb:DeleteItem"
            ],
            "Resource": ["arn:*:dynamodb:*:*:table/*", "arn:*:dynamodb:*:*:table/*/index/*"]
        },
        {
            "Effect": "Allow",
            "Action": ["lambda:InvokeFunction"],
            "Resource": "arn:*:lambda:*:*:function:*vectorReindexer*"
        }
    ]
}
```

> The DynamoDB statement covers the `orphanedTriggers` step (`Query` on `TriggersByBaseTypeGSI`, `GetItem` on
> the workflow V2 table, `DeleteItem` on the triggers table) and the `systemPipelineRetirement` step
> (`Query` on `WorkflowExecutionsByWorkflowGSI`, `Scan` on the workflow V2 table, `GetItem` on the workflow
> and pipeline V2 tables); the `/index/*` resource is what `Query` on a global secondary index requires.
> `dynamodb:DeleteItem` is the only write. The `vectorBackfill` step needs only `lambda:InvokeFunction`;
> the reindexer runs under its own role. `ssm:GetParametersByPath` is needed for the prefix lookup,
> `cloudformation:DescribeStacks` only to read the `ResourceNamesSSMParamPrefixOutput` output while
> configuring the migration, and `sts:GetCallerIdentity` for the target echo (a principal denied it still
> runs; the echo then shows `UNRESOLVED`). When the tables use a customer-managed KMS key
> (`app.useKmsCmkEncryption.enabled`), add `kms:Decrypt` on that key. Scope the resource ARNs to the
> deployment's tables and function where required.

### Python Dependencies

```bash
pip install boto3
```

Python 3.9 or later. The script imports only the standard library, `boto3`, and
`infra/deploymentDataMigration/tools/ssm_resource_lookup.py`, so it runs from a checkout of the repository
without the backend's dependencies.

## Configuration

Copy the template and fill in the prefix:

```bash
cp v2.6_to_v2.7_migration_config.json my_migration_config.json
```

| Key                                         | Required | Purpose                                                                                                                                         |
| ------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `resource_names_ssm_param_prefix`           | yes      | Core stack output `ResourceNamesSSMParamPrefixOutput`, format `/{configName}-{baseStackName}/resourceNames`. Every name below resolves from it. |
| `workflow_triggers_storage_table_name`      | no       | Override for `dynamoTables/workflowTriggersStorage`                                                                                             |
| `workflow_storage_table_name_v2`            | no       | Override for `dynamoTables/workflowStorageV2` (used by steps 1 and 3)                                                                           |
| `vector_reindexer_function_name`            | no       | Override for `lambdaFunctions/vectorReindexer`                                                                                                  |
| `clear_vectors`                             | no       | Same as `--clear-vectors` (default `false`)                                                                                                     |
| `workflow_executions_storage_table_name_v2` | no       | Override for `dynamoTables/workflowExecutionsStorageV2`                                                                                         |
| `pipeline_storage_table_name_v2`            | no       | Override for `dynamoTables/pipelineStorageV2`                                                                                                   |
| `dry_run`, `limit`                          | no       | Same as `--dry-run` / `--limit`                                                                                                                 |
| `aws_profile`, `aws_region`                 | no       | Same as `--profile` / `--region`                                                                                                                |

A value that is `null`, empty, or still a `<PLACEHOLDER>` is treated as unset. `_comment*` keys and
`_instructions` are ignored.

## Running the migration

Always dry-run first, then run:

**Linux / macOS**

```bash
chmod +x run_migration.sh
./run_migration.sh my_migration_config.json --dry-run
./run_migration.sh my_migration_config.json
```

**Windows**

```powershell
.\run_migration.ps1 -ConfigFile my_migration_config.json -DryRun
.\run_migration.ps1 -ConfigFile my_migration_config.json
```

**Directly**

```bash
python v2.6_to_v2.7_migration.py --config my_migration_config.json --dry-run
python v2.6_to_v2.7_migration.py --config my_migration_config.json
python v2.6_to_v2.7_migration.py --config my_migration_config.json --steps orphanedTriggers
python v2.6_to_v2.7_migration.py --config my_migration_config.json --steps vectorBackfill --clear-vectors
python v2.6_to_v2.7_migration.py --config my_migration_config.json --steps systemPipelineRetirement
```

Flags: `--steps {orphanedTriggers,vectorBackfill,systemPipelineRetirement,all}` (default `all`),
`--dry-run`, `--limit N`, `--clear-vectors`, `--async`, `--profile`, `--region`,
`--log-level {DEBUG,INFO,WARNING,ERROR}`, `--confirm-account <id>`, `--yes`. The wrappers write a
timestamped log to `logs/` and exit with the migration's own status.

A dry run reports zero rows when there is nothing to do, so a zero-row result on its own is not evidence
that the step is configured correctly. A deployment that ran either retired pipeline with
`autoRegisterAutoTriggerOnFileUpload: true` holds at least one orphaned trigger row; read the counts
against what the deployment actually holds.

### Confirming the target

The script prints the resolved account, Region, caller ARN, SSM prefix, dry-run flag, and what the run
deletes before touching anything. When a run deletes data (`orphanedTriggers`, or `vectorBackfill` with
`--clear-vectors`) and is not a dry run, it asks you to type the account id. `--confirm-account <id>`
replaces the prompt with a check that the resolved account matches (preferred for automation); `--yes`
skips the prompt without checking.

## Rollback

| Step                       | Writes to                                                                                                                                                      | Reversible by redeploying v2.6? | Safe to repeat?                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------ |
| `orphanedTriggers`         | **Deletes rows** from the workflow triggers table                                                                                                              | No                              | Yes — a second run finds nothing     |
| `vectorBackfill`           | Nothing directly; the reindexer it invokes deletes every vector item when `--clear-vectors` is passed, and launches executions that write vectors and metadata | No                              | Yes — items are overwritten in place |
| `systemPipelineRetirement` | Nothing                                                                                                                                                        | n/a                             | Yes                                  |

What each step does to your data:

-   `orphanedTriggers` deletes only rows whose workflow is archived, missing, or retired, so nothing that
    could fire is lost. Redeploying v2.6 does not restore them: the retired built-ins' triggers are
    re-registered only if their (rejected) configuration blocks are restored and a v2.6 stack redeploys, and
    a user workflow's trigger deleted because the workflow was archived stays deleted (re-create it with
    `vamscli workflow trigger set` after unarchiving the workflow, if it is ever needed).
-   `vectorBackfill` with `--clear-vectors` empties the vector index; natural-language search returns nothing
    until the launched executions complete. The executions themselves (rows, run-bucket objects, written
    metadata and attributes) remain in history like any other run and are removed only through the
    executions API (`vamscli execution permanent-delete`, or per group with the abort route's `--group-id`).
-   Redeploying v2.6 after a v2.7 deploy is a separate matter (the retired nested stacks and the vector index
    would be re-created / deleted by CloudFormation); this migration neither helps nor hinders it.

### Before you run

-   **Back up the workflow triggers table** (`aws dynamodb export-table-to-point-in-time`, or enable
    point-in-time recovery) — `orphanedTriggers` deletes rows and there is no automated rollback. See
    [Update the solution](https://awslabs.github.io/visual-asset-management-system/deployment/update-the-solution).
-   **Confirm the target account and Region** from the echo at startup before answering the prompt.
-   **Abort in-flight executions of the retired workflows before the v2.7 deploy** where you can; the
    `systemPipelineRetirement` step lists any that remain afterwards.

## Migration Checklist

-   [ ] Abort or drain in-flight executions of the two retired workflows before deploying
-   [ ] Edit `infra/config/config.json`: remove `app.pipelines.useGenAiMetadata3dLabeling` and
        `app.pipelines.useConversionCadMeshMetadataExtraction`; add `app.vectorSearch` and
        `app.pipelines.useSystemGenAiMetadata`
-   [ ] Deploy the v2.7 CDK stack
-   [ ] **Export or enable point-in-time recovery on the workflow triggers table**
-   [ ] Get the SSM resource-name prefix from the `ResourceNamesSSMParamPrefixOutput` CloudFormation output
-   [ ] Copy `v2.6_to_v2.7_migration_config.json`, set the prefix and the AWS region
-   [ ] Run a dry run (`--dry-run`); read the `orphanedTriggers` counts against what the deployment holds
-   [ ] Run the migration
-   [ ] Act on the `systemPipelineRetirement` report (abort in-flight executions, re-point workflows)
-   [ ] Watch the vector backfill (`vamscli execution list ... --trigger-type System-Reindex`) and confirm
        `vamscli search nlp -q "<something in a seeded file>"` finds a re-embedded file
-   [ ] Confirm the trigger cleanup took effect: re-run `--steps orphanedTriggers --dry-run` and check that the
        summary reads `Rows that would be deleted` = 0 with `Trigger rows examined` > 0 (the live workflows'
        triggers), or list the remaining trigger keys with the `aws dynamodb query` under Step 1 and confirm
        no `GLOBAL:<retired id>` key remains

## Troubleshooting

**Symptom:** `No vectorReindexer function is published for this deployment`

**Cause:** `app.vectorSearch.enabled` is false on the deployed configuration, so the search stack created
no reindexer and published no `lambdaFunctions/vectorReindexer` parameter. Under `--steps all` the step is
skipped; under `--steps vectorBackfill` it fails.

**Solution:** Enable vector search and redeploy, then re-run the step.

**Symptom:** `AccessDeniedException` on `dynamodb:Query` with an `/index/` ARN in the message

**Solution:** The `TriggersByBaseTypeGSI` and `WorkflowExecutionsByWorkflowGSI` reads need
`dynamodb:Query` on `arn:*:dynamodb:*:*:table/*/index/*`, not only on the table ARN.

**Symptom:** the `LAMBDA INVOCATION TIMED OUT` warning during `vectorBackfill`

**Cause:** the synchronous invoke outlived the client's read timeout; the reindexer keeps running and
re-invokes itself to continue.

**Solution:** Nothing to repair. Watch the reindexer's CloudWatch log group and the executions list. Use
`--async` on very large deployments.

**Symptom:** `Refusing to run: --confirm-account ... does not match the resolved account`

**Solution:** The ambient credentials or `aws_profile` point at a different account than intended. Fix
the profile (or pass `--profile`) — the SSM prefix carries no account, so two deployments with the same
`configName`/`baseStackName` resolve identical parameter paths in different accounts.

## Testing

Unit tests run under `moto` (installed in the backend dev environment) and a hand-written Lambda fake;
they seed synthetic rows for every transform, because a zero-row dry run proves nothing:

```bash
cd infra/deploymentDataMigration/v2.6_to_v2.7/upgrade
python -m pytest -q
```

The wrapper's exit-status propagation, this README's IAM policy, and the step names documented in the
upgrade guide are additionally pinned by `infra/test/platform/migrationTooling.test.ts`
(`cd infra && npx jest test/platform/migrationTooling.test.ts`).
