# VAMS v2.6 to v2.7 Migration Guide

## Overview

This is the single consolidated migration for the VAMS v2.7 release. One script,
`v2.6_to_v2.7_migration.py`, runs six steps (select with `--steps`; default runs all):

| Step                              | `--steps` value            | What it does                                                                                                                                                                                                                  |
| --------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Asset location folder keys        | `assetLocationFolderKeys`  | Finds asset rows whose location key has no trailing `/`, no object at the key and objects under `{key}/`, reports them, and appends the `/` on a real run. Runs first.                                                        |
| Orphaned trigger cleanup          | `orphanedTriggers`         | Deletes `WorkflowTriggersStorageTable` rows whose workflow is archived or missing — including the two retired built-ins' `fileUpload` triggers.                                                                               |
| Vector index backfill             | `vectorBackfill`           | Invokes the deployed `vectorReindexer` Lambda so every latest live file is analysed by the system GenAI pipeline and receives a vector. Skipped when vector search is not enabled on the deployment.                          |
| Metadata backfill (opt-in)        | `metadataBackfill`         | With vector search off and the system pipeline on, and only when requested, invokes the `vectorReindexer` with `enqueue` so every existing file gets GenAI metadata.                                                          |
| System-pipeline retirement report | `systemPipelineRetirement` | Lists executions of the two retired workflows that are still in flight and user workflows that reference a retired pipeline id, with guidance. Writes nothing.                                                                |
| Asset location index (required)   | `assetLocationIndex`       | Runs last, after `assetLocationFolderKeys`. Writes `locationBucket` and `locationKey` on every asset row for the new `AssetLocationGSI`, reports the rows it cannot index, and writes the completion marker last. No S3 call. |

Running with no `--steps` (or `--steps all`) runs the steps in the order above. Any step can be run on its own, but `assetLocationIndex` builds the index from the location keys `assetLocationFolderKeys` fixes, so run `assetLocationFolderKeys` first: under `--steps all` the index step runs last and, in a real run, is skipped when `assetLocationFolderKeys` failed.

Every run is a **dry run** unless `--execute` is given and the config's `dry_run` is `false` (the shipped
config sets it `true`). A real run that changes asset location keys, deletes trigger rows, deletes vectors, or
launches Bedrock-billed executions is confirmed against the resolved AWS account id first; see
[Confirming the target](#confirming-the-target).

### Step 0 — Asset location folder keys (`assetLocationFolderKeys`)

From v2.7 an asset location key (`assetLocation.Key` on the asset row) has one meaning: a key ending in `/`
is a folder, and any other key names one Amazon S3 object, a single-file asset. Before v2.7 a folder key
written without the trailing `/` still listed the files under it; v2.7 reads it as one object and finds
none. This step finds those rows and gives them back their `/`. It runs first, before `vectorBackfill` and
`metadataBackfill` and before any later step that walks every asset's location, so they read each folder
as a folder.

The step scans every asset row, archived rows included, and for each key without a trailing `/`:

| What it finds                                             | Report class           | Real run                                                   |
| --------------------------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| An object at the key, current or archived                 | `single-file`          | Part (b) below, when the file has a copy named like it     |
| No object at the key, objects under `{key}/`              | `folder-without-slash` | Appends `/`, only if the key is still the one read         |
| No object at the key and none under `{key}/`              | `no-objects`           | Nothing; listed in the report for you to check             |
| A key it cannot read (unregistered bucket, access denied) | `unreadable`           | Nothing; listed in the report, and the step exits non-zero |

A key ending in `/` is a folder and costs no Amazon S3 read. For each other key the step sends one
`HeadObject` and, when there is no current object, one `ListObjectVersions` with `MaxKeys=1` for the key
itself (an archived file is still a single file, never a folder) and one `ListObjectsV2` with `MaxKeys=1`
under `{key}/`; it never walks a bucket. A key that only shares its first characters with others
(`p/h` next to `p/h.bak` or `p/hh/`) has nothing under `p/h/` and is reported as `no-objects`.

-   **Report.** Every finding is one JSON line of `assetLocationFolderKeys-dry-run-report.jsonl` or
    `assetLocationFolderKeys-execute-report.jsonl` in `asset_location_output_dir` (default: the working
    directory), with the database id, asset id, bucket, key, class and action.
-   **Pacing.** The step pauses `asset_location_pace_seconds` (default `0.05`) after each key that needed an
    Amazon S3 read, and scans the asset table 100 rows at a time.
-   **Checkpoint and resume.** After every page the step saves its scan position to
    `assetLocationFolderKeys-<dry-run|execute>-checkpoint.json` next to the report. A stopped run continues
    from there with `--resume` (`-Resume` in PowerShell); a finished run removes the file. A checkpoint
    written for another asset table is refused.
-   **Idempotent.** The write is conditional on the key being unchanged, so a key edited in between is
    skipped, and a second run finds nothing to append. Part (b) never overwrites a record and skips every
    asset row it marked done (see below).
-   **Account confirmation.** A real run changes asset rows, so it asks for the resolved account id like
    `orphanedTriggers` does (see [Confirming the target](#confirming-the-target)).

#### Part (b): the copy named like the file

Before v2.7 a file in a single-file asset's companion folder named exactly like the asset's file,
`{key}/{name}`, had the asset-relative path `/{name}`. From v2.7 `/{name}` is the asset's file and that
copy is `/{name}/{name}`. For every single-file location whose copy exists (the step lists the versions of
`{key}/{name}` and of `{key}` itself, one key each), the records that describe the copy move from
`/{name}` to `/{name}/{name}`:

| Table                                                                                               | What moves                                                                                         |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `AssetFileMetadataStorageTableV2`, `FileAttributeStorageTableV2`                                    | Every metadata and attribute record at `/{name}`                                                   |
| `AssetFileVersionsStorageTableV2` (and the legacy `AssetFileVersionsStorageTable` when it has rows) | An asset version's entry for `{name}` whose S3 version id is one of the copy's                     |
| `AssetFileMetadataVersionsStorageTable`                                                             | That asset version's `metadata:` and `attribute:` rows for `/{name}` (`type:filePath:metadataKey`) |
| `AssetFileVersionHistoryStorageTable`                                                               | Every history record at `/{name}` except those whose version id is one of the file's own           |

Every move is one transaction: the record is written at the new path only if nothing is there yet, and
the old record is deleted only if it is still there. A record already at `/{name}/{name}` is never
overwritten; the report names the clash and the old record stays. An entry whose version belongs to the
asset's own file, or to neither key, stays and is reported. `VectorEmbeddingsStorageTable` and the workflow
and pipeline execution tables are not changed: run `vectorBackfill` after this step (it runs next under
`--steps all` when vector search is on) so the copy's vectors are rewritten for its new path, and past
executions keep the paths they read.

When a real run has finished part (b) for a single-file asset without an error, with or without a copy,
it sets `assetLocationCopyRecordsMovedAt` (the time, in UTC) on that asset row, conditional on the row
having none. Every later run, dry or real and from any directory, skips a row that carries it before any
read, so metadata written for the asset's own file at `/{name}` after the move is never moved. The
attribute travels with the row when the asset is archived or unarchived and is not returned by the API.

**Run the step before users edit metadata on single-file assets.** File metadata and file attribute
records carry no modification time, so part (b) cannot tell a record written for the copy before the
upgrade from one written for the asset's own file between the deploy and the step's real run: it moves
every metadata and attribute record at `/{name}` of an asset whose copy exists. Run the step right after the
deploy, before users or pipelines write file metadata on single-file assets, or read the dry-run report's
part (b) lines for those assets first and move a record back by hand when it belongs to the asset's file.
Version entries and file version history carry an S3 version id, so they are decided by version and are not
affected.

Read the dry-run report before the real run. A `no-objects` row is an asset whose files are gone or were
never written; an `unreadable` row usually means the migration principal cannot read that bucket.
Part (b) lines carry `"part": "companion-copy"`, the table and the old and new paths.

### Step 1 — Orphaned trigger cleanup (`orphanedTriggers`)

v2.7 retires the GenAI 3D Metadata Labeling and CAD/Mesh Metadata Extraction built-ins in favour of the
single `system-genai-metadata` pipeline. The v2.7 deploy removes their nested stacks, and the schema
importer archives their `GLOBAL` pipeline and workflow rows
(`genai-metadata-3d-labeling-obj-glb-fbx-ply-stl-usd`, `metadata-extraction-cad-mesh`). Archiving a
workflow leaves its `fileUpload` trigger rows in place, and the v2.6 upload dispatcher kept matching them:
every matching upload paid one `executeWorkflow` invocation that ended `400 Workflow is archived and cannot
be executed.` — no execution row, no dead-letter entry, no alarm. The same happened to any workflow of your
own that was archived through the API before v2.7.

The step enumerates every `fileUpload` trigger row through the `TriggersByBaseTypeGSI` index, looks up the
workflow row in `WorkflowStorageTableV2` (one `GetItem` per distinct workflow), and deletes a trigger row
when:

-   its workflow is one of the two retired built-ins under `GLOBAL` — deleted whether or not the deploy-time
    archive reached the workflow row (that archive is best-effort, and the pipeline resources are gone either
    way);
-   its workflow row is missing; or
-   its workflow row carries `archived: true`.

Rows whose workflow is live are kept. Both the bare `fileUpload` sort key and the `fileUpload#<triggerId>`
form of an additional trigger are handled. Every deleted row is logged with its composite key and reason,
and the summary counts each reason separately. A dry run (the default) names each row it would delete
without deleting; `limit` caps the number of trigger rows examined.

The step is idempotent: the rows it deletes belong to workflows that cannot fire, so a second run finds
nothing to delete. It **deletes rows**, so the account-id confirmation described under
[Confirming the target](#confirming-the-target) applies.

To confirm a real run took effect, observe the step's own result: re-run it with
`--steps orphanedTriggers` (without `--execute`) and check that the summary reads
`Rows that would be deleted` = 0 while `Trigger rows examined` is still > 0 (the live workflows' triggers —
at least the system workflow's own `fileUpload` trigger when the system pipeline is registered with it), or
list the trigger keys that remain and confirm no `GLOBAL:<retired id>` key is among them:

```bash
aws dynamodb query --table-name <triggers table> --index-name TriggersByBaseTypeGSI \
  --key-condition-expression 'triggerBaseType = :t' \
  --expression-attribute-values '{":t":{"S":"fileUpload"}}' \
  --projection-expression '#k' --expression-attribute-names '{"#k":"workflowDatabaseId:workflowId"}'
```

An upload does not verify this step: after the v2.7 deploy the dispatcher skips archived and disabled
workflows on its own, so no `400` is recorded whether or not a trigger row was deleted.

### Step 2 — Vector index backfill (`vectorBackfill`)

Natural-language search (`app.vectorSearch.enabled`) is served from a DynamoDB vector index that the
system GenAI pipeline populates through its upload trigger: each execution embeds one file version and
publishes a `vector.embedding.ready` event that the vector indexer writes to the table. A file that existed
before the upgrade therefore has no vector until it is re-processed.

The step invokes the deployed `vectorReindexer` Lambda (function name resolved from the SSM parameter
`lambdaFunctions/vectorReindexer`) with the payload:

```json
{ "operation": "enqueue", "dryRun": false }
```

`--clear-vectors` sends `"operation": "both"`, which deletes every stored vector before enqueueing.
Without `--execute` the payload carries `"dryRun": true` (the reindexer counts instead of enqueueing), and
`--limit N` sends `"limit": N`. The reindexer enumerates the latest live version of every file in every
asset bucket (archived assets excluded), filters them by the system workflow's input-file filters, and
enqueues one system-workflow execution per file onto the `SystemWorkflowLaunchQueue`; at most
`app.vectorSearch.indexingConcurrency` of those executions run at once (each holds a reindex slot until it
ends; the rest wait in the queue). The reindexer re-invokes itself when it
nears its own 15-minute cap, so a synchronous invocation that outlives the client read timeout is reported
as "continues in the background", not as a failure.

The backfill embeds live files only. The files of an archived asset and a file behind a delete marker are
not embedded, so `vamscli search nlp --include-archived` does not find a file archived before the upgrade.
Unarchiving such a file (`vamscli assets unarchive <assetId> --unarchive-files`, or a file unarchive)
queues its embedding onto the same launch queue, and the file is searchable once that execution finishes.
A file that already has a vector item is flipped back to live and not re-embedded.

The step returns when the work is **enqueued**. Its summary prints the reindexer's response —
`reindexRunId`, `phase`, `deleted`, `enqueued`, `chunks`, `continued` (the reindexer re-invoked itself to
finish), `invocations`, and `tableEmpty` once a clear has finished — and the run id as the executions-list
filter value. Reindex executions are stored with trigger type `System-Reindex` and an execution group id of
the form `vec-<runId>-<chunk>` (chunks numbered from 0, one per 1,000 files), so one chunk of the run is
listed by group id and every reindex run by trigger type:

```bash
vamscli execution list --group-id vec-<runId>-0 --auto-paginate
vamscli execution list --workflow-database-id GLOBAL --workflow-id system-genai-metadata --trigger-type System-Reindex --status RUNNING
```

A chunk can be aborted with `vamscli execution abort <executionId> --group-id vec-<runId>-<chunk> --yes`.
A dry run starts nothing, so its summary labels the counts `Would delete` and `Would enqueue` and prints
no watch commands.
Each execution renders or extracts its file, calls the Bedrock analysis model, and calls the Bedrock
embedding model, so a large deployment bills accordingly; a first run with `--limit 25` shows the per-file
cost before the full run. Because the executions are the cost, a real `vectorBackfill` run — with or
without `--clear-vectors` — passes through the same account-id confirmation as the deleting steps (see
[Confirming the target](#confirming-the-target)). `--async` invokes the reindexer with
`InvocationType=Event` and returns immediately.

#### When the step runs, and when it is skipped

The step reads the deployment first: the `VECTORSEARCH` row of the app feature table (resolved from the
same SSM prefix as every other name, `dynamoTables/appFeatureEnabledStorage`, read with one consistent
`GetItem`), and the `lambdaFunctions/vectorReindexer` parameter. The deploy writes the `VECTORSEARCH` row
only while `app.vectorSearch.enabled` resolves to `true`.

| Deployment state                                                                                         | What the step does                                                                                                      | Exit           |
| -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------- |
| `VECTORSEARCH` absent (vector search off), reindexer published or not                                    | Skips, logs `Vector search is not enabled on this deployment, so there is nothing to re-index; vectorBackfill skipped.` | `0`            |
| `VECTORSEARCH` present and a reindexer to invoke                                                         | Invokes it as described above                                                                                           | `0` on success |
| `VECTORSEARCH` present, no reindexer published and no override set                                       | Fails: the deployment is inconsistent; redeploy, or set `vector_reindexer_function_name`                                | `1`            |
| State unreadable: no prefix, SSM or the table not readable, a prefix that publishes no app feature table | Fails, naming what could not be read; the step is never skipped on an error                                             | `1`            |

The rule is the same under `--steps all` and `--steps vectorBackfill`. The target echo lists the planned
steps (`vectorBackfill (skipped: vector search is not enabled)`), a skipped backfill needs no account-id
confirmation because it bills nothing, and the closing `MIGRATION SUMMARY` prints
`vectorBackfill: skipped: vector search is not enabled`. `vector_reindexer_function_name` is used only
while the switch is present.

The four cases an operator meets:

-   **Upgrading with vector search on:** deploy v2.7, then run the migration; `vectorBackfill` embeds the
    files that existed before the upgrade.
-   **Upgrading with vector search off:** the migration skips `vectorBackfill`, and nothing else is needed.
-   **Turning vector search on later on a 2.7 deployment:** deploy with `app.vectorSearch.enabled: true`,
    then run this script again with `--steps vectorBackfill` (or set `app.vectorSearch.reindexOnCdkDeploy`
    to `true` for one deploy, or invoke the reindexer directly). The run costs one analysis and one
    embedding per file in scope, as on an upgrade, so try `--limit 25` first.
-   **Upgrading with vector search off and the system pipeline on:** `vectorBackfill` is skipped; to analyze
    the existing files (GenAI metadata, no vectors), opt in to `metadataBackfill` (Step 3).
-   **Turning vector search off and on again:** the vectors written before survive; the same
    `--steps vectorBackfill` run embeds the files whose pipeline runs completed while it was off.

The script is not tied to the upgrade itself: every step reads the deployment as it is when it runs, so
it can be run again on any 2.7 deployment. See [Reindexing](https://github.com/awslabs/visual-asset-management-system/blob/main/documentation/docusaurus-site/docs/concepts/vector-search.md#reindexing) for the reindexer's operations.

Repeat-safety: `enqueue` re-embeds files in place — each vector item is keyed on the file path and S3
version id, so a repeat overwrites the same items — and the system workflow's `perInputFileVersion` lock
drops a duplicate launch for a version whose execution is still running. `both` is safe to repeat as well,
but every repeat empties the index until the executions finish.

### Step 3 — Metadata backfill for existing files (`metadataBackfill`, opt-in)

With vector search off, `vectorBackfill` is skipped, and the files that predate the system GenAI metadata
pipeline have no `sys_*` attributes or `genai_*` metadata until a run reaches them. The deploy builds the
`vectorReindexer`, its launch queue and launcher whenever the pipeline is on and registers its workflow,
with vector search on or off. `metadataBackfill` invokes that reindexer with `{"operation": "enqueue"}`, so
the system workflow analyzes every existing latest live file the workflow's input filters admit; with
vector search off the runs skip the embedding step. It is opt-in: it runs only when
`generate_metadata_for_existing_files` is `true` in the config (shipped `false`) or
`--generate-metadata-for-existing-files` (PowerShell: `-GenerateMetadataForExistingFiles`) is passed. It
honours `--execute`, `dry_run`, `--limit`, `--async` and the account-id confirmation exactly as
`vectorBackfill` does, and costs one analysis run per file in scope. `--clear-vectors` does not apply (there
are no vectors with vector search off); the step says so when it is set.

The step reads the same deployment state as `vectorBackfill`, once per run:

| Deployment state                                                     | `vectorBackfill`                        | `metadataBackfill`                                                     |
| -------------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------- |
| `VECTORSEARCH` present (vector search on)                            | runs                                    | skipped: `vectorBackfill analyzes every file when vector search is on` |
| `VECTORSEARCH` absent, reindexer published (pipeline on), option off | skipped: `vector search is not enabled` | skipped: `metadata generation for existing files not requested`        |
| `VECTORSEARCH` absent, reindexer published (pipeline on), option on  | skipped: `vector search is not enabled` | runs                                                                   |
| `VECTORSEARCH` absent, no reindexer published (pipeline off)         | skipped: `vector search is not enabled` | skipped: `the SYSTEM GenAI metadata pipeline is not enabled`           |
| `VECTORSEARCH` present and no reindexer, or the state unreadable     | fails (exit `1`)                        | fails (exit `1`)                                                       |

Each skip logs one INFO line and appears in the closing `MIGRATION SUMMARY` (for example
`metadataBackfill: skipped: metadata generation for existing files not requested`). Turning the pipeline on
later with vector search off is the same step: deploy, then run
`--steps metadataBackfill --generate-metadata-for-existing-files`.

### Step 4 — System-pipeline retirement report (`systemPipelineRetirement`)

Read-only. Prints three listings:

1. **Retired built-in definitions** — for each retired id, whether the `GLOBAL` pipeline and workflow rows
   are absent, archived (expected after the deploy), or present and **not** archived (the deploy-time
   archive did not run; the report prints the `vamscli pipeline delete` / `vamscli workflow delete` command
   that archives it).
2. **In-flight executions of retired workflows** — rows of `WorkflowExecutionsStorageTableV2` under
   `GLOBAL:<retired workflow id>` whose `executionStatus` is not terminal (`SUCCEEDED`, `FAILED`, `ABORTED`,
   `TIMED_OUT`, or `SKIPPED`, the record of a trigger launch that never ran). Their inner state machines were deleted with the retired nested stacks, so no result will
   arrive; the workflow records each one `FAILED` when its task times out (18,000 s for GenAI labeling,
   900 s for CAD/Mesh extraction). Abort them with `vamscli execution abort <executionId>` or wait.
3. **User workflows referencing a retired pipeline** — every `WorkflowStorageTableV2` row (other than the
   retired workflows themselves) whose `specifiedPipelines` name `GLOBAL:genai-metadata-3d-labeling-obj-glb-fbx-ply-stl-usd`
   or `GLOBAL:metadata-extraction-cad-mesh`. They fail at execute because the pipeline is archived; edit
   each one to replace the step with `GLOBAL:system-genai-metadata` (template
   `system-genai-metadata-default`) or remove the step. Archived rows are listed too (an unarchive would
   revive the problem).

`limit` caps the executions listed per retired workflow and the workflow rows scanned. Dry run or not
changes nothing about this step, and it needs no `--execute`. The step exits 0 whenever its reads succeed;
findings are printed under an `ACTION REQUIRED` line.

### Step 5 — Asset location index backfill (`assetLocationIndex`, required)

v2.7 adds `AssetLocationGSI` to the asset table: the bucket name and stored location of every asset
(`locationBucket`, `locationKey`), so VAMS can find the asset that owns an S3 key by its location rather
than by the first folder of the key. The deploy creates the index empty, and new assets are written with
the two attributes. Assets that existed before the deploy have neither until this step writes them. Nothing
in v2.7 reads the index for a decision until the step has written its **completion marker**, so until then
VAMS behaves exactly as v2.6 did; later releases that resolve keys through the index fall back to the
v2.6 logic on a deployment without the marker.

A **new deployment needs no backfill.** When the stack is created and its asset table is new (created
within an hour of the deploy step) and holds no row, the deploy writes the same completion marker, with
`writtenBy` set to `deploy` and every count at 0. Running this step there anyway is harmless. An upgrade
never gets a marker from the deploy, because its asset table predates it: run this step. The deploy never
overwrites a marker that already exists.

Run it after `assetLocationFolderKeys` (Step 0): the index stores each asset's `assetLocation.Key`, and that
step appends the `/` to folder keys written without it. Under `--steps all` this step runs last, and in a real
run it is skipped (`assetLocationIndex: skipped: assetLocationFolderKeys failed in this run`, exit `1`) when
`assetLocationFolderKeys` failed. A key `assetLocationFolderKeys` fixes on a row this step already indexed has
its `locationKey` updated in the same pass, so the index stays in step either way.

The step:

1. scans the asset table (live and archived rows) and, for each row, reads its bucket registration
   (`S3AssetBucketsStorageTable`, one `Query` per registration);
2. writes `locationBucket` (the registration's bucket name) and `locationKey` (`assetLocation.Key`
   without a leading `/`) with one `UpdateItem`, conditional on the row still existing with the same
   `assetLocation.Key`. A row that already carries the right values is not written, so a second run makes
   no write. Writes are paced to `asset_location_writes_per_second` (default 25) and retried on
   throttling. 100,000 assets cost about 200,000 write units (the row and its index entry);
3. checkpoints after every scanned page to `asset_location_checkpoint_file`. An interrupted run resumes
   from the checkpoint; a checkpoint written for another table is refused;
4. scans the table again **strongly consistent** and repairs any row that changed during the run (a row
   archived, unarchived or restored from a read taken before the backfill reached it), up to three
   passes, stopping at the first pass that writes nothing;
5. writes the report to `asset_location_report_file` and then, last, the completion marker: the SSM
   String parameter `<resource_names_ssm_param_prefix>/dataMigrations/assetLocationIndex`, value
   `{"version": 1, "status": "complete", "assetTable": "<asset table name>", ...}`. The backend accepts a
   marker only when it names its own asset table.

A dry run (the default) scans once, writes nothing (no row, no checkpoint, no marker) and writes the report
with the counts a real run would write. `--limit N` stops after N rows and never writes the marker.

The report lists:

| Section                            | Meaning                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `notIndexed.registrationMissing`   | the row's `bucketId` names no bucket registration (the bucket was removed from the configuration)                                                                                    |
| `notIndexed.noLocation`            | the row has no `assetLocation.Key`                                                                                                                                                   |
| `notIndexed.noBucketId`            | the row has no `bucketId`                                                                                                                                                            |
| `notIndexed.bucketRoot`            | the location is the bucket root (`/`)                                                                                                                                                |
| `notIndexed.registrationRoot`      | the location is the bucket registration's own prefix, which create refuses since v2.6.1                                                                                              |
| `review.sharedLocation`            | one location held by two or more assets; `ambiguous: true` when two of them are live (no file there can be attributed later)                                                         |
| `review.nestedLocation`            | an asset whose location another asset's location holds: inside its folder, or in a single-file asset's companion folder `{key}/` or among its own previews `{key}.previewFile.{ext}` |
| `review.singleObjectLocation`      | a location that names one object (no trailing `/`), from a `bucketExistingKey` that named a file                                                                                     |
| `review.outsideRegistrationPrefix` | a location outside its registration's prefix                                                                                                                                         |

Rows under `notIndexed` stay out of the index; rows under `review` are indexed. Resolve a shared or nested
pair by archiving or permanently deleting one of the assets, then run the step again (it writes only what
changed). The step makes no S3 call and changes no object.

The asset table streams every change to the search, compliance, Garnet and Physna consumers, so each row
the step writes is one more asset-table change for them: the asset search document is rewritten with the
same content, Garnet and Physna re-send the asset's metadata, and the compliance trigger evaluates an
asset of a bound database whose last evaluation does not cover the change. A row the step skips raises
nothing. Lower `asset_location_writes_per_second` on a deployment with many bound assets or add-ons.

A **new** v2.7 deployment has no rows without the attributes; run the step once after the first deploy to
write the marker.

The marker is not part of the CloudFormation stack. Removing VAMS leaves it; delete it with
`aws ssm delete-parameter --name <prefix>/dataMigrations/assetLocationIndex`. A deployment created again
under the same names ignores it (it names the old table) until the step runs again.

## Prerequisites

### Required AWS Resources

1. **v2.7 CDK stack deployed.** The deploy archives the retired built-ins (step 1 relies on it), creates
   `VectorEmbeddingsStorageTable` and — when `app.vectorSearch.enabled` — its vector index, registers the
   system pipeline and its trigger, and publishes the deployment's resource names to SSM Parameter Store
   (base prefix exposed as the CloudFormation output `ResourceNamesSSMParamPrefixOutput`).
2. **For the `vectorBackfill` step to embed anything:** `app.vectorSearch.enabled: true` in the deployed
   configuration, so the `VECTORSEARCH` feature switch is set and the `vectorReindexer` name is published
   under `<prefix>/lambdaFunctions/vectorReindexer`. With vector search off the step is skipped.
3. **Download as Zip and large workflow outputs need no step here.** The v2.7 deploy creates, on every
   deployment, the `ZipDownloadRequestsStorageTable` table and the two `vams.preparedDownloads/` lifecycle
   rules on the auxiliary bucket (archives expire after 7 days; an incomplete upload is aborted after a
   day), and for workflow outputs over 1 GiB and API uploads over 5 GiB the `LargeObjectCopyJobsStorageTable`
   table and the copy engine's state machine. With `app.pipelines.useZipDownloads.enabled` (which requires
   the VPC) it also registers the Zip Archive system pipeline and workflow `GLOBAL/utility-zip-archive` and,
   with `app.useGlobalVpc.addVpcEndpoints`, the AWS Batch, Amazon ECR API and Amazon ECR Docker interface
   endpoints its jobs use (one of each per VPC, shared with the other AWS Fargate pipelines). No step reads
   or writes any of them: `orphanedTriggers` reads `fileUpload` trigger rows only, and the Zip Archive
   workflow has none (triggers cannot be added to a system workflow); `systemPipelineRetirement` lists the
   runs of the two retired workflows only, so Download as Zip runs (workflow `GLOBAL/utility-zip-archive`,
   trigger value `System-ZipDownload`) are never counted; `vectorBackfill` and `metadataBackfill` walk the
   asset buckets, never the auxiliary bucket that holds `vams.preparedDownloads/`.
4. **Media previews need no step here.** With `app.pipelines.useMediaPreviews.enabled` (which requires the
   VPC) the v2.7 deploy registers the Media Preview Thumbnail system pipeline and workflow
   `GLOBAL/preview-media-thumbnail` (`SYSTEM - Preview`) on the 3D Preview Thumbnail container. No step
   rewrites them: `orphanedTriggers` keeps the workflow's `fileUpload` trigger while the workflow is live
   (and the deploy itself deletes the trigger when it archives the records), `systemPipelineRetirement`
   lists the runs of the two retired workflows only, and `vectorBackfill` and `metadataBackfill` never
   enqueue the `.previewFile.` objects the pipeline writes: the reindexer keeps only the files the SYSTEM
   GenAI metadata workflow's input filters admit, and those exclude `*.previewFile.*`.

### Upgrading from v2.5

A v2.5 deployment that deploys v2.7 directly runs both migrations after the deploy, the
[v2.5 to v2.6 migration](../../v2.5_to_v2.6/upgrade/v2.5_to_v2.6_migration_README.md) first and this one

`vams.preparedDownloads/` prefix, so a Download as Zip archive created after the deploy is never moved.

## Running the migration

Every run is a dry run until you pass `--execute` **and** set `dry_run` to `false` in your copy of the
config. Dry-run first, read the counts, then flip `dry_run` and run for real:

**Linux / macOS**

```bash
chmod +x run_migration.sh
./run_migration.sh my_migration_config.json
./run_migration.sh my_migration_config.json --execute
```

**Windows**

```powershell
.\run_migration.ps1 -ConfigFile my_migration_config.json
.\run_migration.ps1 -ConfigFile my_migration_config.json -Execute
```

**Directly**

```bash
python v2.6_to_v2.7_migration.py --config my_migration_config.json
python v2.6_to_v2.7_migration.py --config my_migration_config.json --execute
python v2.6_to_v2.7_migration.py --config my_migration_config.json --execute --confirm-account <account-id>
python v2.6_to_v2.7_migration.py --config my_migration_config.json --execute --steps orphanedTriggers
python v2.6_to_v2.7_migration.py --config my_migration_config.json --execute --steps vectorBackfill --clear-vectors
python v2.6_to_v2.7_migration.py --config my_migration_config.json --steps systemPipelineRetirement
python v2.6_to_v2.7_migration.py --config my_migration_config.json --execute --steps assetLocationIndex
```

Flags: `--steps {assetLocationFolderKeys,orphanedTriggers,vectorBackfill,metadataBackfill,systemPipelineRetirement,assetLocationIndex,all}`
(default `all`), `--execute`, `--resume`, `--limit N`, `--clear-vectors`, `--async`, `--profile`, `--region`,
`--log-level {DEBUG,INFO,WARNING,ERROR}`, `--confirm-account <12-digit id>`. The wrappers write a
timestamped log to `logs/` and exit with the migration's own status. `--execute` given while the config
still says `"dry_run": true` is logged as a warning and the run stays a dry run.

A dry run reports zero rows when there is nothing to do, so a zero-row result on its own is not evidence
that the step is configured correctly; read the counts against what the deployment actually holds. The
v2.7 deploy archives the retired built-ins' pipeline and workflow rows, deletes their `fileUpload` trigger
rows and keeps their past executions, so after it `orphanedTriggers` usually finds 0 rows to delete. A row it
does name belongs to a workflow archived before the upgrade, a missing workflow, or a retired built-in whose
deploy-time trigger delete did not complete.

### Confirming the target

The script prints the resolved account, Region, caller ARN, SSM prefix, dry-run flag, and what the run
will change, delete or bill before touching anything. A real run of `assetLocationFolderKeys` (changes
asset rows), `orphanedTriggers` (deletes rows), `assetLocationIndex` (writes every asset row) or
`vectorBackfill` (launches one Amazon Bedrock-billed execution per file; with `--clear-vectors` it also deletes
every stored vector) or `assetLocationIndex` (writes every asset row) then requires the resolved account id to be confirmed, one of two ways:

-   interactively — the script asks you to type the account id, and refuses anything else;
-   `--confirm-account <12-digit id>` — the resolved account must equal it (use this for automation, where
    stdin is not a terminal and the prompt cannot be answered).

There is no flag that skips the check. When the caller identity cannot be resolved
(`sts:GetCallerIdentity` denied) the account cannot be confirmed and the real run is refused; a
non-interactive real run without `--confirm-account` is refused too. `--confirm-account` is checked
whenever it is given, dry run included, so a mismatch surfaces on the first (dry) run. The read-only
`systemPipelineRetirement` step and every dry run pass the echo without a prompt.

## Rollback

| Step                       | Writes to                                                                                                                                                      | Reversible by redeploying v2.6?                                                                         | Safe to repeat?                                                                                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assetLocationFolderKeys`  | Appends `/` to `assetLocation.Key` on asset rows whose key names a folder; moves the copy's records from `/{name}` to `/{name}/{name}`                         | Not needed for the `/`; the moved records are listed in the report, one line each, to move back by hand | Yes: part (a) finds nothing to append and part (b) skips every asset row it marked done, but a record written at `/{name}` before the first real run is moved (see part (b)) |
| `orphanedTriggers`         | **Deletes rows** from the workflow triggers table                                                                                                              | No                                                                                                      | Yes — a second run finds nothing                                                                                                                                             |
| `vectorBackfill`           | Nothing directly; the reindexer it invokes deletes every vector item when `--clear-vectors` is passed, and launches executions that write vectors and metadata | No                                                                                                      | Yes — items are overwritten in place                                                                                                                                         |
| `systemPipelineRetirement` | Nothing                                                                                                                                                        | n/a                                                                                                     | Yes                                                                                                                                                                          |
| `assetLocationIndex`       | Adds `locationBucket` and `locationKey` to asset rows; writes the marker parameter                                                                             | Not needed (v2.6 ignores both)                                                                          | Yes — a second run writes no row                                                                                                                                             |

What each step does to your data:

-   `orphanedTriggers` deletes only rows whose workflow is archived, missing, or retired, so nothing that
    could fire is lost. Redeploying v2.6 does not restore them: the retired built-ins' triggers are
    re-registered only if their (rejected) configuration blocks are restored and a v2.6 stack redeploys, and
    a user workflow's trigger deleted because the workflow was archived stays deleted (re-create it with
    `vamscli workflow trigger set` after unarchiving the workflow, if it is ever needed).
-   `vectorBackfill` with `--clear-vectors` empties the vector index; natural-language search returns nothing
    until the launched executions complete. The executions themselves (rows, run-bucket objects, written
    metadata and attributes) remain in history like any other run and are removed only through the
    executions API (`vamscli execution permanent-delete`, or per group with the abort route's `--group-id`).
-   Redeploying v2.6 after a v2.7 deploy is a separate matter (the retired nested stacks and the vector index
    would be re-created / deleted by CloudFormation); this migration neither helps nor hinders it.

### Before you run

-   **Back up the workflow triggers table** (`aws dynamodb export-table-to-point-in-time`, or enable
    point-in-time recovery) — `orphanedTriggers` deletes rows and there is no automated rollback. See
    [Update the solution](https://awslabs.github.io/visual-asset-management-system/deployment/update-the-solution).
-   **Back up the asset table and the file metadata, file attribute, asset file version, metadata version
    and file version history tables** before a real `assetLocationFolderKeys` run; its report lists every key and record it
    changed, so a change can also be undone row by row.
-   **Confirm the target account and Region** from the echo at startup before answering the prompt.
-   **Abort in-flight executions of the retired workflows before the v2.7 deploy** where you can; the
    `systemPipelineRetirement` step lists any that remain afterwards.

## Troubleshooting

**Symptom:** `Vector search is not enabled on this deployment, so there is nothing to re-index; vectorBackfill skipped.`

**Cause:** the deployment has no `VECTORSEARCH` feature switch: `app.vectorSearch.enabled` resolved to
`false` at the last deploy. This is not an error; the step exits `0`.

**Solution:** None needed. To use natural-language search, deploy with `app.vectorSearch.enabled: true`,
then run `--steps vectorBackfill`.

**Symptom:** `Vector search is enabled on this deployment (the VECTORSEARCH feature switch is set), but no vectorReindexer function is published`

**Cause:** the feature switch and the published resource names disagree, usually after an interrupted
deploy.

**Solution:** Redeploy, or set `vector_reindexer_function_name` in the config, then re-run the step.

**Symptom:** `Cannot tell whether vector search is enabled on this deployment: ...`

**Cause:** the state could not be read: no `resource_names_ssm_param_prefix`, a prefix that publishes no
app feature table (usually a wrong prefix), or SSM or the app feature table denied the read.

**Solution:** Fix what the message names (the prefix, `ssm:GetParametersByPath`, `dynamodb:GetItem` and,
with a customer-managed key, `kms:Decrypt` on the app feature table), then re-run the step.

**Symptom:** `AccessDeniedException` on `dynamodb:Query` with an `/index/` ARN in the message

**Solution:** The `TriggersByBaseTypeGSI` and `WorkflowExecutionsByWorkflowGSI` reads need
`dynamodb:Query` on `arn:*:dynamodb:*:*:table/*/index/*`, not only on the table ARN.

**Symptom:** the `LAMBDA INVOCATION TIMED OUT` warning during `vectorBackfill`

**Cause:** the synchronous invoke outlived the client's read timeout; the reindexer keeps running and
re-invokes itself to continue.

**Solution:** Nothing to repair. Watch the reindexer's CloudWatch log group and the executions list. Use
`--async` on very large deployments.

**Symptom:** `Refusing to run: --confirm-account ... does not match the resolved account`

**Solution:** The ambient credentials or `aws_profile` point at a different account than intended. Fix
the profile (or pass `--profile`) — the SSM prefix carries no account, so two deployments with the same
`configName`/`baseStackName` resolve identical parameter paths in different accounts.

**Symptom:** `Completion marker NOT written; run the step again` after `assetLocationIndex`

**Cause:** a write failed, or rows kept changing through three verification passes (heavy archive and
unarchive traffic during the run).

**Solution:** Run `--steps assetLocationIndex --execute` again; it resumes and writes only what is missing.

**Symptom:** `Checkpoint ... belongs to table ...`

**Solution:** The checkpoint file was written for another deployment. Delete it, or point
`asset_location_checkpoint_file` at a path of its own.

**Symptom:** `--execute was given but the config sets dry_run: true, so this remains a DRY RUN`

**Solution:** Set `"dry_run": false` in your copy of the config. The shipped template pins `true` so a
freshly copied config can never write; `--execute` alone does not override it.

**Symptom:** `Refusing to run: this run would ... and stdin is not a terminal` or `... the caller identity could not be resolved`

**Solution:** A real run that deletes rows or launches billed executions must confirm the account id. In
automation pass `--confirm-account <12-digit id>`; the resolved account must equal it. When the identity
cannot be resolved, grant `sts:GetCallerIdentity` to the principal — there is no flag that skips the check.

## Verification

The migration directories carry no test files. Verify a change to a transform against a deployment:
run it without `--execute` first (a dry run), then for real, and confirm the outcome through the API (`vamscli
workflow trigger list`, `vamscli execution list --trigger-type System-Reindex`) and the tables the
step reports on. Unit-style checks written while developing a transform — a `moto` seed for each row
shape and a Lambda fake, for example — are run locally and are not committed here.

The wrapper's exit-status propagation, this README's IAM policy, and the step names documented in the
upgrade guide are pinned by `infra/test/platform/migrationTooling.test.ts`
(`cd infra && npx jest test/platform/migrationTooling.test.ts`).
