# Controls mapping

This page maps the controls `vra` implements to three widely used references: the AWS Well-Architected
Framework, NIST SP 800-53 Revision 5, and the SLSA build track. Use it to explain the design to a
reviewer and to find the evidence each control produces.

:::warning[Supporting evidence, not compliance]
Using `vra` does not make a system compliant with any framework, and this page is not an assessment.
Each control below covers only the release and change path of a VAMS deployment. Whether a control is
satisfied for your system depends on your whole environment, your procedures and an assessor's
judgment. Where a row says "supports", `vra` provides a mechanism and evidence; you still own the
policy, the procedures and the rest of the control.
:::

## NIST SP 800-53 Revision 5

Control names are from [NIST SP 800-53 Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final).
The "Scope" column states what part of the control `vra` can support; the rest is the system owner's
responsibility.

| Control | Name                               | How `vra` supports it                                                                                                                                                               | Scope and limits                                                                                                                                                                                                                                        |
| ------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CM-2    | Baseline Configuration             | Each environment's configuration is a reviewed, versioned ledger entry; each deployed build is recorded                                                                             | Covers VAMS deployment configuration only, not the account baseline, OS images or network devices                                                                                                                                                       |
| CM-3    | Configuration Change Control       | Changes flow through merge requests, a recorded `cdk diff`, tests and an approval record; history retains the decision                                                              | You define the change board, criteria and retention; `vra` records and enforces                                                                                                                                                                         |
| CM-5    | Access Restrictions for Change     | Only the deploy role changes stacks; approval-gated environments refuse unapproved changes                                                                                          | Effective only if humans cannot change stacks outside `vra`; enforce with IAM and SCPs                                                                                                                                                                  |
| AC-5    | Separation of Duties               | Approver must differ from initiator and be on the environment's list; initiator from the CI platform / STS; approvals from the CI platform's own approval feature, bound to the run | Local hand-written approval records still rely on the ledger's git review; the CI lanes depend on the platform's approval controls (CodePipeline approval permissions, GitHub required reviewers with prevent-self-review, GitLab deployment approvals) |
| AU-2    | Event Logging                      | Every run, step, approval, deploy, rollback, restore and data copy is logged                                                                                                        | Application-level logs; combine with AWS CloudTrail and your log retention for the full control                                                                                                                                                         |
| CP-9    | System Backup                      | Checkpoint before every change; PITR verified                                                                                                                                       | Backup schedule, retention, off-site copy and protection come from AWS Backup and your plan; see _Productionizing VAMS_                                                                                                                                 |
| CP-10   | System Recovery and Reconstitution | Rollback, checkpoint restore, search reindex, documented forward-only cases                                                                                                         | Recovery objectives, drills and alternate sites are the owner's plan                                                                                                                                                                                    |

Related controls you will likely need to address outside `vra` include SA-10 (developer configuration
management), SI-2 (flaw remediation, for which a current upstream is useful evidence) and SR-4
(provenance).

## SLSA build track

[SLSA v1.0](https://slsa.dev/spec/v1.0/levels) defines build levels L1 (provenance exists), L2 (signed
provenance from a hosted build platform) and L3 (hardened build platform).

| Level    | Status with `vra`                                                                                                                                                                                                                                                                                                                                                             |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build L1 | `vra build` follows a consistent process and records the source commit, tag, toolchain versions and per-environment hashes in `manifest.json`. That information is the substance of L1 provenance. To claim L1, publish it to the people who deploy, in a provenance format your organization accepts (for example a SLSA provenance attestation generated from the manifest) |
| Build L2 | Not met by an operator workstation. Running builds in a CI template puts them on a hosted platform; you would also need provenance that is signed by the build platform and verified before deploy                                                                                                                                                                            |
| Build L3 | Not addressed. Requires a hardened build platform with isolation between runs and signing keys unreachable from build steps                                                                                                                                                                                                                                                   |

`vra deploy` verifies the bundle hashes in `manifest.json` before deploying. Without `build.signing` this
is an integrity check: it catches accidental change, not a writer who also recomputes the hashes. With
`build.signing.kmsKeyArn` the manifest digest is signed with an asymmetric AWS KMS key at build and the
signature is verified before every deploy, which makes it a tamper check for anyone without `kms:Sign` on
that key. That is the substance of signed provenance for L2, from whichever platform holds the key; a
SLSA-format attestation is still yours to publish.

## Gaps to plan for

-   **Signed provenance.** Optional by default; turn on `build.signing` with `tags: true` for production (one
    asymmetric AWS KMS key per customer that only the build tier may sign with). If you need a SLSA attestation
    format, generate it from the signed manifest. Upstream VAMS release tags are not verified (upstream
    publishes no signing key).
-   **Write freeze.** When the deployed VAMS does not publish a maintenance-mode switch, restores and data copies
    rely on the operator's recorded confirmation that writes are stopped. Background writers (pipelines, S3 event processing) are not
    stopped by maintenance mode either; list and, if needed, abort running workflow executions.
-   **Out-of-band changes.** `vra` runs CloudFormation drift detection before deploys to gated environments
    and stops on drift. It does not watch continuously; schedule drift detection (see _Productionizing VAMS_)
    and restrict console write access in approval-gated accounts.
-   **Identity assurance for approvals.** Outside CI, an approval record is a file reviewed through your
    git host. Require signed commits and protected branches on the home repository, set
    `approvalSigningKeyArn`, or use pipeline approval actions.
-   **Retention.** Keep run directories, history and IT requests for as long as your records policy
    requires, for example in the home repository's history or the Amazon S3 backend with versioning and
    lifecycle rules.
