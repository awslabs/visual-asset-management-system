# SYSTEM - GenAI Metadata Generation Pipeline

Files often arrive in a deployment with little more than a file name. The SYSTEM GenAI metadata pipeline gives each of them a description. It reads what is stored in the file, looks at the file the way a person would (renders of a 3D model or CAD part, a video's keyframes, a document's pages and text), and writes back technical attributes, filterable metadata, a location when the file has one, and a generated title, description, keywords, and classification. That metadata makes the file easier to find, filter, and understand in keyword search, in the metadata panels, and on the map, and it is the source of the embeddings behind [natural-language search](../concepts/vector-search.md).

The SYSTEM GenAI metadata pipeline runs on every uploaded file, of any type, and writes what it learns back onto the file. The extraction layer records the attributes stored on the file itself — EXIF and XMP tags for images, container and stream tags for video and audio (a recording time, a camera location), document properties for PDF and Office files, archive contents for zip and tar containers, geometry and scene facts for 3D files, and the S3 object's own facts for everything else — as `sys_*` attributes, promotes a curated subset to typed `ext_*` metadata, and writes a GeoJSON `location` when the file carries a position. The GenAI layer, on by default (`useGenAiAnalysis`), then asks an Amazon Bedrock model to describe and classify the file from renders, keyframes, extracted text, and the existing metadata on the file, its asset, and its database; with that layer off the pipeline is attributes-only and makes no Amazon Bedrock Converse call. When [vector search](../concepts/vector-search.md) is enabled, it also produces one embedding per file version — plus one per video window or content chunk — and publishes them for the vector indexer. Every Amazon Bedrock model it calls is named in the `bedrockModels` block of its configuration. It is a [system pipeline](system-pipelines.md): it ships with the deployment, is read-only through the API except for its pause switches and template content, and runs automatically on file upload. With the GenAI layer on, the same deployment registers a second system workflow, the [asset summary](#asset-summary-workflow), which describes a whole asset or a folder of it from the descriptions this pipeline wrote on its files.

## How it works

![SYSTEM GenAI metadata pipeline architecture](/img/pipeline_usecase_systemGenAiMetadata.png)

```mermaid
flowchart TD
    VE[vamsExecute Lambda] --> OP[openPipeline Lambda]
    OP --> CP[ConstructPipelineTask<br/>classify, size gate, choose branch]
    CP --> RB{RenderBranchChoice}
    RB -->|BLENDER| BL[BlenderRenderTask<br/>Blender 5.2 image]
    RB -->|RENDER3D| R3[Render3dTask<br/>PyVista / CadQuery / laspy image]
    RB -->|MEDIA| ME[MediaExtractTask<br/>Pillow / FFmpeg / pypdfium2 image]
    RB -->|FARGATE| FG[FargateRenderJob<br/>AWS Batch, useFargateRenderer only]
    RB -->|NONE| NR[NoRenderPass]
    BL --> GM[GenerateMetadataTask<br/>attributes, then Amazon Bedrock analysis]
    BL -->|referenced files over the Lambda budget<br/>useFargateRenderer only| FG
    R3 --> GM
    ME --> GM
    FG --> GM
    NR --> GM
    BL -. render fault .-> RD[RenderDegradePass]
    R3 -. render fault .-> RD
    ME -. render fault .-> RD
    FG -. render fault .-> RD
    RD --> GM
    GM --> VC{VectorSearchChoice}
    VC -->|vector search on and analysis succeeded| GE[GenerateEmbeddingTask<br/>Amazon Bedrock embedding, publish event]
    VC -->|otherwise| PE[PipelineEndTask]
    GE --> VS{VideoSegmentChoice}
    VS -->|window plan and embedding succeeded| VM[VideoSegmentMap<br/>one EXPRESS child per window]
    VS -->|otherwise| PE
    VM --> PE
    PE --> ES{EndStatesChoice}
```

1. The workflow invokes `vamsExecute`, which resolves the input file, output prefixes, asset identity, and file version from the execution manifest and hands them to `openPipeline`.
2. `openPipeline` checks the extension against the allow list, starts the sub-state-machine, and registers the sub-execution and its log group with VAMS so the execution detail page can show and abort it.
3. `ConstructPipelineTask` classifies the file into a `fileClass`, applies the size gates, and chooses a render branch. For a file no library can read (`NONE`) it writes the analysis manifest itself.
4. The branch task downloads the file to the function's `/tmp`, with the files a 3D scene references (see [Referenced files](#referenced-files)), extracts attributes, and renders stills or keyframes. When the Fargate renderer is deployed and a scene's referenced files exceed what the Blender function can hold, `DependencyOverflowChoice` sends the run to `FargateRenderJob` before anything is rendered. A render fault routes through `RenderDegradePass` to `GenerateMetadataTask`, which records the render as skipped (`renderSkipped: "error"`) and continues attributes-only — a render failure never fails the execution.
5. `GenerateMetadataTask` writes the file's attributes first — the `sys_*` groups, the `ext_*` facts promoted from them, and the run's `genai_*` provenance — promotes the GeoJSON `location`, then calls the analysis model with the renders, text excerpt, attributes, asset context, the existing metadata when `SEED_WITH_EXISTING_METADATA` is `true`, and the classification vocabulary, and writes the result to the file, the asset, or both (see [Write targets](#write-targets)).
6. When vector search is enabled and the analysis succeeded, `GenerateEmbeddingTask` composes the embedding text, calls the embeddings model, writes the embedding document, and publishes `vector.embedding.ready` — and, for document, text, and data files with `CONTENT_CHUNKING` on, one more document and event per [content chunk](#content-chunks).
7. When the media branch produced a window plan (a video at least two windows long, with `VIDEO_SEGMENT_SECONDS` of `2` or more) and the embedding succeeded, `VideoSegmentMap` runs one child execution per [video window](#video-windows) — `SegmentAnalyzeTask`, the media image's second function — eight at a time, and writes its own result manifest under the execution's auxiliary prefix.
8. `PipelineEndTask` reports success or failure to the workflow through the task token. The workflow's process-output step then applies the metadata and attribute files to the asset.

The file-upload trigger fires on a **new** version of a file: an upload, a direct Amazon S3 write, a copy, move, or rename into the asset, a revert to an earlier version, and — when the workflow allows trigger chaining — another workflow's output. It does not fire when a file or an asset is **unarchived**: the restore copies the file's newest content version forward under a new version id, the pipeline has already analyzed that content, and its metadata, attributes, and vectors stay as they were (the vector indexer marks them live again without re-embedding; see [Vector search](../concepts/vector-search.md#only-the-latest-live-version-is-searchable)). With vector search on, a restored file that has no vector yet gets its embedding queued: one launch of this workflow through the reindexer's paced launch queue. To analyze a restored file again, re-execute the workflow on it or run the vector reindexer.

### Files already in the deployment

Turning the pipeline on does not analyze the files a deployment already holds. The file-upload trigger fires only for a version written after the trigger is armed, so a file uploaded before then has no `sys_*` attributes, `genai_*` metadata or vector until a run reaches it. Three ways start those runs, with vector search on or off:

-   **Run the workflow on a file.** The system workflow runs like any other workflow: in an asset's **File Manager**, select a file and choose **Execute Workflow** from the **Automation** menu, then pick **SYSTEM - GenAI Metadata Generation**; or launch it with `vamscli workflow execute --workflow-database-id GLOBAL -w system-genai-metadata --input-file <databaseId>:<assetId>:<fileKey>`. Each execution analyzes one file, so a whole asset or a folder is not accepted as the selection. This works with vector search on or off.
-   **Run the vector reindexer over every file.** The reindexer exists whenever the pipeline is on and registers its workflow, with vector search on or off. Its `enqueue` operation launches the full workflow for the latest live version of every file the workflow's input filters admit; at most `app.vectorSearch.indexingConcurrency` of those runs are running at once, and the others wait in the launch queue until one ends. A waiting file checks for a free slot again after a delay that grows from 30 seconds to 15 minutes, so the last files of a run can start up to 15 minutes after a slot frees. Uploads and manual runs are not counted. With vector search off the runs write the attributes and the `genai_*` metadata and skip the embedding step. A file with no attributes or metadata yet gets them, and a file that has them is analyzed again. Each file costs one analysis run (plus its embedding with vector search on). See [Reindexing](../concepts/vector-search.md#reindexing) for its options.
-   **Run it through the data migration.** The [v2.6 to v2.7 migration](../deployment/update-the-solution.md#v26-to-v27) wraps the same call: its `vectorBackfill` step with vector search on, and, with vector search off, its opt-in `metadataBackfill` step, which runs only when `generate_metadata_for_existing_files` is `true` in its config or `--generate-metadata-for-existing-files` is passed. The script runs on any 2.7 deployment, so turning the pipeline on later with vector search off is `--steps metadataBackfill --generate-metadata-for-existing-files` after the deploy.

## Supported files and how each is analyzed

The pipeline accepts every file: the pipeline, workflow, and trigger filters are the one `*` wildcard with the `*.previewFile.*` thumbnails excluded, and the openPipeline gate admits any extension or none. An extension with dedicated handling — every extension a viewer in the deployment's viewer catalog supports (see [File Viewers](../concepts/viewers.md)) plus the formats marked ‡ below — takes the class and branch the table gives it. The robotics logs the Robotics Data Viewer plays (`.mcap .bag .db3 .ulg .ulog`) have no extractor and are `other`, as is every file the table does not name; both take the generic probe at the bottom of the table. The `fileClass` decides the branch, the attributes written, and what the analysis model receives.

`.ply` is disambiguated by loading it: faces make it a mesh, `f_dc_0` properties make it a splat, anything else is a point cloud. `sys_file` is written for every file: `name`, `ext`, `sizeBytes`, `contentType`, `etag`, `versionId`, `lastModified`, the object's own user metadata as `s3Metadata` (`x-amz-meta-*` keys), the format its leading bytes identify as `detectedFormat` (`jpeg`, `mp4`, `zip`, `glb`, `utf8-text`, …), and `sha256` for files up to 512 MB. `contentType` is the type stored on the Amazon S3 object; VAMS stores every upload as `application/octet-stream`, so use `detectedFormat` and `ext` for the file's actual format. A file over `lambdaLimits.maxInputFileSizeMb` whose class is `other` keeps `sys_file` alone and never takes the Fargate branch.

‡ Formats no viewer renders, admitted through the classifier's `ADDITIONAL_EXTENSIONS` for their extracted content. The `.avi`, `.flv` and `.wmv` containers FFmpeg decodes but no browser plays take the video branch for their stream facts, tags and keyframes. A `.geojson` file is read by the same rule as a `.json`: a GeoJSON root is classified `data` and writes `sys_geo` and a [`location`](#location), a tileset root is `tiles3d`, any other JSON is `text`, and bytes that are not UTF-8 are `other`. The office formats are admitted for their text: `.docx` (paragraphs and table cells, in order) and `.pptx` (slide text and notes, one page per slide) are classified `document`, `.xlsx` (per sheet, the header row then tab-separated rows, one page per sheet) is classified `data`; spreadsheet row counts are taken up to 200,000 rows per sheet, so a larger sheet's `ext_row_count` is that floor. The GIS containers are admitted for their layer catalogue, read without GDAL or any Esri software: a `.gpkg` GeoPackage is an SQLite database, opened read-only, of which the extractor reads the `gpkg_contents` rows of the first 50 layers, the `gpkg_geometry_columns` and `gpkg_spatial_ref_sys` rows those layers name, and for each listed table a column listing and a row count bounded at 2,000,000 rows (`featureCountExact` is `false` above it); a layer that is a view is listed without a count, and an SQLite time budget (120 seconds per file, 15 seconds per layer count) ends any read that runs longer, so the cost is set by those bounds rather than by the file's size; a `.lyrx` layer file is a JSON document in Esri's CIM schema and records its layers, their data connections (reduced to the keys that locate the data: server, instance, database, version, branch, client and URL, with every URL stripped of user-info, query string and fragment), visible fields and renderers, and no data of its own, so it records no feature count or geometry types. Names taken from either file are cut to 200 characters, and `sys_geo` is kept under 300,000 characters by leaving out per-layer field lists, with a warning. Both are classified `data`. A footprint is written only when the layers are in EPSG:4326; another spatial reference keeps its extent as `nativeExtent` with its `crs` and writes no `location`. They receive attributes and generated metadata from the text alone and are never rendered. An input larger than 3,500 MiB is not downloaded by the MEDIA image at all, whatever its class: the `sys_file` attributes stand, the manifest carries a warning naming the size and the bound, and the GenAI layer describes the file from them.

:::note[Proprietary CAD formats]
Proprietary CAD formats that an add-on viewer opens are allow-listed so that every viewable file is covered, but no open library reads them. They receive `sys_file` attributes and metadata generated from the file name and the asset's own metadata.
:::

### Referenced files

A 3D scene is often several files: a USD stage that composes other layers, a glTF file with its buffers and textures, an OBJ file with its material library. When the template tag `RESOLVE_DEPENDENCIES` is `true` (the default), the render branch loads the files the input references before it renders, so the scene renders complete. It follows the references transitively, and each referenced file lands at its own path relative to the asset, so `../` references resolve as they do in the asset.

| Input               | References followed                                                                                                                                                                             |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.usd .usda .usdc`  | Sublayers, references, payloads, and asset-valued attribute paths authored in the layer, for every variant. A UDIM texture set is not fetched.                                                  |
| `.usdz`             | The package's references to files outside the package, which are fetched but not loaded into the scene (see below); a path to a member of the package is read from the package itself           |
| `.gltf`, `.glb`     | The `buffers` and `images` URIs, except `data:` URIs (a GLB's own binary chunk needs none)                                                                                                      |
| `.dae`              | Images (`<image><init_from>`) and the documents its `instance_*` elements place from other files. The document is read with an XML parser that refuses document type declarations and entities. |
| `.obj`, `.mtl`      | The OBJ file's `mtllib` material libraries, and the texture maps they name                                                                                                                      |
| `.fbx`              | The texture file names stored in the file (the first 512 MiB is scanned), each also tried as a file beside the FBX file                                                                         |
| `.lcc` (XGRIDS LCC) | The scene's data files beside it                                                                                                                                                                |

A reference is followed only when it is a relative path that, resolved against the referring file's folder, stays inside the input file's own asset. Absolute paths, any URI scheme (`https:`, `s3:`, `file:`, a Windows drive letter), a `..` that leaves the asset, control characters, and values over 1,024 characters are refused before any Amazon S3 request is made. Files of a linked asset are not followed, and nothing is fetched over HTTP. For an asset created on an existing bucket folder, the asset's root is the folder it was created on.

The walk runs in two phases. Discovery downloads the files that can name further files (USD layers and packages, glTF, OBJ, MTL, FBX, COLLADA; a GLB's JSON chunk is read with a ranged request) and sizes every other file, recording the S3 version each lookup returned. The fetch then downloads those files at those versions, so a file replaced during the run does not mix two versions into one scene. A file referenced twice is fetched once, and a reference cycle is reported and not followed again.

A reference that is missing, refused, or past a limit never fails the run: the scene renders from what was found, and the run records what was left out. A missing USD layer, glTF buffer, or COLLADA external document makes the scene partial. When a required file is missing and the input was uploaded less than five minutes ago, discovery waits 30 seconds once and looks again, because a multi-file upload lands file by file. For a USD scene the Blender branch also takes the list of missing files from Blender's OpenUSD dependency check of the composed stage, which covers asset paths that only composition reveals. A file the walk fetched is never listed as missing. When the composed stage still does not load it, the report lists it under `notComposed`, the run's warnings name it, and a USD layer among them makes the scene partial. That is always the case for a `.usdz` package's reference to a file outside the package: OpenUSD resolves every relative reference in a package's layers inside the package, so `../parts/bolt.usda` in `usdz/station.usdz` is looked up as a package member and the scene renders without it, although `parts/bolt.usda` was fetched. Put such files inside the package to have them rendered. The 3D render branches do not run this check.

| Limit                               | Value                                                                                                                                    |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Files fetched                       | 2,000                                                                                                                                    |
| Objects looked up, found or not     | 4,000                                                                                                                                    |
| Reference depth below the input     | 32                                                                                                                                       |
| References read from one file       | 100,000                                                                                                                                  |
| Referenced bytes                    | About 6 GiB on the Lambda branches (`BLENDER`, `RENDER3D`); 50 GiB on the Fargate render job                                             |
| Free disk kept beyond each download | 1 GiB                                                                                                                                    |
| Time                                | The remaining invocation time less 390 seconds on the Blender branch and less 300 seconds on the 3D render branches, at least 30 seconds |

A template configuration body can lower the file, byte, and depth limits with the optional keys `maxDependencyFiles`, `maxDependencyBytes`, and `maxDependencyDepth`. The lookup limit follows at twice the file limit, a value above a built-in limit is ignored, and a byte budget lowered below the Lambda budget also keeps the scene on the Lambda branch. Set them by editing the body as described in [Editing the classification vocabulary](#editing-the-classification-vocabulary).

When the Fargate renderer is deployed (`useFargateRenderer`) and the files a scene references are larger than the Lambda byte budget, the Blender branch stops before rendering and the state machine runs the scene on the Fargate render job instead. That job renders with the [3D Preview Thumbnail](3d-thumbnail.md) pipeline's container image rather than Blender, so its views look different from a Blender render. Without the Fargate renderer, the Lambda branch renders what fits, and the run records that the walk stopped at its byte limit.

The walk reports to three places. The analysis manifest (the `analysis.json` object under the execution's auxiliary prefix) carries the full report as `dependencyReport`: the files fetched with their versions, sizes and depth, the missing and refused references, the cycles, the limit that stopped the walk (`files`, `lookups`, `bytes`, `disk`, `depth`, `references`, or `deadline`), the byte totals, the reference graph, and whether the scene is partial. The file's `sys_dependencies` attribute holds a bounded copy (see [Attribute groups](#attribute-groups)). The prompt and the embedding text carry one line of counts, for example `dependencies: 36 referenced files loaded; 2 missing; 1 refused` (a file fetched but not composed is counted as `fetched but not composed` rather than loaded), and never a path.

With `RESOLVE_DEPENDENCIES` set to `false`, the input file is fetched alone. The [3D preview thumbnail](3d-thumbnail.md) pipeline follows the same references for the formats it reads, at the files' current versions.

### COLLADA files

COLLADA (`.dae`) files are rendered by the 3D render image with the same COLLADA reader the 3D preview thumbnail uses: it refuses document type declarations and external entities, and a file that places the same part many times is expanded only up to the triangle budget. Its attributes differ from those of the Blender-rendered mesh formats in three ways:

-   `sys_format.loader` is `expat`. `sys_format.declaredMetersPerUnit`, `declaredUnits`, and `declaredUnitsSource` record the unit the file's `<asset><unit>` element declares.
-   The numbers are the authored coordinates, so `sys_geometry.units` (and `ext_units`) is the file's own unit, and the dimensions follow the 3D render image's Y-up convention: `height` is the vertical extent. A 2 m × 1 m × 0.5 m box authored in centimetres is `200 x 50 x 100 cm` (width × height × depth).
-   No `sys_scene` group (object counts, material names) is written.

### Size gates and the Fargate renderer

`lambdaLimits.maxInputFileSizeMb` (default 2048) and `lambdaLimits.maxPointCloudPoints` (default 20,000,000, checked from the file header) bound what a Lambda render attempts. A file above either limit is processed attributes-only, with the skip recorded in the analysis manifest, in `genai_source_modalities`, and in `analysis-summary.json`. With `useFargateRenderer: true`, those files instead take the `FARGATE` branch, an AWS Batch job that runs the 3D Preview Thumbnail pipeline's container image with a four-hour attempt limit, which requires `app.useGlobalVpc.enabled` and adds the AWS Batch, Amazon ECR API, and Amazon ECR Docker interface endpoints. The same job renders a scene whose [referenced files](#referenced-files) exceed the Lambda byte budget. Every shipped configuration template leaves the sub-flag off.

An attempt of the render job whose task fails to start is retried, up to three attempts in all: AWS Batch reports `Timeout waiting for EphemeralStorage` or `Timeout waiting for network interface provisioning` as the status reason, or `CannotPullContainerError` as the container reason. A render that ran and exited with an error, or an attempt that reached its four-hour limit, ends the job on that attempt. A retried render appears as a second or third attempt on the AWS Batch job. The other AWS Fargate pipeline jobs (Potree viewer, 3D preview thumbnail, coordinate transform, GenAI CAD STEP agent, Video SOP/BOM Extraction) run one attempt. The job's container output goes to the pipeline's own `/aws/vendedlogs/Pipelines/SystemGenAiMetadataRender<hash>` log group (KMS-encrypted, one-year retention), which `openPipeline` registers as the `FargateRenderJob` stage's log source so the execution log view can read it, and the state machine can describe and terminate the job when an execution is stopped. See [Pipeline log groups](../architecture/aws-resources.md#pipeline-log-groups-per-enabled-pipeline).

## Outputs

The pipeline writes two layers per file to the execution's metadata output prefix, and the workflow's process-output step applies the files to the asset as `SYSTEM_USER`.

**File attributes** — `<relativePath>.attribute.json`: the complete technical record. One `sys_*` key per attribute group, each value a JSON string; the deterministic `ext_*` facts promoted from those groups; and, when the GenAI layer is on, the run's provenance — `genai_model`, `genai_generated_at`, `genai_source_modalities`, the model's `genai_complexity` grade, and, after embedding, `genai_content_chunk_count`; with key reuse, `genai_written` records the keys outside the `genai_` namespace that the run wrote, and `genai_targets` the key each field went to when that is not its `genai_*` key (see [Key reuse](#key-reuse)). File attributes are string-typed, so a promoted number, flag, or triple is carried as its rendered text (`"1200"`, `"true"`, `{"x": 1.0, ...}`). The attributes are written before the analysis model is called, so they land even when the model call fails; the complexity grade is added once the model has answered. With `useGenAiAnalysis` off, this file and the deterministic rows of the metadata file are the whole output: no `genai_*` analysis row or provenance is written (the embedding step's `genai_content_chunk_count` still lands when vector search is on), and `analysis-summary.json` records `analysisMode: attributes-only`.

**File metadata** — `<relativePath>.metadata.json` (`updateType: update`): a GeoJSON `location` when the file has none, the video window counts, and, when the [write target](#write-targets) includes the file, the descriptive `genai_*` block the analysis model produces (title, description, keywords, category, and the rest). Every `ext_*` and `genai_*` key is pipeline-owned and rewritten on each run. A key you author yourself is never overwritten: `replace_all` is never used, and the pipeline writes a key outside its own namespace only under the rules in [Key reuse](#key-reuse). A promoted key whose source disappears in a later file version (a re-export without textures, for example) keeps its previous value until the next run writes it. List-valued keys are written as `string` rather than `inline_controlled_list` because the web interface's inline controlled list field holds a single value. Every key, its type, and its source are catalogued in [Fields written](#fields-written).

**Asset metadata** — `asset.metadata.json` (`updateType: update`, so the asset's other keys are untouched) with the descriptive `genai_asset_*` keys and the provenance keys that say which file or folder they describe. It is written when `METADATA_WRITE_TARGET` is `asset` or `both` (see [Write targets](#write-targets)) and by the [asset summary](#asset-summary-workflow); the default write target, `file`, writes no asset metadata.

**Results** — written to the execution's results prefix and recorded on the execution as results rows: `analysis-summary.json` always (model ids; token usage; modalities; skips; vocabulary corrections; the number of promoted fields; `guardrailMasked` and `guardrailMaskedTypes`, whether the guardrail's PII filter masked entities and which types; an `existingMetadata` block with how many existing-metadata lines were kept, how many the budget dropped, and whether the analysis prompt was seeded with them; the `writeTarget` and the `assetMetadataFile` it wrote; the `keyReuse` block and the `keyConflicts` list described in [Key reuse](#key-reuse); `replyFormat`, `tool` or `text`; and `imagesSent` and `imagesWithheld`), and `execution.status.json` when a Bedrock call failed (see [Failure behaviour](#failure-behaviour)). With video windows, one `segments/<segmentKey>.json` per window (its description, keywords, objects, actions, on-screen text, label, and time range) and, beside it, `segments/<segmentKey>.failed.json` for a window whose model call failed or from which no frame could be read; the map's own result manifest is written under the execution's auxiliary prefix (`segments/results/`), not here. `execution.status.json` is a reserved results file name for every pipeline; see [Building custom pipelines](custom-pipelines.md).

### Location

When the template tag `EXTRACT_GEO_LOCATION` is `true` (the default) and the file carries no `location` metadata, the pipeline writes `location` as a `geojson` value — the key the geospatial index and the map view read. A `location` you entered yourself is never overwritten: the file's existing metadata arrives with the execution, so the check costs no extra call. The value is a GeoJSON geometry rather than a point only, so a survey area or a tileset footprint is stored as the area it covers. Sources, first match wins:

| Source                                                                                                                                                                                        | Geometry written                                                                                                           | Classes                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `sys_image.exif.gps`                                                                                                                                                                          | `Point` `[longitude, latitude]`, with the altitude as a third coordinate when present                                      | `image`                                                                   |
| `sys_media.gps` (the container's ISO 6709 `location` tag — the QuickTime `©xyz` atom, `com.apple.quicktime.location.ISO6709`, or the 3GPP `location-<lang>` tag — decoded to decimal degrees) | `Point` `[longitude, latitude]`, with the altitude as a third coordinate when the tag carries one                          | `video`, `audio`                                                          |
| `sys_ifc.site` (the IfcSite reference latitude and longitude, converted from degrees-minutes-seconds)                                                                                         | `Point`                                                                                                                    | `ifc`                                                                     |
| `sys_pointcloud` bounds, when `crs.geographic` is `true` (the EPSG:4326 family)                                                                                                               | `Polygon` — the bounding-box ring. A projected CRS contributes `ext_crs` only; coordinates are not reprojected             | `pointcloud`, `splat`                                                     |
| `sys_tiles3d.region` (`[west, south, east, north, minHeight, maxHeight]`, radians converted to degrees)                                                                                       | `Polygon` — the region's bounding box                                                                                      | `tiles3d`                                                                 |
| `sys_geo.footprint`                                                                                                                                                                           | The file's own geometry when it is a single `Point` or `Polygon`; otherwise the bounding-box `Polygon` of all its features | `data` (GeoJSON, GeoPackage in EPSG:4326, layer file with a WGS84 extent) |

Every value passes the structural and ring checks the metadata API applies to `geojson` values before it is written. Setting `EXTRACT_GEO_LOCATION` to `false` also stops the media extractor from recording a coordinate in the attributes: `sys_image.exif.gps` and `sys_media.gps` are not written, and a video or audio container's position tags are withheld from `sys_media.tags`; `hasGps` still records that the file carries one.

### Editing the classification vocabulary

The analysis prompt lists the categories, styles, materials, and colors the model may choose from. They come from the `classificationVocabulary` object in the template's configuration body — a plain JSON object beside the tag placeholders, not a tag — with this shape:

```json
{
    "classificationVocabulary": {
        "categories": {
            "<Category name>": {
                "description": "<one line the model uses to decide>",
                "subcategories": ["<Subcategory>", "..."]
            }
        },
        "styles": ["<style>", "..."],
        "materials": ["<material>", "..."],
        "colors": ["<color>", "..."],
        "allowUnlisted": true
    }
}
```

The shipped default is VAMS-wide rather than domain-specific: the categories `Vehicle`, `Industrial Equipment`, `Architecture`, `Interior & Furniture`, `Terrain & Environment`, `Character & Creature`, `Prop & Object`, `Infrastructure & Utility`, `Medical & Scientific`, `Electronics`, `Document`, `Media`, `Data`, and `Other`, each with a one-line description and three to eight subcategories; the styles `realistic`, `stylized`, `low-poly`, `technical/CAD`, `scanned`, `schematic`, and `other`; sixteen materials (metal, steel, aluminium, plastic, wood, glass, concrete, stone, brick, fabric, leather, rubber, ceramic, composite, paper, other); and sixteen basic color names. `allowUnlisted` is `true`, so the model may answer outside the lists when nothing fits: an off-list value is kept, and is normalised to the vocabulary's spelling when it matches an entry case-insensitively. With `allowUnlisted: false` an off-list category becomes `Other`, an off-list subcategory or style is dropped, off-list materials and colors are removed, and every correction is listed in `analysis-summary.json`.

To change the vocabulary, read the current body, edit the `classificationVocabulary` object while keeping every `{{TAG}}` placeholder in place (the body must still reference every tag), and write it back:

```bash
vamscli pipeline template get -d GLOBAL -p system-genai-metadata -t system-genai-metadata-default --json-output
vamscli pipeline template update -d GLOBAL -p system-genai-metadata -t system-genai-metadata-default --config-body-file config-body.json
```

Editing the configuration body is one of the two changes a [system template](system-pipelines.md) allows, so the new vocabulary applies to the next execution without a deployment. A deployment that registers the bundle again restores the shipped body (the deployment owns system records), so keep a copy of a customised body and re-apply it after such a deployment. Keep the object under 6 KB so the prompt section stays small.

:::warning[Databases that restrict metadata to schemas]
A database with **Restrict metadata outside schemas** (`restrictMetadataOutsideSchemas`) enabled limits an entity's metadata to the fields its schemas give that entity, and only when they give it at least one: a file whose extension no schema field reaches accepts any key. The pipeline's own write-back is not checked against schemas. The workflow's process-output step writes as `SYSTEM_USER`, which the metadata service exempts from schema validation, so the `genai_*` keys land on such a database even where no schema defines them.

The restriction applies to the writes a person or an API client makes, and only to keys that are new to the record: a key already stored on the file or asset passes later writes, including a change to its value, so the `genai_*` keys the pipeline wrote do not block editing the record ([#968](https://github.com/awslabs/visual-asset-management-system/issues/968)). A write that adds a key no schema gives the entity is refused with the metadata service's message, for example when a person adds back a pipeline key they deleted:


## Write targets

The template tag `METADATA_WRITE_TARGET` decides where the descriptive fields land. The asset receives the eight fields an asset-level description needs (title, description, keywords, category, subcategory, style, materials, colors); the file receives all of them.

| Value   | Writes                                                                                                                                                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file`  | The file's `genai_*` metadata. No asset metadata is written.                                                                                                                                                                                                  |
| `asset` | The asset's `genai_asset_*` metadata with `genai_asset_source` (`file:<relativePath>`), `genai_asset_source_version`, and `genai_asset_generated_at`. No descriptive row is written on the file, and the file's existing `genai_*` rows are left as they are. |
| `both`  | Both.                                                                                                                                                                                                                                                         |

The file's attributes, its GeoJSON `location`, and the video window rows go to the file whatever the target. A value other than the three is treated as `file`, with a warning in `analysis-summary.json`. Each run that writes the asset rows replaces their values; the asset's other keys are untouched.

Deployment registers two templates over the pipeline. `system-genai-metadata-default` (**Default GenAI metadata**) writes to the file and is the upload trigger's template. `system-genai-metadata-scene-to-asset` (**Scene to asset GenAI metadata**) is identical except that `METADATA_WRITE_TARGET` defaults to `both`; use it for a scene file that stands for the whole asset, such as a USD stage, a glTF scene, or an assembly. Choose it in the web interface's execute dialog, or name it in a CLI run:

```bash
vamscli workflow execute --workflow-database-id GLOBAL -w system-genai-metadata \
    --input-file <databaseId>:<assetId>:/scenes/main.usda \
    --pipeline-parameters '{"system-genai-metadata": {"templateId": "system-genai-metadata-scene-to-asset"}}'
```

When two files of one asset run with the `asset` or `both` target at the same time, the later write wins for each key; `genai_asset_source` names the file that wrote last. The [asset summary](#asset-summary-workflow) writes the same keys, with the same last-writer rule.

## Key reuse

With the template tag `REUSE_EXISTING_KEYS` on (the default), a run fills the keys a file or asset already carries instead of adding `genai_*` keys beside them, and never overwrites a value a person wrote. With it off, every run writes the plain `genai_*` layer (`genai_asset_*` for the asset targets), clears nothing, keeps no digest record, and reads no metadata schema.

**Which key a field lands in.** The template body's `fieldMapping` object lists, per analysed field, the existing key names that field may fill. The shipped mapping is:

```json
{
    "fieldMapping": {
        "title": ["title"],
        "description": ["description"],
        "keywords": ["keywords", "tags"],
        "category": ["category"],
        "materials": ["material"],
        "colors": ["color", "colour"]
    }
}
```

The fields a mapping can name are `title`, `description`, `keywords`, `category`, `subcategory`, `style`, `materials`, `colors`, `primaryColor`, `objects`, `orientation`, `sizeEstimate`, and `textSummary`. A field takes at most 20 names of at most 128 characters each; an unknown field or a malformed entry is ignored with a warning in `analysis-summary.json`. Names match ignoring case, spaces and punctuation, camelCase, character width (NFKC), a plural on the last word, and a leading `AB_`, so `material` matches `Material`, `MATERIALS`, and `AB_Material`. A field lands in the key that its first matching name finds, and two fields never share one key. Keys under `genai_`, `ext_`, and `sys_`, and `location`, are never filled this way. The model never names a key: a target is the field's own `genai_*` key or a key the entity already carries, and any member of the answer beyond the listed fields is dropped. Edit `fieldMapping` the way you edit the [classification vocabulary](#editing-the-classification-vocabulary); a deployment restores the shipped mapping.

**A person's value is never overwritten.** The pipeline records a SHA-256 digest of each key outside the `genai_` namespace that it writes: in the file's `genai_written` attribute and the asset's `genai_asset_written` metadata. A later run writes such a key again only while its stored value still has that digest. A value someone has edited is left alone: the field lands in its own `genai_*` key, and `analysis-summary.json` lists the key in `keyConflicts` as `{"entity", "field", "key", "reason": "edited"}`.

**Keys and the metadata schema.** The metadata service lists every field of a database's metadata schemas as a key, empty ones included, so an empty key the field mapping finds is usually a schema field, and so is a key the pipeline filled on an earlier run. Both shipped workflows ask for the metadata schema (`metadataInputs.metadataSchema`), and when the run's input carries the schema entry for the file's or asset's database, a key the run may fill, empty or holding the value the pipeline wrote on an earlier run, is filled by its schema type:

-   A text field (`string`, `multiline_string`) receives the value, written with the field's type.
-   An `inline_controlled_list` field receives the list entry that the value, or its first `", "`-separated item, names, in the list's spelling. A value outside the list stays in its `genai_*` key, listed with the reason `notInControlledList`.
-   A field of any other type (`number`, `date`, and the rest) is not filled; the value stays in its `genai_*` key with the reason `typeUnsupported`.
-   A key the schema does not define receives the value with the type of the field's `genai_*` key.

When the schema refuses the value for a key the pipeline filled on an earlier run, that key is emptied too, so its earlier value does not stand beside the new one, and `analysis-summary.json` lists it in `keyReuse.cleared`. A later run fills it again when its value fits.

A file takes, per field, the type from the schema whose file-type restriction lists the file's extension, else from a schema with no restriction; a file without an extension takes only unrestricted schemas. Without the schema entry (a custom workflow that does not ask for it, or a database whose schemas the launching identity may not read), the run cannot tell a text field from a controlled list, so it writes no key outside the `genai_` namespace that the field mapping finds, neither an empty one nor one it filled on an earlier run: the value stays in its `genai_*` key with the reason `typeUnknown`, the key keeps its value, and the next run that has the schema fills it again. `analysis-summary.json` carries the warning "No metadata schema of database `<db>` reached this run (the workflow does not ask for it, or the launching identity may not read it); metadata keys outside the `genai_` namespace that the field mapping matched were not written." Runs that the upload trigger and the vector reindexer start read the schema as `SYSTEM_USER`, which the deployment's default role assignment allows to read the schemas of every database.

**Structured output.** When the schema applies, the analysis request offers the model one tool, `record_analysis`, whose input schema is the field list. A field that lands in a controlled-list key has the list's values named in its description, and the prompt lists them under "Values the metadata schema lists, per field:"; the model is asked to give one of them when it fits and the value that does when none fits. The list is guidance rather than a constraint, so a subject that none of its values describes keeps its own value in the field's `genai_*` key with the reason `notInControlledList` (see above) instead of receiving a wrong list entry. The complexity grade is the one field limited to fixed values (`low`, `medium`, `high`). A request with the tool also asks the model to leave out a field that does not apply. A model that refuses tool use (a `ValidationException` that names tool use) is asked again in the prompt's JSON form without spending an attempt, and later requests from the same function instance skip the tool for that model. A model that fails while producing the tool call (a `ModelErrorException` that names tool use, which Amazon Nova Lite returns for some files) is asked the same request once again in the JSON form, without spending an attempt; its later requests still offer the tool, and a failure of the JSON request is recorded as `BedrockModelError`. A model that answers in text is read the same way. `analysis-summary.json` records the form in `replyFormat` (`tool` or `text`). With the `both` target only the file's schema constrains the answer, because one answer feeds both entities; an asset key whose list does not hold the answer keeps the value in its `genai_asset_*` key and is listed as a conflict.

A guardrail attached to a Converse call does not evaluate the tool input a model returns (see [Use a guardrail with the Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)), so the pipeline screens a tool answer with `ApplyGuardrail` as model output before reading it. A block fails the analysis as `BedrockGuardrailIntervened`; masked values are written with the mask tokens and set `guardrailMasked`. Only the listed fields survive, and their types, lengths, and controlled lists are checked as for a text answer.

**Clearing.** A `genai_*` field (`genai_asset_*` on the asset) that a re-run no longer produces is written as an empty value, and so is the `genai_*` key of a field that now lands in a key the entity already carried. A key outside the `genai_` namespace is emptied only when the pipeline filled it on an earlier run and the schema refuses this run's value (see above); a key a person owns is never cleared, and neither is one the pipeline filled when the run does not produce its field or has no schema. With the `asset` target the file's `genai_*` rows are left as they are.

**Previous analysis.** With `SEED_WITH_EXISTING_METADATA` also on, the prompt carries the pipeline's earlier values for the entity it writes (the asset's for the `asset` target) under "Previous analysis of this file:", so titles and keywords stay stable between runs, and `genai_source_modalities` includes `previous-analysis`. The section is guarded like the other existing metadata.

**The `autoGeneratedKeywords` key.** On an asset that carries `autoGeneratedKeywords`, the asset targets and the asset summary write the keywords there and treat the key as the pipeline's own, and `genai_asset_keywords` is cleared if present.

`analysis-summary.json` records the outcome in its `keyReuse` block (`enabled`, `schemaRead`, `targets` per entity as field to key, `cleared`, and `previousValues`, the number of earlier-result lines the prompt carried) and its `keyConflicts` list.

## Asset summary workflow

The SYSTEM GenAI asset summary describes a whole asset, or one folder of it, from the descriptions the per-file pipeline wrote on its files, and writes the result as the asset's `genai_asset_*` metadata. It is a second system workflow of the same deployment and configuration block.

**Running it.** Run it after the per-file pipeline has described the asset's files, from the web interface's execute dialog with the asset or a folder selected, or from the CLI:

```bash
vamscli workflow execute --workflow-database-id GLOBAL -w system-genai-asset-summary \
    --input-file <databaseId>:<assetId>:/
```

A single-file selection is accepted at launch and then fails the execution with `SystemGenAiAssetSummaryError` and the message "This workflow summarises a whole asset or a folder of it: select the asset or a folder, not a single file."

**What it reads.** The workflow asks for the per-file metadata of every current file under the selection (`metadataInputs.assetFileMetadata`, at most 500 files per selection; archived files and `*.previewFile.*` thumbnails are left out) and for the metadata schema. From each file it reads the title, description, keywords, and category the per-file analysis wrote, and the `sys_dependencies` attribute. Each field is read from its `genai_*` key (`genai_title`, `genai_description`, `genai_keywords`, `genai_category`), or, when that is empty, from the key the file's `genai_targets` attribute names: with [key reuse](#key-reuse) the per-file run may write the description into a `Description` key the file already carries. A value a person edited in that key since the run is read as it stands. A file whose analysis wrote its description to the asset only (write target `asset`) has no description to summarise. The asset's name, description, and tags are in the prompt, and with `SEED_WITH_EXISTING_METADATA` on its existing metadata as well; database metadata is not read.

**Order in the prompt.** Scene files that load other files and that no other file of the selection loads come first, the one that loads the most first, and a file a scene loads is marked as that scene's part; then the other scenes, then every other file. Each line carries the file's title, its description cut at 400 characters, its keywords, and its category. The file lines are capped at 40,000 characters, and the prompt says how many described files were left out. When the selection holds more files than the run's input carries, the prompt says so, `analysis-summary.json` carries a warning, and `files-without-description.json` records `selectionCapped: true`.

**What it writes.** One Converse call on the model, with the file lines and the asset's metadata guarded, produces `asset.metadata.json` (`updateType: update`): the eight descriptive `genai_asset_*` keys under the [key reuse](#key-reuse) rules, typed by the asset's metadata schema when the run carries it; `genai_asset_source` as `aggregate:<selection>`; an empty `genai_asset_source_version`; `genai_asset_file_count`, the number of files whose descriptions the prompt carried; `genai_asset_generated_at`; and `genai_asset_written` when key reuse changed it.

**Results.** `analysis-summary.json` with `analysisMode: asset-summary`, `selection`, `fileCount`, `describedCount`, `undescribedCount`, `filesListed`, `fileExpansion`, token usage, guardrail masking, warnings, vocabulary corrections, `writeTarget: asset`, `assetMetadataFile`, `keyReuse`, `keyConflicts`, and `replyFormat`; and, when any file had no description or the selection was capped, `files-without-description.json` with `count`, the first 200 `files`, `moreNotListed`, `selectionCapped`, `omittedFileCount`, and `omittedFileCountExact`. A selection none of whose files carries a description fails with `AssetSummaryNoFileDescriptions` ("No file under / carries a description yet; run the SYSTEM GenAI metadata pipeline on the asset's files first.") and makes no model call. A Bedrock failure is recorded through `execution.status.json` with the per-file pipeline's error codes.

**Permissions.** Running the summary needs the same workflow execute permission as any workflow. The per-file metadata and the schema are read with the launching user's identity, so a summary carries only what that user may read.

## Embeddings and the `vector.embedding.ready` event

When `app.vectorSearch.enabled` is `true` and the analysis succeeded, `GenerateEmbeddingTask` builds the embedding text from, in order and deduplicated, one line per part: the asset name, description, and tags; the database id, the file path, and the file class; the `genai_*` block — `genai_title`, `genai_description`, `genai_keywords`, `genai_category`, `genai_subcategory`, `genai_style`, `genai_materials`, `genai_colors`, `genai_objects`, `genai_size_estimate`, `genai_orientation`, `genai_text_summary`; human-readable attribute facts (dimensions with units, counts, duration, resolution, pages, camera, CRS — the same values the `ext_*` fields carry); the existing metadata of the file, then of its asset, then of its database, then the file's attributes that no pipeline wrote, as `key: value` lines sorted by key within each group; and, last, the text excerpt when `EMBEDDING_INCLUDE_TEXT_EXCERPT` is `true`. The `genai_*` part is read from the run's `analysis-result.json` under the execution's auxiliary prefix, which holds the analysis in the pipeline's own key names, so the text is the same whichever keys the values landed in, and a file analyzed with the `asset` [write target](#write-targets) is embedded like any other.

The existing metadata contributes in every run — `SEED_WITH_EXISTING_METADATA` governs only what the analysis model is shown — so the embedding represents what users already recorded about a file whether or not the model saw it. Keys under the `ext_`, `genai_`, and `sys_` prefixes are skipped because the current run contributes them fresh; legacy `autoGeneratedKeywords` and `AB_*` rows and other pipelines' keys are kept. A GeoJSON value is rendered as its geometry type (for example `Point geometry`), any other value longer than 400 characters is cut there, and the lines are kept whole up to 12,000 characters in total: the first line that would cross the budget and every later line are dropped, and the dropped count is logged as a warning and recorded in `analysis-summary.json`. The excerpt comes last because it is the one unbounded, low-density part — when the embedding model's window cuts anything, it cuts the excerpt, never the metadata. The text is truncated to VAMS's per-model budget (30,000 characters for Amazon Titan Text Embeddings V2 — below the model's own 8,192-token limit, leaving headroom for dense attribute JSON), embedded with `normalize: true`, and written as a document to the auxiliary bucket.

`sourceModalities`, on the event and on the vector item, lists in composition order each part that contributed at least one line: `asset-metadata`, `file-identity`, `genai-metadata`, `file-attributes`, `existing-file-metadata`, `existing-asset-metadata`, `existing-database-metadata`, `existing-file-attributes`, and `file-text`. A `videoTime` segment document also lists `segment-frames`; a `textChunk` document lists `asset-metadata`, `file-identity`, `genai-metadata`, and `file-text`. The four `existing-*` labels show — on the vector item, in the API's `_vector` block, and in the web interface's relevance popover — that a database's or an asset's metadata reached a file's vector without reading the stored text. A label records that at least one line of that scope reached the text, not that the scope was captured whole; a scope whose metadata could not be read carries no label, like one that has nothing. This vocabulary is distinct from the analysis model's `genai_source_modalities`, which records what the model saw.

The embedding reflects the metadata that existed when the run read its inputs, and those inputs are bounded when the execution is launched: each entity's metadata is kept in key order up to 1,000 entries and 300 KiB — an entry that does not fit is skipped, so a single value larger than that budget never reaches the run — and an entity whose metadata could not be read contributes an empty scope. A bounded entity and an unreadable database are reported in the execute request's response `warnings`, and every partial capture is logged by the execute-workflow Lambda; a run launched by the upload trigger or by the reindexer has no caller to receive the warnings. A first upload usually carries asset and database metadata but no file metadata yet, and a later metadata edit does not re-embed the file; re-executing the workflow on the same file version, or running the vector reindexer, picks up the current values.

The pipeline then publishes one event on the VAMS orchestration bus — the same contract any pipeline with `events:PutEvents` on the bus can use to contribute embeddings:

| Event field  | Value                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Source`     | The execution's `orchestrationEventPrefix` from the manifest                                                                                                                                                                                                                                                                                                                                                            |
| `DetailType` | `vector.embedding.ready`                                                                                                                                                                                                                                                                                                                                                                                                |
| `Detail`     | `schemaVersion` (1), `databaseId`, `assetId`, `filePath`, `versionId`, `contentEtag`, `bucketId`, `fileClass`, `fileExt`, `fileSize`, `contentType`, `embeddingModelId`, `embeddingDimensions`, `analysisModelId`, `sourceModalities`, `pipelineExecutionId`, `workflowExecutionId`, `generatedAt`, `documentS3Location`, `segmentKey`, `segmentKind`, `segmentLabel`, `segmentStartMs`, `segmentEndMs`, `segmentCount` |

The embedding vector and the source text travel only in the document at `documentS3Location`, never in the event. The vector indexer reads the document, writes the vector item, marks the file's other versions as not latest, and deletes the document. It drops a document whose `embeddingModelId` or `embeddingDimensions` differ from the deployed vector index. A manifest built from an earlier workflow step's outputs carries an empty `bucketId`; the indexer then resolves the file's bucket from the asset row. See [Vector search](../concepts/vector-search.md).

### Segment vectors

A file version may carry more than one vector. Beside the whole-file vector, the pipeline publishes one vector per [video window](#video-windows) and one per [content chunk](#content-chunks), each under the same file with its own `segmentKey` — a fixed-width key of at most 32 bytes that sorts in content order (`t` plus a 10-digit start millisecond for a window, `c` plus a 6-digit ordinal for a chunk, `c000001` first) — and a `segmentKind` of `videoTime` or `textChunk`. The whole-file vector carries `segmentKey` empty, `segmentKind` `none`, `segmentLabel` empty, and `segmentStartMs`/`segmentEndMs` null; every vector of the run carries the same `segmentCount`: the number of chunks the run embeds (its chunk count), or the number of windows planned (`0` for a run without segments; for windows, a count a skipped window does not reduce — see [Video windows](#video-windows)). `segmentKind` is one of the seven filter attributes of the vector index, so a search can ask for whole-file vectors only.

Segment vectors share the file's key prefix in the vector table, so every lifecycle rule — a new version, archive, unarchive, permanent delete, reindex — covers them together with the whole-file vector, and the vector indexer removes the segments an earlier run published for the same version when the new run's whole-file document arrives. Search returns one hit per file however many of its windows or chunks matched; see [Vector search](../concepts/vector-search.md).

Any pipeline that publishes `vector.embedding.ready` may emit several vectors for one file version the same way, by giving each document and event a distinct `segmentKey`, a `segmentKind` of `videoTime` or `textChunk`, a `segmentLabel`, and — for `videoTime` only — `segmentStartMs` and `segmentEndMs`. A `Detail` without the six segment fields is indexed as the file's whole-file vector.

### Video windows

Off by default. When the template tag `VIDEO_SEGMENT_SECONDS` is `2` or more, the media branch divides the video into equal time windows: the window count is the duration divided by the tag value and rounded up, capped at 360 per file, and the effective window length is the duration divided by that count — so a window is at most as long as the tag and usually slightly shorter (a 45-second video at `10` gives five windows of 9.0 seconds, not four of 10 and one of 5), and a longer video is sampled coarser rather than cut off. The effective length is recorded in `genai_segment_interval_seconds`; a video shorter than two windows produces none. Each window is analyzed by one child execution of the pipeline's state machine, eight at a time: it reads three frames at 10 %, 50 %, and 90 % of the window through a presigned URL (downloading the file once when the URL read fails), asks the analysis model for a short description, keywords, objects, actions, and any on-screen text, embeds those together with the asset name, the file path, and the file's own `genai_title` and `genai_category` (the guardrail screens that composed text before it is embedded — see [Amazon Bedrock guardrail](#amazon-bedrock-guardrail)), and publishes the vector with `segmentKind` `videoTime`, a key of `t` plus the window's start millisecond zero-padded to 10 digits, and a label of the form `HH:MM:SS.mmm–HH:MM:SS.mmm`. The window document's `sourceModalities` are `asset-metadata`, `file-identity`, `segment-frames`, and `genai-metadata` — `segment-frames` marks the three frames as the content the model described. The file's metadata records `genai_segment_count` and `genai_segment_interval_seconds`; window descriptions are **not written as file metadata** (file metadata has no time axis) but land as results — `segments/<segmentKey>.json` per window — so a consumer can read matching timestamps without re-analyzing the video.

A window whose model call fails, or whose `vector.embedding.ready` event cannot be published, is recorded, not raised: the child writes `execution.status.json` with `BedrockSegmentError` or `SegmentPublishError` and `segments/<segmentKey>.failed.json` beside the window records, then completes normally; the map completes, the execution is recorded **FAILED**, and every vector already published stays indexed (a window document written but not published is overwritten by key on the re-run). A window from which `ffmpeg` can read no frame — a black or corrupt stretch — is **skipped**, not failed: the child returns `SKIPPED` with `SegmentFramesUnavailable`, writes the `.failed.json` record and no `execution.status.json`, and publishes no vector. The whole-file vector's `segmentCount` is therefore the **planned** window count, and a video with skipped windows carries fewer window vectors than it states. A child that crashes — a timeout, an out-of-memory condition, a throttled invocation — is retried twice, after 10 and 20 seconds; a Lambda service fault on the invocation itself is instead retried up to six times by the invoke retrier — whichever retrier matches the error class applies; a window is idempotent, so a retry publishes the same vector under the same key. A child that still fails after its retries fails the map and the execution like any other crash. The map's own result manifest — each window's `segmentKey`, `status` and `documentS3Location`, with an `error` code (`BedrockSegmentError`, `SegmentPublishError` or `SegmentFramesUnavailable`) on a failed or skipped window — is written under the execution's auxiliary prefix, `segments/results/`.

Three images per window are about 5,000 input tokens: about $0.005 per window with Claude Haiku 4.5, about $2 per hour of video at a 10-second interval, plus a negligible embedding cost — which is why the tag is off by default and its interval is bounded below at 2 seconds. One video in flight is about eight children every ten seconds, or about 240,000 input tokens per minute against the account's Claude Haiku 4.5 quota — commonly 1–2 million tokens per minute — so roughly four to eight videos analyze concurrently before Amazon Bedrock throttles; a throttled window retries adaptively and then records `BedrockThrottled`. The pipeline reserves no Lambda concurrency: raise the model quota or stagger bulk video uploads.

Each window request uses the deployment's `bedrockModels.inference` settings, the same as the whole-file analysis. `maxTokens` is a ceiling and billing follows the tokens the model produces; a window description is short (at most 400 characters plus short lists), so the setting does not change a normal window's cost. Window analysis needs an image-capable analysis model. With `bedrockModels.analysisModelSupportsImages` set to `false`, no window is analyzed and no window vector is published, the video gets no `genai_segment_count` or `genai_segment_interval_seconds` rows, `sys_media.videoSegments` records `"analysed": false` with the reason `analysisModelTakesNoImageInput`, and `analysis-summary.json` carries a warning.

### Content chunks

On by default. For document, text, and data files (including the ‡ office formats), the media branch captures the full extracted text — up to 2,000,000 characters — together with the page, slide, or sheet boundaries, and `GenerateEmbeddingTask` embeds it in windows of 1,600 characters with 200 characters of overlap, each end snapped to the last paragraph or sentence break inside the final fifth of the window, at most 1,000 chunks per file version (text beyond that is not chunked, and the dropped count is logged). Each chunk is published as its own vector with `segmentKind` `textChunk`, a key of `c` plus the chunk's 1-based ordinal zero-padded to 6 digits (`c000001` is the first chunk), and a label of the form `chunk 12/200 · page 7` (the page, slide, or sheet where the chunk starts; omitted when the file has none), embedding the asset name, the file path, the file's `genai_title`, the label, and the chunk text; its `sourceModalities` are `asset-metadata`, `file-identity`, `genai-metadata`, and `file-text`. The file's attributes record `genai_content_chunk_count`. Content chunks are produced for files up to 50 MiB. A larger document, text, or data file keeps its whole-file vector, built from the first 12,000 characters of its text and the generated summary, and produces no chunks; the run records the skip in its results and writes no `genai_content_chunk_count`. A thousand chunks cost about a thousand embedding calls — well under a cent with Amazon Titan Text Embeddings V2 — so the feature is on by default; set `CONTENT_CHUNKING` to `false` for whole-file vectors only. A failure while chunking is recorded like any other embedding failure (`BedrockAccessDenied`, `BedrockThrottled`, or `BedrockEmbeddingError`), and a chunk event that cannot be published is recorded as `SegmentPublishError`; in every case the chunks already published stay indexed.

## Prerequisites

### Amazon Bedrock model access

The pipeline calls Amazon Bedrock with the deployment's Lambda roles, which hold `bedrock:InvokeModel` on the configured models and no AWS Marketplace permissions; no function streams a response. Each function is granted the models it calls: the analysis function the analysis model and, when one is set, the text model; the embedding function the embedding model; the video window function the analysis model and the embedding model; the asset summary the text model, or the analysis model when no text model is set. Model access itself is account state, and every configured model needs it:

-   **Commercial AWS** — Bedrock enables third-party models on first invocation when a principal in the account holds `aws-marketplace:Subscribe`, `aws-marketplace:ViewSubscriptions`, and `aws-marketplace:Unsubscribe`. Invoke the analysis model once from such a principal, or enable it on the Bedrock console's **Model access** page, before the first upload. Amazon-provider models — including the default Amazon Titan Text Embeddings V2 — need no Marketplace step.
-   **Anthropic models** (the commercial and GovCloud defaults) additionally require a one-time use-case form, submitted once per account or once at the organization's management account. Until it is submitted, Bedrock returns `FTUFormNotFilled` and the pipeline records the execution as failed with `BedrockAccessDenied`.
-   **AWS GovCloud (US)** — model access is a manual step. Enable a third-party model, such as the default Anthropic analysis model, in **both** the linked commercial account and the GovCloud account (console **Model access** page in `us-gov-west-1`); enable an Amazon model, such as Amazon Titan Text Embeddings V2, in the GovCloud account only (see [Access Amazon Bedrock foundation models in AWS GovCloud (US)](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html#model-access-govcloud)). Use a `us-gov.` inference profile id for `bedrockModels.analysisModelId`.
-   **AWS European Sovereign Cloud** — configuration validation rejects `app.vectorSearch.enabled: true`, and the template ships `useGenAiAnalysis: false` with no analysis model, so the pipeline runs attributes-only there; set a model and turn the layer on once one is available in the partition.

Configuration validation warns at synthesis when `bedrockModels.analysisModelId` or `textModelId` names an Anthropic model, as a reminder of the form. Deployment prerequisites are collected in [Prerequisites](../deployment/prerequisites.md).

### Amazon Bedrock guardrail

The analysis prompt carries untrusted content — the text extracted from an uploaded file, user-entered metadata, and asset descriptions. Amazon Bedrock Guardrails screens that content before the model reads it, and the deployment creates the guardrail by default (`app.pipelines.useSystemGenAiMetadata.bedrockGuardrail.create.enabled`, `true` in the commercial template). The pipeline wraps the untrusted blocks of every Converse call — the analysis call, each video-window call, and the asset summary's call — in guardrail content tags so the filters evaluate them. The same content reaches the embeddings model, which accepts no guardrail on its own invocation, so with vector search enabled the embedding step (`GenerateEmbeddingTask`, and the window child for its window text) first sends the composed text — and every content chunk, several per call — through the guardrail's `ApplyGuardrail` operation and embeds the text the guardrail returns: an entity the PII filter masks is a type token (`{NAME}`, `{EMAIL}`, …) in the vector's input and in the `sourceText` the vector table stores, never the value. The analysis, embedding, and video window functions and the asset summary step receive `bedrock:ApplyGuardrail` on that guardrail only; the analysis function and the summary step also use it to screen a structured-output answer (see [Key reuse](#key-reuse)).

The created guardrail is configured as follows:

-   **Prompt-attack filter** on the prompt at `create.promptAttackInputStrength` (`LOW`, `MEDIUM`, or `HIGH`; default `LOW`), and none on the model response. Start at `LOW` and raise the strength only when malicious prompts pass; a higher strength blocks more legitimate file content. Configuration validation rejects any other value, so the input side is never `NONE`.
-   **PII filter** per `create.piiFilter`, applied to the prompt and to the model response alike: `anonymize` (default) masks, and `block` rejects, an email address, phone number, person name, postal address, US Social Security number, payment card number, AWS access key, AWS secret key, or password; `off` adds no PII filter. Metadata generation does not need personal data, so the default masks an entity in the prompt before the model reads it and masks one the model writes before the response reaches the pipeline, each replaced by its type token (`{NAME}`, `{ADDRESS}`, `{EMAIL}`, …). The address detector also matches some place names, so survey and GIS data can show `{ADDRESS}` where a site or landmark was named; set `piiFilter` to `off` for data that holds no personal information. A masked prompt or response is analyzed normally and the run **succeeds**: the `genai_*` values carry the tokens where the entities were, and `analysis-summary.json` records `guardrailMasked: true` with the masked entity types in `guardrailMaskedTypes` (types only, never the values). Only `block` makes a detected entity an intervention. An operator-owned guardrail whose PII filter sets the legacy per-entity `action` alone masks the response only; set its input action too, or use `block`, to keep PII from reaching the model.
-   **Encryption** with the deployment's KMS key when `app.useKmsCmkEncryption.enabled` is `true`, otherwise with the AWS-managed Amazon Bedrock key. The role that deploys the stack needs `kms:Decrypt`, `kms:GenerateDataKey`, `kms:DescribeKey`, and `kms:CreateGrant` on that key (the default AWS CDK bootstrap role has them), and the analysis functions hold `kms:Decrypt` through the standard VAMS key grant.
-   **A published version** follows the draft, and the analysis functions reference that version, never `DRAFT`. Changing the strength or the PII filter publishes a new version on the next deployment.
-   **A fixed name**, `VAMS-SystemGenAiMetadata-<deployment hash>`, unique per deployment in an account and Region. The name is required by Amazon Bedrock, so the guardrail is an explicitly named resource: an orphaned copy left by a failed teardown collides with a redeploy of the same configuration (see [Uninstall](../deployment/uninstall.md#step-1-destroy-the-cdk-stack)).

To use a guardrail you own instead — one with denied topics, word filters, or a different PII treatment — set `create.enabled` to `false` and reference it in `guardrailIdentifier` and `guardrailVersion` (both or neither): create it in the deployment Region with the **Prompt attacks** content filter enabled at input strength `LOW` or higher and publish a version. Configuration validation rejects `create.enabled` together with a `guardrailIdentifier`, because the analysis functions carry one guardrail. A configuration written before the `create` block existed that already names a guardrail keeps it: an absent `create.enabled` defaults to `true` only when no `guardrailIdentifier` is set.

**How an intervention surfaces.** Amazon Bedrock returns `stopReason: guardrail_intervened` whenever the guardrail acted — when a filter **blocked** the prompt or the response, and also when the PII filter only **masked** text — so the pipeline reads the guardrail trace to tell the two apart. A `BLOCKED` action in any filter of the trace — a prompt-attack detection, or PII under `piiFilter: block` — is a caught failure: the pipeline writes `execution.status.json` with `BedrockGuardrailIntervened` and a cause that lists the filters that fired (policy, type, action, and confidence — never the matched text), and the execution is recorded **FAILED** while the file's attributes and promoted metadata still land (see [Failure behaviour](#failure-behaviour)). A video window the guardrail blocks fails that window only. A trace whose actions are all `ANONYMIZED` is not an intervention: the response is the complete answer with mask tokens, the analysis completes, and `guardrailMasked` is recorded (on `analysis-summary.json` for the file, on `segments/<segmentKey>.json` for a window). A `guardrail_intervened` response that carries no trace at all is treated as an intervention. The embedding step's `ApplyGuardrail` pass follows the same reading: a masked text is embedded and stored masked, and the embedding summary (`embedding/summary.json` under the execution's auxiliary prefix) records `guardrailMasked` with the masked types; a blocked whole-file text is the same `BedrockGuardrailIntervened` failure with no vector published, and a blocked content chunk is skipped while the other chunks are still embedded and the run is recorded **FAILED** naming that chunk. Every successful analysis, window, asset summary, and embedding logs one `Guardrail assessment` line — the filters that acted, by side (prompt or response), policy, type, and action — so input-side masking is auditable from Amazon CloudWatch. For an answer that came as a [structured-output](#key-reuse) tool call, the response side lists the filters of the `ApplyGuardrail` screen of that answer.

:::tip[Guardrail coverage]
Every Amazon Bedrock call fed with user-supplied content runs behind a prompt-attack filter, with PII masked in both the input and the output under the default `piiFilter`: the analysis, window, and asset summary Converse calls through their guardrail configuration and, for a tool answer, an `ApplyGuardrail` pass on the output, the embeddings calls through the `ApplyGuardrail` pass on the text they receive. Configuration validation rejects `create.enabled` `false` without a `guardrailIdentifier` whenever the pipeline calls Amazon Bedrock, that is with the GenAI analysis on or with vector search on, in every partition and with no opt-out. The commercial and AWS GovCloud (US) templates create the guardrail. The AWS European Sovereign Cloud template ships `create.enabled` `false` with the attributes-only pipeline, which makes no Amazon Bedrock call, because Amazon Bedrock Guardrails availability there is unverified; turning on the GenAI layer there requires a guardrail, created or named.
:::

### Network

The pipeline's Lambda functions run outside the VPC unless `app.useGlobalVpc.useForAllLambdas` is `true`, in which case VAMS creates the Amazon Bedrock Runtime interface endpoint for them. With `useFargateRenderer` the AWS Batch job runs in the isolated pipeline subnets and needs the shared Batch and ECR endpoints. See [Pipeline System Overview — VPC and Network Requirements](overview.md#vpc-and-network-requirements).

An input file whose asset bucket is in another Region is read through that Region: the workflow manifest names the bucket's Region, `vamsExecute` forwards it, and every reader of the file — the classifier's header and digest reads, the media and Blender extractors, the 3D renderer — signs its requests for that Region through the state's `bucketRegions` map. Whether such an input is admitted depends on where the code that reads it runs:

-   **Outside the VPC** (the default, `app.useGlobalVpc.useForAllLambdas` off), the Lambda functions read a bucket in any Region through the public Amazon S3 endpoints, and the input is admitted.
-   **With `useForAllLambdas`**, every function runs in the isolated pipeline subnets, so the input is admitted only when the VPC carries a cross-Region Amazon S3 interface endpoint for its Region (`app.useGlobalVpc.addCrossRegionS3Endpoints`); an input in any other Region is rejected at launch with `SendTaskFailure` naming both remedies.
-   **The Fargate renderer** (`useFargateRenderer`) always runs in the isolated subnets, so it is used only for an input in the deployment Region or in a Region with such an endpoint. Elsewhere a file over the Lambda limits is described from its attributes, as it would be without the renderer, and a scene whose referenced files exceed the Blender function's budget is rendered by that function with the files that fit; a warning in `analysis-summary.json` names the Region.

See [External Amazon S3 Setup — Pipelines and cross-Region inputs](../deployment/external-s3-setup.md#pipelines-and-cross-region-inputs).

## Template

Deployment registers two templates over the pipeline, `system-genai-metadata-default` and `system-genai-metadata-scene-to-asset`, which differ only in the default of `METADATA_WRITE_TARGET` (see [Write targets](#write-targets)). Each configuration body references every tag below and carries two plain JSON objects that are not tags: `fieldMapping` (see [Key reuse](#key-reuse)) and `classificationVocabulary` (see [Editing the classification vocabulary](#editing-the-classification-vocabulary)). The default template is the trigger's default for the pipeline. A template's body and tag schema are the only parts of it that can be edited on a system pipeline. The asset summary has a template of its own; see [Asset summary workflow](#asset-summary-workflow).

A template never names a model: the models are deployment settings, and each function's Amazon Bedrock grant is scoped to the models the configuration names. A rendered configuration body or a custom template override that carries `modelId`, or any key ending in `ModelId` in any spelling and at any depth, is refused before the run starts. The keys inside `classificationVocabulary` and `fieldMapping` are data, so a category named `Product Model ID` is accepted:

```text
The template configuration sets <keys>: this pipeline's Amazon Bedrock models are deployment settings (app.pipelines.useSystemGenAiMetadata.bedrockModels), so a template or an override may not name one.
```

To change a model, edit `bedrockModels` in `config.json` and deploy.

## Failure behaviour

-   **Attributes first.** `<relativePath>.attribute.json` is written before any Bedrock call, so a model failure never discards extracted attributes.
-   **Bedrock failures are recorded, not raised.** When the analysis or embedding call fails with an access, model, throttling, guardrail, or input-length error, the pipeline writes `execution.status.json` to the results prefix as `{"status": "FAILED", "error": "<code>", "cause": "<detail>"}` with one of `BedrockAccessDenied`, `BedrockModelError`, `BedrockThrottled`, `BedrockGuardrailIntervened`, or `BedrockEmbeddingError`, completes normally, and the workflow's process-output step applies the attributes and then records the execution — and its pipeline step — as **FAILED** with `executionError` set to `<code>: <cause>`. No embedding is published for an execution recorded as failed; the vector for that file version is produced by a later run (a re-upload or a reindex).
-   **Window failures are recorded per window.** A child of `VideoSegmentMap` whose model call fails (`BedrockSegmentError`) or whose event cannot be published (`SegmentPublishError`) writes `execution.status.json` with that code and `segments/<segmentKey>.failed.json`, then completes normally; the map finishes, the execution is recorded **FAILED**, and every vector already published stays indexed. A chunk event that cannot be published is `SegmentPublishError` the same way. A content chunk the guardrail blocks is skipped and recorded as `BedrockGuardrailIntervened` naming the chunk, while the whole-file vector and the other chunks are still published. A window with no readable frame is skipped (`SegmentFramesUnavailable`) and fails nothing (see [Video windows](#video-windows)).
-   **Configuration faults stop the run before it starts.** A configuration body or custom template override that is not a JSON object, or that names a model, fails the execution in `vamsExecute`, before the state machine starts.
-   **Render faults degrade.** A timeout, out-of-memory condition, or loader exception in a render task marks the render as skipped and continues attributes-only; the execution succeeds. `analysis-summary.json` then records `renderSkipped: "error"`, the branch whose render failed in `renderBranch` (`FARGATE` for the Fargate render job), and the reason in `warnings` (for example `Render failed: <reason>`), and the 3D render image logs a line saying that the render failed on that branch and the file was analysed without views. A missing or refused [referenced file](#referenced-files) is recorded and never fails the run. An AWS Batch render attempt whose task fails to start is retried, up to three attempts (see [Size gates and the Fargate renderer](#size-gates-and-the-fargate-renderer)).
-   **Asset summary failures.** A summary of a selection none of whose files carries a description is recorded as `AssetSummaryNoFileDescriptions` without a model call, and a single-file selection fails the execution with `SystemGenAiAssetSummaryError`; Bedrock failures use the codes above.
-   **Crashes fail.** An uncaught fault in `ConstructPipelineTask`, `GenerateMetadataTask`, `GenerateEmbeddingTask`, or — after its two retries — a child of `VideoSegmentMap` reports failure through the task token and the workflow records the execution as failed through its error handler.

The execution detail page shows the recorded error, and `analysis-summary.json` lists every skip.

The execution's log view reads each of the pipeline's Lambda functions as a separate log source: `openPipeline` registers the `/aws/lambda/<function>` log group of every Lambda the state machine runs, under the state that runs it (`ConstructPipelineTask`, `BlenderRenderTask`, `Render3dTask`, `MediaExtractTask`, `GenerateMetadataTask`, `GenerateEmbeddingTask`, `VideoSegmentMap` for the window function, and `PipelineEndTask`), and its own log group, alongside the state machine log and, with the Fargate renderer, the render job's container log. Every run shares these log groups, so every line the functions log carries the run's `workflowExecutionId` and `pipelineExecutionId`, and the view reads only the lines of the run it shows. A branch the file did not take shows no lines.

## Costs

Each execution incurs one Amazon Bedrock Converse call (text plus up to eight images) on the analysis model and, with vector search enabled, one embeddings call. Lambda time is dominated by rendering (up to 10 GB memory for the 3D images). With `VIDEO_SEGMENT_SECONDS` of `2` or more, add one Converse call with three images per window (about $0.005 with Claude Haiku 4.5, at most 360 windows per file); content chunks add one embeddings call per chunk, which is negligible. Every analysis call carries the guardrail, so it is also billed on the text units of its screened prompt text and of its response, and the embedding step adds `ApplyGuardrail` calls on the text it embeds: one for the whole-file text and one per ten content chunks (a call carries at most ten texts and 20,000 characters). Each is billed per policy on the guardrail's text units of 1,000 characters — about $0.25 per 1,000 text units for the created guardrail's prompt-attack (content filter) and PII policies, so a 10-page document of some 30 chunks costs about 2 cents to screen and a 1,000-chunk document about 50 cents; a video window adds one call of a single text unit. With `useFargateRenderer`, the VPC endpoints the renderer needs are a standing monthly charge and each render job bills AWS Fargate time at 16 vCPU and 64 GiB. With the commercial template's models, a typical file costs about $0.01–$0.05 to analyze and embed. A request without images goes to `bedrockModels.textModelId` when one is set, at that model's price. With a guardrail configured, a schema-aware analysis (key reuse on, with the metadata schema in the run's input) that receives a tool answer adds one `ApplyGuardrail` call on that answer, a few text units. Each [asset summary](#asset-summary-workflow) is one text Converse call whose input grows with the number of described files, up to 40,000 characters of file lines, plus the guardrail's text units on the guarded part and, for a tool answer, one `ApplyGuardrail` call on it. See [Natural-language (vector) search costs](../overview/costs.md#natural-language-vector-search) for the per-file, per-query, and standing figures.
