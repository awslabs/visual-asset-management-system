# EDH Workstations User Guide

The EDH Workstations add-on lets you launch GPU workstations on a connected EDH cluster from VAMS, open them in your browser as Amazon DCV desktops, and, where the deployment enables container jobs, run simulation jobs on the same cluster. EDH itself calls a workstation a _virtual desktop_; this page says _workstation_ for the VAMS record and _desktop_ for the EDH object it wraps. Administrators register the images users launch, review and reclaim sessions, set the lease policy and, where enabled, build images from AMI recipes.

:::note
The workstation pages appear only when the deployment enables the EDH Workstations add-on and your role allows them. For how the add-on works internally, see [EDH Workstations Add-on](overview.md).
:::

## Before you begin

### Deployment features

The add-on and its optional parts are turned on in the deployment configuration. The pages read the enabled features at sign-in, so a section that is not enabled is not shown.

| Feature                               | Deployment setting                                                                                                | What it adds                                                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| EDH Workstations add-on               | `app.addons.useEdhWorkstations.enabled`                                                                           | The **Virtual Workstations** and **Admin - Workstations** navigation sections                                        |
| Container jobs                        | `app.addons.useEdhWorkstations.containers.enabled`                                                                | The **Simulations** tab of the Workstations page                                                                     |
| Amazon EKS backend for container jobs | `app.addons.useEdhWorkstations.containers.eksEnabled`                                                             | The **Amazon EKS (experimental)** backend on the **Simulations** tab                                                 |
| AMI builds                            | `app.addons.useEdhWorkstations.amiBuilds.enabled`                                                                 | The **AMI Recipes** tab of the Workstation Admin page and the **Custom AMI Recipe** images of **Launch Workstation** |
| Leases                                | The lease policy on the Workstation Admin **Settings** tab, seeded from `app.addons.useEdhWorkstations.vdi.lease` | The **Remaining** column, **Expires in (hours)** and **Renew lease**                                                 |

See [EDH Workstations](../../deployment/configuration-reference.md#edh-workstations-appaddonsuseedhworkstations) in the configuration reference for every setting. To deploy an EDH cluster and enable the add-on, an administrator follows [Enable the EDH Workstations Add-on](enable.md).

### Permissions you need

Workstation access follows the VAMS [two-tier permission model](../../user-guide/permissions.md): a web route shows a page, an API route allows an action, and a constraint on an EDH object type decides which images, instance types and job definitions that action may use.

| To                                                                                                                                            | Your role needs                                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| See **Virtual Workstations** and the Workstations page                                                                                        | Web route `/edh/workstations`                                                                                                                                                                                                                                    |
| List, launch, connect to, stop, start, renew and delete your own workstations, and show the Windows password of your own Windows workstations | `GET`, `POST` and `DELETE` on `/addon/edh/workstations`, with `edhWorkstation` constraints for the same methods                                                                                                                                                  |
| See image names, the launch catalog, the instance types and the lease policy                                                                  | `GET` on `/addon/edh/catalog`, with `edhImage` `GET` constraints for the images you may launch                                                                                                                                                                   |
| Launch into a capacity reservation                                                                                                            | `GET` on `/addon/edh/catalog`, with `edhCapacityReservation` `GET` (see it in the launch wizard) and `POST` (launch into it) constraints for each reservation; with `GET` alone the wizard shows it as `(view only)`, and without them every launch is on-demand |
| Use the **Simulations** tab                                                                                                                   | `GET`, `POST` (submit) and `DELETE` (kill) on `/addon/edh/containers`, with `edhContainer` constraints for the job definitions you may use                                                                                                                       |
| See **Admin - Workstations** and the Workstation Admin page                                                                                   | Web route `/edh/admin`, and the `/addon/edh/admin` routes each tab reads and changes, with `edhImage` and `edhWorkstation` constraints                                                                                                                           |

The side navigation checks each link's web route. **My Workstations** checks `/edh/workstations`, and **Simulations** checks the `/edh/workstations/simulations` route beneath it, so a `starts_with` constraint on `/edh/workstations` shows both; **Workstation Admin** checks `/edh/admin`.

In a deployment with the add-on, the default `basicReadOnly` role can also open the **Workstations** page, list and connect to its own workstations, and browse the image catalog, but cannot launch, stop, start, renew or delete a workstation. The default `admin` role has full access to workstations, images and container jobs. See [Default roles](../../user-guide/permissions.md#default-roles).

The **EDH User** and **EDH Admin** permission templates (`edh-user.json` and `edh-admin.json`) grant the workstation and administration rows and `GET` on the `/auth/routes` prefix, which covers the `GET /auth/routes/api/allowed` call the **Workstations** and **Workstation Admin** pages make to decide which actions to offer; neither grants the container job routes that the **Simulations** tab uses. For the templates, the constraint fields and the roles to create, see [Permissions](overview.md#permissions).

:::info[Administrator roles that require MFA]
The administrator role for the **Workstation Admin** page is created with **Require Multi-Factor Authentication** selected before the `edh-admin.json` template is imported into it (see [Roles](overview.md#roles)). Such a role applies only in a session signed in with multi-factor authentication through Amazon Cognito, so **Admin - Workstations** appears only after an MFA sign-in. See [MFA-required roles](../../user-guide/permissions.md#mfa-required-roles).
:::

:::tip[When a workstation request is refused]

-   Another user's workstation answers `404` `Workstation not found` rather than `403`, because each user reaches only their own workstations.
-   Launching or starting a workstation requires an interactive sign-in. A session authenticated with a VAMS API key, such as `vamscli` signed in with a workstation's session key, receives `403`; use the web interface or a CLI session signed in with `vamscli auth login`.
-   If the **Workstations** page opens but offers no actions, or every **Workstation Admin** tab reports `You do not have access to …`, the role lacks `GET` on `/auth/routes/api/allowed`, which these pages call to check which actions are allowed; a `GET` grant on the `/auth/routes` prefix covers it.
-   The **Simulations** tab reports `You do not have access to container jobs.` when the role cannot call `GET /addon/edh/containers/jobs` (or `GET /auth/routes/api/allowed`). With the routes but no `edhContainer` constraint, the tab lists no jobs and offers no job definitions.

:::

## How workstations work

When you launch a workstation, VAMS asks the connected EDH cluster to create a desktop for you, and the cluster starts it as an Amazon EC2 instance. When you connect, your browser opens the desktop's Amazon DCV session directly from the cluster rather than through VAMS, which is why your browser needs a network path to the cluster. The following diagram shows both paths.

![EDH Workstations add-on overview](/img/addon_edhWorkstations_overview.png)

A launch is accepted at once and runs in the background, so a new workstation appears in the list straight away and moves through its states as the cluster reports them. A start of a stopped workstation is accepted the same way: the workstation reads **Starting** at once and the list follows it until it is **Active**. Stopping a workstation stops its Amazon EC2 instance and keeps its root disk, and starting it again starts the same instance; deleting it destroys both. A start that AWS cannot carry out, for example for lack of capacity, leaves the workstation stopped with its disk and says why; it never deletes the workstation. VAMS sets each workstation so that the cluster does not start it on its own; once that setting is in place, a stopped workstation stays stopped until it is started again (see [Stopping and starting a workstation](#stopping-and-starting-a-workstation)). Where the deployment time-boxes workstations with a lease, an expired workstation is stopped and, after a grace window, removed.

```mermaid
stateDiagram-v2
    state "Start stalled" as StartStalled
    [*] --> Creating: Launch
    Creating --> Starting: cluster places the desktop
    Starting --> Active: cluster reports it running
    Creating --> Orphaned: launch refused or timed out
    Starting --> Orphaned: cluster reports an error
    Active --> Stopping: Stop, idle timer, administrator, or lease expiry
    Stopping --> Stopped: cluster reports it stopped
    Stopped --> Starting: Start, once the cluster reports it stopped (renew first if the lease expired)
    Starting --> Stopped: start refused (no capacity, reservation full or ended), disk kept
    Starting --> StartStalled: start not finished after 30 minutes
    StartStalled --> Active: cluster reports it running
    StartStalled --> Stopping: Stop
    StartStalled --> Removed: Delete
    Stopped --> Removed: grace window after lease expiry
    Active --> Removed: Delete
    Stopped --> Removed: Delete
    Orphaned --> Removed: Delete
    Creating --> Removed: Delete, 15 minutes after the last change
    Removed --> [*]
```

_Removed_ is not a status badge: a deleted workstation leaves the list at the next refresh. The status badges are:

| Badge             | Meaning                                                                                                                                                                                                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Creating**      | The launch is recorded and the cluster has not yet created a desktop for it.                                                                                                                                                                                     |
| **Starting**      | The workstation is being started: the last phase of a launch, or a stopped workstation from the moment you choose **Start** until the cluster reports it running.                                                                                                |
| **Active**        | The desktop is running, so **Connect** opens it.                                                                                                                                                                                                                 |
| **Stopping**      | The cluster is still stopping the desktop, after a stop by you, an administrator, the cluster's idle timer or the lease sweep. **Start** is offered once it has stopped.                                                                                         |
| **Start stalled** | The cluster accepted a start of a stopped workstation and has not reported it running after 30 minutes. Stop it, then start it again (see [When a start stalls](#when-a-start-stalls)).                                                                          |
| **Stopped**       | Stopped by you, by an administrator, by the cluster's idle timer, or by the lease sweep when the lease expired. A workstation whose start was refused also reads **Stopped**, with the reason beneath the badge (see [When a start fails](#when-a-start-fails)). |
| **Orphaned**      | The launch was refused or failed. The reason is shown beneath the badge; delete the workstation to clear it.                                                                                                                                                     |

Hovering over a badge shows the cluster's own state for the desktop (for example `running`), or the explanation for an orphaned or lease-expired workstation or a refused start. For the full state model, see [Session states](overview.md#session-states).

### Why a launch failed

Beneath an **Orphaned** badge, the first line explains the failure in VAMS's words (the sentences are listed under [Troubleshooting](#troubleshooting)). Where the cluster's own record of the desktop names the AWS error behind the failure, or the setup step the desktop stopped at, a second line shows it:

| Second line                                                     | What happened                                                                                                                                                                                                                          |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AWS: InsufficientInstanceCapacity (CreateCapacityReservation)` | AWS had no capacity for the instance type where the cluster tried to place the desktop. The first line reads **EDH found no available AWS capacity for the chosen instance type. Launch again later or choose another instance type.** |
| `AWS: VcpuLimitExceeded (RunInstances)`                         | The AWS account's vCPU quota for the instance family is used up. The first line reads **EDH refused the launch because a desktop, session or budget quota is used up. Delete a workstation or ask an administrator.**                  |
| `AWS: <error code>` or `AWS: <error code> (<operation>)`        | Another AWS error, named by its code and, where the cluster recorded it, the AWS operation that returned it.                                                                                                                           |
| `Desktop setup failed at <step>`                                | The cluster created the desktop, but its setup stopped at the named step.                                                                                                                                                              |

A failed launch without a second line is one for which VAMS read no such detail from the cluster. The **Sessions** tab of the Workstation Admin page shows administrators the same two lines. What to do for each is under [Troubleshooting](#troubleshooting).

## The Workstations page

The **Workstations** page (**Virtual Workstations** > **My Workstations**, `#/edh/workstations`) lists the GPU workstations you have launched on the connected EDH cluster, and each one opens in a browser tab as an Amazon DCV desktop. Where container jobs are enabled, the page shows a **Workstations** tab and a **Simulations** tab under one heading; see [The Simulations view](#the-simulations-view).

Opened in a deployment without the add-on, for example from a bookmark, the page shows "EDH Workstations is not enabled in this deployment. Ask a VAMS administrator to enable the add-on."

### The workstation list

**Launch Workstation** sits above the list when your role allows launching, beside a search box and a refresh button. The search matches a workstation's name, image name and image id, operating system, instance type, state and identifiers. The list refreshes every 20 seconds, and every 5 seconds while a workstation is being created, started or stopped; a list left open in a hidden browser tab is not refreshed until you return to it.

| Column            | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Name**          | The workstation name.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Status**        | The status badge. An orphaned or lease-expired workstation, and one whose start was refused, shows the reason beneath it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Image**         | The name of the image the workstation was launched from, with the image id beneath it: for an image built from an AMI recipe, the recipe's name and build version, such as `Isaac Sim 6.2 v13`; else the image name. The id alone shows only when neither VAMS nor the image catalog can name the image. A workstation that is active, stopped or being created and whose recipe has a newer build carries a **Newer image: v14** badge beneath the id; see [Newer image builds](#newer-image-builds).                                                                                                                                             |
| **OS**            | Linux or Windows.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Instance type** | The Amazon EC2 instance type. Beneath it, **Capacity:** names the capacity reservation the workstation was launched into (its label and id, or the id alone once an administrator has unregistered it), reads **Capacity: On-demand (reservation full)** when you chose a reservation that was full and it launched on-demand, or **Capacity: On-demand (reservation &lt;label&gt; ended)** (the id in place of the label once the reservation is unregistered) when the reservation it was launched into had ended and VAMS moved the stopped workstation to on-demand capacity to start it. An on-demand workstation shows no **Capacity** line. |
| **Created**       | When the workstation was launched, in your local time.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Remaining**     | What is left of the workstation's lease. Present only while the deployment's lease policy is enabled.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Connect**       | Opens the desktop, or shows why it cannot be opened yet.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Actions**       | The **⋮** menu: **Stop**, **Start**, **Renew lease**, **Show desktop sign-in** and **Delete**, limited to the actions your permissions allow. A dash when none apply.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

Select a column header to sort by it; the list shows 10 workstations per page. An action that does not apply to the workstation's state is shown disabled, with the reason beneath it.

The **Remaining** column counts down the lease — `in 2 d 4 h`, `in 3 h 20 min`, `in 40 min` — and turns orange in the final hour. Once the lease expires it reads, in red, `Expired, stopping`, then `Expired, removed in 20 h` while the stopped workstation waits out the grace window, then `Expired, removing`. Hovering over the value shows the expiry date and time. A workstation launched without an expiry shows a dash.

### Newer image builds

A workstation keeps the image it was launched from. When an administrator builds an AMI recipe again, a workstation launched from an older build keeps showing that build's name and version, such as `Isaac Sim 6.2 v13`, also once the older build is no longer offered in **Launch Workstation**. Stopping and starting the workstation does not move it to the newer build.

A workstation that is active, stopped or being created shows a **Newer image: v14** badge in its **Image** cell when its recipe has a newer build available. Hovering over the badge shows, and a screen reader reads with it: `This workstation runs v13 of Isaac Sim 6.2. v14 is the latest build. A workstation keeps the image it was launched from; launch a new workstation to use the latest build.` To use the newer build, launch a new workstation from it and delete the old one once you have moved your work. A workstation on the latest build, one launched from an image not built from a recipe, a deleted workstation and a failed launch show no badge.

## Launching a workstation

1. On the Workstations page, choose **Launch Workstation**. The **Launch workstation** dialog opens on the **Image** step.
2. Choose an image. The list holds the desktop images your role may launch, in two groups: **Custom AMI Recipe**, the images built from an AMI recipe, and **Baseline Image**, every other image; a group with no images is not shown. Each group is sorted by name without regard to case, with numbers in numeric order, so `Ubuntu 9` comes before `Ubuntu 22`. Each card shows the image name, its operating system, its CPU architecture (such as `x86_64` or `arm64`) when the image records one, and its description, and a **Custom AMI Recipe** image also shows the version of the build it comes from, such as `v3`. Simulation images are never offered here.
3. Choose **Next**, and complete the **Name and size** step. A field's message appears once you leave the field, and **Next** stays disabled until every field on the step is valid.

| Field                   | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Required |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| **Workstation name**    | 1-256 letters, digits, spaces, hyphens, periods or underscores. Prefilled with the image name when that name fits the rule, and follows the chosen image until you type a name of your own.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Yes      |
| **Instance type**       | The instance types the deployment allows that run the chosen image's architecture, sorted by name with numbers in numeric order, so `g5.2xlarge` comes before `g5.12xlarge`; an image that records no architecture is offered every allowed type. An image built from an AMI recipe that lists launch instance types is offered only the allowed types on that list: the Isaac Sim image is offered its GPU types only. Choosing another image clears an instance type the new image does not run or offer. Larger types carry more vCPUs and GPU memory and cost more while the workstation runs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Yes      |
| **Capacity**            | Present when an administrator has registered a capacity reservation for the chosen instance type whose platform suits the image (`Linux/UNIX` for a Linux image, `Windows` for a Windows image), and your role grants it. **On-demand** launches an ordinary instance; each reservation reads `<label> (<free>/<total> free)`. A full reservation reads `<label> (full, will launch on-demand)` when the administrator set it to fall back, and the launch then runs on-demand; one that does not fall back reads `<label> (full)` and cannot be chosen. A reservation your role may see but not launch into reads `<label> (view only)` and cannot be chosen, and the hint beneath the field says so. A reservation in an Availability Zone where the cluster has no private subnet is not listed, since the cluster cannot launch into it. The first reservation with a free slot that you may launch into is chosen for you, else **On-demand**; a view-only reservation is never chosen for you. Choosing another instance type or image lists the reservations that suit it and clears a reservation that no longer does. | No       |
| **Root disk size (GB)** | A whole number from 10 to 2048. Defaults to the chosen image's root size within those bounds, or 100 when the image records none. It cannot be smaller than the root size the image records.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Yes      |
| **Expires in (hours)**  | Present when the lease policy is enabled and an administrator has not forced the lease. A whole number from 1 to the policy's lease hours; leave it blank for a workstation with no expiry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | No       |

4. Choose **Next**. The **Review** step lists the name, image, operating system, architecture (`-` when the image records none), instance type and root disk, **Capacity** when the field was offered (the reservation's label and id, followed by `, full, will launch on-demand` for a full one, or **On-demand**) and, under a lease policy, **Expires in**: the hours you chose, `No expiry`, or the administrator's value followed by `(set by administrator)`.
5. Choose **Launch**. The dialog closes with the notification **Workstation launch requested**, and the workstation appears in the list as **Creating**.

A launch that the service refuses keeps the dialog open with **Launch failed:** and the reason on the **Review** step. Choosing **Launch** again in the same dialog never creates a second workstation, because the retry carries the same launch key. When the launch request receives no reply, the dialog closes with the notification **Launch outcome unknown**: the workstation may still be starting, so wait for the list to refresh before launching again.

A reservation that filled up after the wizard listed it, and that does not fall back, refuses the launch with **The capacity reservation has no free capacity and does not allow an on-demand launch. Choose On-demand or another reservation, or try again once a slot is free.** Go **Back**, choose **On-demand** or another reservation, and launch again. A capacity reservation is an administrator's EC2 setting that holds instances of one type for the deployment; a workstation launched into one uses a held slot while it runs and gives it back when it stops.

Where the deployment gives each Linux workstation its own VAMS sign-in for `vamscli`, a launch or a start that could not place that sign-in raises a **Workstation sign-in not provisioned** warning that stays on screen until you dismiss it. The warning says whether your account holds no roles (ask an administrator to assign one, then stop and start the workstation once it is active) or the sign-in could not be provisioned (the workstation still starts; stop and start it to try again). A lease renewal that could not replace the sign-in raises the same warning, whose text says to renew the lease again; see [The workstation's VAMS sign-in](#the-workstations-vams-sign-in). See [Session bootstrap](overview.md#session-bootstrap).

## Connecting to a workstation

**Connect** is available when the workstation is **Active**. Until then the control is inactive and shows the reason beneath it: `Available once the workstation is running.`, `Start the workstation to connect.` or `The launch did not complete.`

A workstation can also be **Active** and still not connectable, when the desktop is running but its remote display session has ended. `The workstation is running but its remote display session has ended. Stop it, then start it again, to reconnect.` then appears beneath **Connect**. VAMS notices an ended display session within about five minutes on **My Workstations**, and at once when you read the workstation with `vamscli edh workstation get` or the MCP `get_edh_workstation` tool, not only when you choose **Connect**. **Connect** stays available and checks again when chosen, so a session that was only briefly unreachable opens normally; a session that has ended answers with the same sentence in a **Connect failed** notification. Stop the workstation, then start it again: in EDH's default high-scale layout the cluster registers a desktop's display session with its Amazon DCV broker only while it places or starts the desktop, so rebooting the desktop from inside does not bring the session back.

Choosing **Connect** opens a new browser tab at once, requests the connection address, and loads the Amazon DCV desktop in that tab. The address is requested only when you choose **Connect** and is never kept in the page. If the browser blocks the new tab, a **Connect failed** notification asks you to allow pop-ups for the site and try again.

The address is the Amazon DCV connection URL that EDH returns for the desktop. It points at the EDH cluster's DCV entry point, which passes the session on to the desktop instance: in EDH's default high-scale layout, a Network Load Balancer in front of the Amazon DCV Connection Gateway, which relays the session, or, in its standard layout, the EDH Application Load Balancer. VAMS never proxies, frames or stores the desktop traffic. Your browser therefore needs a network path to that entry point: where the cluster's load balancer is internal, connect from the corporate network or over a VPN. See [Architecture](overview.md#architecture).

In EDH's default configuration that entry point presents a self-signed certificate, so the browser warns that the connection is not private before the desktop opens: accept the certificate for that host to continue or, where browser policy does not allow that, ask your administrator (see [Browser access to Amazon DCV](enable.md#browser-access-to-amazon-dcv)).

A Linux workstation needs no password and does not lock its screen, whether it is idle or not: Amazon DCV, which signs in the connection **Connect** opens, controls access to it. A Windows workstation opens at the Windows sign-in screen after each start; once you are signed in, one built from the current image does not lock while you are connected and idle. See [Signing in to the desktop](#signing-in-to-the-desktop). A workstation launched from an image built earlier can still lock; see [Troubleshooting](#troubleshooting).

### Signing in to the desktop

In the workstation's **⋮** menu, **Show desktop sign-in** shows how to sign in to that workstation's desktop. It is offered on Windows and Linux workstations alike, is available while **Connect** is, and otherwise shows the same reason beneath it. The dialog is titled **Windows sign-in** or **Linux sign-in** for the workstation.

**Linux.** No password is needed: Amazon DCV signs the session in, so **Connect** opens your desktop already signed in, and a workstation built from the current recipes does not lock its screen. The **Linux sign-in** dialog shows the **User name** the session runs as and **No password is needed.**

**Windows.** After each start the desktop opens at the Windows sign-in screen, and you sign in with the user name and password **Show desktop sign-in** shows, after **Send Ctrl + Alt + Del**. Automatic sign-in at boot is not available yet: it depends on a fix in Engineering Development Hub ([engineering-development-hub issue 164](https://github.com/awslabs/engineering-development-hub/issues/164)), and no VAMS recipe turns it on.

1. In the workstation's **⋮** menu, choose **Show desktop sign-in**.
2. The **Windows sign-in** dialog for the workstation shows the **User name** and the **Password**, masked. Choose **Copy user name** and **Copy password** to copy them, or **Show password** to read the password and **Hide password** to mask it again.
3. Choose **Close**, then **Connect**. The desktop opens in a new tab at the Windows sign-in screen; choose **Show desktop sign-in** again in the VAMS tab to read the sign-in while you type it.
4. In the Amazon DCV toolbar, open the menu under the computer name and choose **Send Ctrl + Alt + Del**. If Windows offers another account, as the first sign-in does with **Administrator**, choose your user name in the lower-left corner, then enter the password.

Once you are signed in, a workstation built from the current image does not lock while idle or when the last connection to it closes, so until you stop it the next **Connect** opens your signed-in desktop. A workstation launched from an image built before the current recipe still locks when the last connection closes; the next **Connect** then opens at the lock screen, and the same password unlocks it. After a stop and start, the desktop opens at the sign-in screen again and the same password signs in; Windows then shows the **Shutdown Event Tracker**, which **Cancel** closes. The password is requested only when you open the dialog and is dropped when you close it; it is never written to the page address or to browser storage. Where the workstation signs in with a directory account, the dialog shows the user name and **Sign in with your directory password.** in place of a password: use your own directory password.

From the command line, `vamscli edh workstation connect SESSION_ID --show-sign-in` prints the same sign-in for a Windows or a Linux workstation; see [edh workstation connect](cli-commands.md#edh-workstation-connect).

## Stopping and starting a workstation

1. In the workstation's row, open the **⋮** menu.
2. Choose **Stop** to stop an **Active** workstation, or **Start** to start a **Stopped** one the cluster has finished stopping. Neither asks for confirmation.

**Stop** stops the workstation's Amazon EC2 instance and keeps its root disk, and **Start** starts the same instance again. After **Stop**, the badge reads **Stopping** while the cluster stops the instance and until it next checks the desktop's state, which can take several minutes, then **Stopped**. Until the cluster reports it `stopped`, **Start** is disabled with the hint `The workstation is still <state>; it can be started once it has stopped.`, naming the cluster's state, for example `stopping` or `interrupted`; straight after a stop the hint can name `running` until the list is next refreshed. **Start** is accepted at once and runs in the background: the badge reads **Starting** straight away, the list refreshes every 5 seconds while it does, and the badge turns **Active** once the cluster reports the desktop running, which can take several minutes. While the badge reads **Starting**, **Start**, **Stop** and **Delete** are disabled with the hint `A start of this workstation is in progress.` A start the cluster cannot carry out leaves the workstation **Stopped** with the reason beneath the badge; see [When a start fails](#when-a-start-fails). The cluster can also stop an idle workstation on its own, at any hour: once it has been running for 2 hours, it is stopped when no client is connected to it and it is using little CPU and GPU. Unsaved work in its open applications is lost when it stops, so save before you disconnect. VAMS sets each workstation so that the cluster does not start it on its own, and a stopped workstation then stays stopped until you start it again. A workstation VAMS has not set yet, or one on a cluster that refuses the setting, can still be started by the cluster's own schedule. For the exact conditions, see [Desktop schedule](overview.md#desktop-schedule). Neither action is offered for a launch that never received a desktop. While a stop, start, lease renewal or delete of a workstation is in progress, **Stop**, **Start**, **Renew lease** and **Delete** are all disabled for it, with the hint `A start of this workstation is in progress.`, `A stop of this workstation is in progress.`, `A renew of this workstation is in progress.` or `A delete of this workstation is in progress.`

A notification confirms the request (**Workstation stop requested** or **Workstation start requested**). A request that the service refuses shows **Stop failed** or **Start failed** and a red banner above the list naming the workstation and the reason, which you dismiss with **×**. When the cluster does not confirm the request in time, the warning **Stop not confirmed** or **Start not confirmed** shows instead, without a banner, and the list is read again: the request may still be in progress, so wait for the list to show its outcome before trying again. While the cluster still reports the workstation stopped, choosing **Start** shows **Start already in progress** when another start of it is still being processed, for example from a second browser tab, when a start the cluster did not confirm was sent less than 3 minutes earlier, while VAMS is taking back the stopped workstation's sign-in key, or while a lease renewal is still replacing that key.

### When a start fails

A start that the cluster cannot carry out leaves the workstation **Stopped**. The workstation is never deleted for it: its instance and its root disk stay as they were, and you can start it again. Beneath the badge, the first line says why, and a second line names the AWS error and the Availability Zone where the cluster reported them, for example `AWS: InsufficientInstanceCapacity in us-west-2b`. Hovering over the badge shows the first line too. Both lines stay until a start of the workstation is accepted; while a new start runs, the badge reads **Starting** and they are hidden.

| First line beneath the **Stopped** badge                                                                                                                                                                                                             | What happened and what to do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AWS had no capacity for &lt;instance type&gt; in this workstation's Availability Zone (&lt;Availability Zone&gt;) when it was started. A stopped workstation keeps its disk and starts only in that zone, so it stays stopped; start it again later. | AWS had no free capacity for the instance type in the zone the workstation's disk is in, for example `g5.16xlarge` in `us-west-2b`. A stopped workstation can start only where its disk is, so it cannot move to another zone or instance type; the cluster first tries to reserve capacity there and then, in its default configuration, an ordinary on-demand start. Choose **Start** again later, when AWS has capacity again. If you need a desktop now, launch a new workstation, which may be placed in another zone, and delete this one only once you no longer need its disk. |
| The capacity reservation has no free capacity; the workstation stays stopped. Start it again once a slot is free, or ask an administrator.                                                                                                           | The workstation was launched into a capacity reservation, and every slot of it is in use. Choose **Start** again once a slot is free, or ask an administrator to free one.                                                                                                                                                                                                                                                                                                                                                                                                             |
| The capacity reservation this workstation was launched into has ended, and VAMS could not move the workstation to on-demand capacity. Ask an administrator.                                                                                          | The reservation the workstation was launched into has expired or been cancelled, and VAMS could not switch the stopped workstation to on-demand capacity, so it did not start it. The workstation and its disk are kept. Ask an administrator, with the AWS line beneath it.                                                                                                                                                                                                                                                                                                           |
| The workstation did not start; it is still stopped with its disk. Start it again, or ask an administrator.                                                                                                                                           | The cluster refused the start for another reason, or the start never took effect. Choose **Start** again; if it fails again, ask an administrator to check the cluster, with the second line where there is one.                                                                                                                                                                                                                                                                                                                                                                       |

A workstation launched into a capacity reservation gives its slot back while it is stopped, and starts again in the same reservation while the reservation lasts; VAMS does not move it to another reservation, nor to on-demand because the reservation is full. Once the reservation has ended (expired or cancelled in EC2), a start moves the stopped workstation to on-demand capacity and starts it there: the start goes ahead as usual, and the **Capacity** line then reads **Capacity: On-demand (reservation &lt;label&gt; ended)**. The workstation keeps running on-demand from then on, also after later stops and starts.

### When a start stalls

A start the cluster accepted, but has not reported running 30 minutes later, reads **Start stalled**. The cluster usually reports a started desktop running within minutes; this one stays in the cluster's `pending` state. VAMS does not stop, delete or change the workstation for it, because the cluster may still finish the start: if it does, the badge turns **Active** on its own. Beneath the badge, and when you hover over it, the workstation shows:

`EDH has not finished starting this workstation after 30 minutes. Stop it, then start it again; if it stalls again, ask your administrator.`

There is no AWS line, because the cluster reported no error. While the badge reads **Start stalled**, **Stop** and **Delete** are offered, **Start** is disabled with the hint `Only a stopped workstation can be started.`, and **Connect** is not available. To recover:

1. Choose **Stop**. The badge reads **Stopping**, then **Stopped** once the cluster has stopped the desktop.
2. Choose **Start** again.
3. If the start stalls again, ask an administrator to check the cluster. The administrator sees the same badge and sentence on the **Sessions** tab.

The list does not refresh every 5 seconds for a stalled start, because nothing changes until you act or the cluster finishes.

## Renewing a lease

**Renew lease** appears in the **⋮** menu when the lease policy is enabled and the workstation carries an expiry. Its hint states the new window, for example `Extends the lease to 8 hours from now`. The renewal sets the expiry to the policy's current lease hours counted from now, whatever length the workstation was launched with, and a notification confirms it with **Workstation lease renewed**.

A workstation the lease sweep stopped shows "The workstation's lease has expired and it was automatically stopped." beneath its badge. To use it again:

1. In the workstation's row, open the **⋮** menu and choose **Renew lease**.
2. Open the menu again and choose **Start**.

Starting it before the renewal fails with "The lease on this workstation has expired; renew it before starting". A lease-stopped workstation is deleted once the grace window has passed, so renew it before the window runs out. Administrators cannot renew another user's lease. For the sweep schedule and the grace window, see [Leases](overview.md#leases).

### The workstation's VAMS sign-in

Where the deployment gives each Linux workstation its own VAMS sign-in for `vamscli`, that sign-in lasts a fixed time from the workstation's launch or its last start: 8 hours, unless the deployment sets another length. A Windows workstation receives none; where `vamscli` is installed on it, sign it in by hand with `vamscli auth login` (see [Setup and Authentication](../../cli/commands/setup-and-auth.md)). Renewing the lease of an **Active** Linux workstation also gives it a new sign-in, which lasts as long from the renewal, and the sign-in it replaces keeps working until it expires. A Linux workstation whose image was built from a shipped recipe, such as an Amazon Linux 2023 or Isaac Sim desktop, picks the new sign-in up within about a minute. If its image was built from an earlier Isaac Sim recipe, which signs in only when the desktop session starts, run `/usr/local/bin/vams-session-bootstrap.sh` in a terminal on the workstation after the renewal; an image built from an earlier Amazon Linux 2023 recipe carries no VAMS CLI, so build the recipe again, or ask an administrator to, and launch a new workstation from the new image. A renewal that could not place a new sign-in raises the **Workstation sign-in not provisioned** warning: a sign-in the workstation still holds keeps working until it expires, and renewing the lease again tries once more. A renewal sent from the workstation's own `vamscli`, which is signed in with the workstation's sign-in, renews the lease only.

Once the sign-in has expired, `vamscli` on the workstation reports `Override token has expired`, and the Isaac Sim connector's status line reads `access refused`. To sign the workstation in again, renew its lease where it carries one. Where it does not — the deployment does not use leases, or the workstation was launched with no expiry — do either of the following:

-   **Stop the workstation, then start it.** A start gives it a new sign-in, which it signs in with when its desktop session starts.
-   **Sign in by hand** in a terminal on the workstation, as yourself:

    ```bash
    vamscli --profile "edh-$(/usr/local/bin/vams-instance-id)" auth login -u <user-id>
    vamscli --profile edh auth login -u <user-id>
    ```

    The first command signs in the workstation's own profile, which the Isaac Sim connector uses, and the second the `edh` profile terminals use. Both prompt for your password; for the other ways to sign in, see [Setup and Authentication](../../cli/commands/setup-and-auth.md). In Isaac Sim, **Authentication** in the connector window signs in the workstation's own profile as well. The workstation's next start or lease renewal replaces a sign-in made by hand.

## Deleting a workstation

1. In the workstation's row, open the **⋮** menu and choose **Delete**.
2. In the confirmation dialog, choose **Delete**.

Deleting a workstation destroys it and its root disk and cannot be undone. For a launch that never received a desktop, such as an **Orphaned** workstation, only the launch record is removed. A notification confirms the deletion with **Workstation deleted**, and the workstation leaves the list at the next refresh. A deletion the cluster does not confirm in time shows the warning **Delete not confirmed**; wait for the list to show its outcome before deleting again.

**Delete** is disabled while a launch or a start is still in progress, and while a stop, start, lease renewal or delete of the workstation you sent is still being answered, with the hint that names it (for example `A delete of this workstation is in progress.`). A launch that has no desktop yet becomes deletable 15 minutes after its last change, as the item's hint says. A workstation whose badge reads **Starting** becomes deletable once it is **Active**, once its start has failed and it reads **Stopped**, or once it reads **Start stalled**; until then **Delete** shows the hint `A start of this workstation is in progress.`

## The Simulations view

The **Simulations** view runs container jobs on the cluster. It is present when the deployment enables container jobs, as the **Simulations** tab of the Workstations page, and has a route of its own beneath the page's, `#/edh/workstations/simulations`. **Virtual Workstations** > **Simulations** opens it directly, and choosing either tab changes the address, so each tab can be bookmarked. A role that may not list container jobs sees "You do not have access to container jobs." inside the tab.

The toolbar holds the **Backend** selector — **AWS Batch** and, where the deployment enables it, **Amazon EKS (experimental)** — a refresh button and **Submit Job**. For Amazon EKS, choose a **Cluster** first; the list stays empty with "Choose a cluster to list its jobs." until you do. The list shows your jobs with their **Name**, **Job id**, **Definition** and **Status** (**Queued**, **Running**, **Succeeded** or **Failed**), and refreshes every 15 seconds.

| Field                                 | Description                                                                                                                                                                                                  | Required |

## The Workstation Admin page

The **Workstation Admin** page (**Admin - Workstations** > **Workstation Admin**, `#/edh/admin`) gives administrators a view of the whole cluster. It calls each EDH desktop a _session_ and has four tabs — **Sessions**, **Capacity**, **Images** and **Settings** — plus **AMI Recipes** between **Images** and **Settings** where the deployment enables AMI builds (`app.addons.useEdhWorkstations.amiBuilds.enabled`). The page opens on the first tab your role may read, or on **Sessions** when it may read none; the selected tab is not kept in the URL.

| Tab             | What it shows                                                                                                                                                                                                                                                                      |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Sessions**    | Every session on the cluster with its VAMS owner, the cluster's state and the reason a launch failed, and a **Stale sessions** view of sessions to reclaim, which **Stop** and **Deactivate** act on. See [Reviewing and reclaiming sessions](#reviewing-and-reclaiming-sessions). |
| **Capacity**    | The cluster's virtual desktop profiles, the total number of sessions, a count per cluster state and the number of distinct owners. See [Checking capacity](#checking-capacity).                                                                                                    |
| **Images**      | Every VDI (desktop) and simulation image registered on the cluster, which administrators register from an AMI and delete. See [Registering and deleting images](#registering-and-deleting-images).                                                                                 |
| **AMI Recipes** | The AMI recipes the deployment ships and the ones administrators define, with their builds. See [Managing AMI recipes](#managing-ami-recipes).                                                                                                                                     |
| **Settings**    | The workstation lease policy and, below it, the capacity reservations launches may target. See [Setting the lease policy](#setting-the-lease-policy) and [Registering capacity reservations](#registering-capacity-reservations).                                                  |

Each tab shows its contents only when your role may read them; otherwise it reads `You do not have access to <what>.`, for example `You do not have access to the lease policy.` While your permissions load, the tab reads `Loading permissions...`.

Where your role allows the health check, the page header shows whether VAMS can reach the cluster: `EDH <cluster id>: reachable (<n> ms)`, or a reason in red — `unreachable`, `probe refused by EDH`, or `credential rejected — re-sync the EDH root key secret`, which asks an operator to write the cluster's current root key into its secret (see [Root key rotation](overview.md#root-key-rotation)). With no answer at all, the header reads `EDH is unreachable or rejected the configured credential`. The check runs when the page opens and when you return to the browser window, unless the last answered check is less than 30 seconds old.

### Reviewing and reclaiming sessions

The **Sessions** tab lists every session on the cluster, whoever owns it, with the columns **Name**, **Session**, **EDH state**, **Owner** (the VAMS user, with the EDH user id beneath), **Status**, **Instance type** (with the **Capacity:** line beneath it, as on the Workstations page), **Created** and **Actions**. It refreshes every 20 seconds. The **Status** badge reads **Starting** for a session being started, **Stopping** for one the cluster is still stopping, **Active** as soon as the cluster reports it running, and **Deleted** for a session VAMS has recorded as deleted. A session whose start was refused shows the reason and the AWS detail line beneath its **Stopped** badge, as on the Workstations page (see [When a start fails](#when-a-start-fails)), and one whose start the cluster accepted but has not finished after 30 minutes reads **Start stalled**, with the same sentence beneath it (see [When a start stalls](#when-a-start-stalls)); **Stop** is offered for it, and the owner can start it again once it has stopped; the **EDH state** column keeps the cluster's own state. For a failed launch, the **Status** column shows the reason beneath the **Orphaned** badge and, where VAMS read it from the cluster, the AWS error or setup step on the line below, as on the Workstations page (see [Why a launch failed](#why-a-launch-failed)); the **Stale sessions** view shows them the same way. A quota error such as `AWS: VcpuLimitExceeded (RunInstances)` usually means the account's Amazon EC2 vCPU quota for the instance family needs raising.

To find sessions to reclaim, set **View** to **Stale sessions**. The view lists sessions stopped or orphaned for at least the number of minutes in **Stopped for at least (minutes)** (default 120; a new value applies when you leave the field or press Enter), stopped desktops VAMS did not launch, and sessions VAMS recorded that the cluster no longer lists. Its **Why stale** column reads **Stopped in EDH** or **Not listed by EDH**.

1. In the session's row, open the **⋮** menu and choose **Stop** or **Deactivate**.
2. Confirm in the dialog. **Stop** is confirmed with the blue button, and the owner can start the session again from the Workstations page. **Deactivate** is confirmed with the red button: the cluster deletes the desktop and its root disk, so the owner's work on it is lost.

**Stop** is not offered for a session the cluster no longer lists; deactivating such a session records it as deleted without a call to the cluster. A launch that has no desktop yet can be deactivated 15 minutes after its last change. Where each workstation has its own VAMS sign-in, both actions revoke it, and the desktop's `vamscli` stops authorizing within about 45 seconds. A stop or deactivation the cluster does not confirm in time shows the warning **Stop not confirmed** or **Deactivate not confirmed**, and the list is read again. See [Administration](overview.md#administration).

### Checking capacity

The **Capacity** tab reads the cluster live: the **Total sessions**, **Distinct owners** and **Virtual desktop profiles** counts, the sessions per EDH state, and a table of the virtual desktop profiles with their **Id**, **Name**, **Allowed instance types**, **Max root size (GB)** and **Subnets**. **Allowed instance types** groups a profile's types by architecture, such as `x86_64: g5.xlarge, g5.2xlarge · arm64: g5g.xlarge`, when the profile groups them. A registered VDI image names one of these profiles by its id. The tab has no timed refresh: it reads the cluster again when you reopen the tab or return to the browser window more than 30 seconds after the last read, or when you use the refresh button.

**Builds** lists the recipe's builds, newest first, with their **Version**, **Status**, **AMI**, **EDH stack**, **Requested** and **Completed** times. A build that becomes **Available** is registered in the EDH catalog as the recipe's stack name followed by its version (for example `Desktop v3`), appears on the **Images** tab and, for a VDI recipe, in **Launch Workstation**, and retires the recipe's other available builds. **Retry registration** retries a build whose status is **Registration failed**, and **Retire** removes an **Available** build's stack from the catalog, so no new session can be launched from it. VAMS deregisters the retired build's AMI once no desktop uses it, so existing desktops can still be started. Until then the line `AMI deregistered once no desktop uses it` appears beneath the build's status, followed by the ids of the instances that use the AMI when the last check found some. An older build whose AMI VAMS keeps for the same reason shows `AMI kept while in use: <instance ids>` there. When VAMS could not check which instances use the AMI, the red warning `in-use check failed (...)` appears beneath the status; a retired build still shows its line, without instance ids unless an earlier check found some.

**Duplicate** opens the recipe form as **Duplicate recipe**, filled in from the recipe: **Recipe id** is empty, **Display name** holds the recipe's display name followed by ` (copy)`, **Stack name** its stack name followed by ` Copy`, and every other field is copied. A recipe that installs files bundled from the repository names them above **Components** as `Bundled files from <recipe id>: <ids>`; the copy keeps those files, and they cannot be changed. Enter a recipe id, change what you need, and choose **Create recipe**. The copy is an administrator's recipe, enabled even when the recipe it copies is not, and is not built until you choose **Build now**; the tab reports **Recipe duplicated**. A duplicate the service refuses, for example because another recipe uses the stack name, reports **Duplicate failed** with the reason and keeps the form open, so give a second copy of the same recipe a stack name of its own. **Edit** on a duplicated recipe names its bundled files the same way.

Deleting an administrator's recipe removes the recipe and its build history. A recipe with a build that is queued, building or registering cannot be deleted until that build ends. Nor can a recipe with a build whose AMI VAMS has yet to remove, such as a build that shows `AMI deregistered once no desktop uses it` or `AMI kept while in use`: the delete reports **Delete failed** with `a build's AMI removal is pending`. VAMS checks such AMIs every 30 minutes and removes each one once no desktop uses it; delete the recipe again after that. The AMIs it has built and their EDH stacks are left in place. For build states and redeploy behaviour, see [AMI recipes](overview.md#ami-recipes).

### Setting the lease policy

The **Settings** tab holds the one lease policy that applies to every workstation:

| Field                     | Description                                                                                    |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| **Enabled**               | When selected, workstations are subject to time-boxed leases.                                  |
| **Lease hours**           | Hours until a workstation lease expires, from 1 to 720. Also the length a renewal grants.      |
| **Force on all launches** | When selected, every launch receives **Lease hours** and users cannot choose their own expiry. |
| **Grace hours**           | Hours a workstation stopped for an expired lease is kept before it is deleted, from 0 to 168.  |

Choose **Save** to write all four. A value out of range is reported beneath its field, and the tab shows who last changed the policy and when. A role without permission to save sees the values with "You do not have permission to save settings." A policy change does not move an expiry already set on a workstation, while a change to **Grace hours** applies at the next sweep; see [The policy](overview.md#the-policy).

### Registering capacity reservations

Below the lease policy, the **Capacity reservations** section lists the Amazon EC2 capacity reservations that workstations may launch into. It shows only when your role may read `/addon/edh/admin/capacity-reservations`, and **Register reservation**, **Edit** and **Unregister** show only when it may register, change or unregister one. With no reservation registered, the section reads "No capacity reservations are registered. Every launch is on-demand.", and every launch is an ordinary on-demand launch.

| Column                | Description                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Label**             | The name the launch wizard shows.                                                                                                                                                                                                                                                                                                                                                    |
| **Reservation**       | The EC2 capacity reservation id.                                                                                                                                                                                                                                                                                                                                                     |
| **Instance type**     | The reservation's instance type, read from EC2.                                                                                                                                                                                                                                                                                                                                      |
| **Availability Zone** | Where the reservation holds its instances.                                                                                                                                                                                                                                                                                                                                           |
| **Platform**          | The reservation's platform, such as `Linux/UNIX` or `Windows`; a Linux image launches only into `Linux/UNIX`, a Windows image only into `Windows`.                                                                                                                                                                                                                                   |
| **State**             | EC2's state, such as `active` or `expired`; **Not found in EC2** when EC2 no longer knows the id, **Unknown (EC2 read failed)** when it could not be read. Beneath it, a warning reads **No EDH subnet in &lt;Availability Zone&gt;** when the cluster has no private subnet in the reservation's Availability Zone: the cluster cannot launch into it, so users are not offered it. |
| **Free / total**      | The free and total instance slots.                                                                                                                                                                                                                                                                                                                                                   |
| **End date**          | When the reservation ends, in your local time, or **No end date**.                                                                                                                                                                                                                                                                                                                   |
| **Fallback**          | **On-demand**: a launch into the full reservation runs on-demand. **Refuse**: it is refused.                                                                                                                                                                                                                                                                                         |
| **Enabled**           | Whether the launch wizard offers the reservation.                                                                                                                                                                                                                                                                                                                                    |

To register a reservation:

1. Create the capacity reservation in Amazon EC2, in the deployment's account and Region, for an instance type the deployment allows and in an Availability Zone where the EDH cluster has a private subnet. See the EDH requirements in [Enable the add-on](enable.md).
2. Choose **Register reservation**.
3. Enter the **Capacity reservation ID** (`cr-` followed by 17 hexadecimal digits) and a **Label** of 1 to 64 letters, digits, spaces, hyphens, periods or underscores.
4. Leave **Fall back to on-demand when full** selected to let a launch into the full reservation run on-demand, or clear it to refuse such a launch. Leave **Enabled** selected to offer the reservation.
5. Choose **Register**. A reservation EC2 does not find in the account and Region is refused with `Capacity reservation not found in this account and Region` in the dialog, which stays open, and one in an Availability Zone where the cluster has no private subnet with `The capacity reservation's Availability Zone (<Availability Zone>) has no EDH private subnet, so EDH cannot launch into it`. When VAMS cannot read the cluster's private subnets, the reservation is registered and the check is made again at each launch.

**Edit** changes the label and the two switches; the id cannot change. **Unregister** asks for confirmation, then stops VAMS offering the reservation. Neither changes the reservation in EC2: it is billed until it ends or is cancelled there, whether workstations use it or not, and workstations launched into it keep running. A user sees a registered reservation only when their role grants it with an `edhCapacityReservation` constraint (the **EDH Admin** template grants every reservation, the **EDH User** template none); see [Permissions](overview.md#permissions).
