# EDH Workstations Add-on Resources

This page lists what the EDH Workstations add-on adds to a VAMS deployment when `app.addons.useEdhWorkstations.enabled` is `true`: the AWS resources it deploys or creates at runtime, its data model, its network placement and paths, its security controls, the AWS WAF exemption on its AMI recipe routes, its costs and its limits. [EDH Workstations Add-on](overview.md) describes how the add-on works, [Uninstall the EDH Workstations Add-on](uninstall.md) removes what it leaves behind, and the [AWS Resources Inventory](../../architecture/aws-resources.md) lists the resources of the core deployment.

### Amazon DynamoDB tables

The add-on keeps its records in two Amazon DynamoDB tables, which its nested stack creates. They are encrypted like the core tables — with the deployment's customer managed key when `app.useKmsCmkEncryption.enabled` is `true`, otherwise with the AWS managed key — and, like every VAMS table, they use a `RETAIN` removal policy and carry no custom name, so they survive `cdk destroy` and never block a redeploy. The add-on publishes their names as [AWS Systems Manager parameters](#aws-systems-manager-parameters), and [Data model](#data-model) describes their schemas.

| Table                    | Partition Key (PK) | Sort Key (SK) | GSIs                                                                          | Purpose                                                                                                                                                                                                                                 |
| ------------------------ | ------------------ | ------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EdhSessionStorageTable   | `bootstrapId`      | --            | `sessionUuidIndex` (PK: sessionId), `userIdIndex` (PK: userId, SK: createdAt) | EDH workstation session records: launch idempotency, ownership, and lifecycle state; the one table with a TTL attribute (`expiresAt`, set on `DELETED` rows that hold no credential, seven days ahead)                                  |
| EdhAmiRecipeStorageTable | `pk`               | `sk`          | `imageBuildArnIndex` (PK: imageBuildVersionArn)                               | EDH AMI recipes (`RECIPE#<recipeId>` / `RECIPE`) and their builds (`RECIPE#<recipeId>` / `BUILD#<version>`): content hash, Image Builder ARNs, build status, AMI id, registered EDH stack. Retained on stack deletion like every table. |

### AWS Lambda functions

`infra/lib/nestedStacks/addon/edhWorkstations/lambdaBuilder/edhWorkstationsFunctions.ts` builds the add-on's functions: `edhWorkstationService`, `edhAdminService`, `edhContainerService` (when `containers.enabled`), `edhLaunchWorker` (asynchronous launch; retried twice within 20 minutes), `edhCatalogRegistration` (deploy-time custom resource), `edhSessionReconciler` (every 15 minutes; enforces expired workstation leases, reconciles state and revokes credentials with or without `sessionBootstrap.enabled`), and `edhAmiRecipeService` and `edhAmiBuildRegistrar` (when `amiBuilds.enabled`). Every function runs in the VPC's isolated subnets behind the [add-on security group](#edh-add-on-lambda-security-group), with a 29-second timeout on the four API-facing functions, 5 minutes on the launch worker and 15 minutes on the registration, reconciler and AMI build registrar functions. [Lambda functions](overview.md#lambda-functions) describes what each one does.

The add-on also deploys these deploy-time helper functions:

| Function                                                                                                                        | Purpose                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EDH catalog registration provider (CDK-managed Node.js runtime)                                                                 | Custom resource provider framework of the `EdhCatalogRegistration` resource, which invokes the in-VPC `edhCatalogRegistration` function on every deployment. Runs outside the VPC with 128 MB memory (when `app.addons.useEdhWorkstations.enabled`)                                                                         |
| EDH image build trigger `BuildTrigger-Edh-<name>` (inline Python 3.12) and its provider framework (CDK-managed Node.js runtime) | One pair per `containers.buildAndPushImages[]` entry, backing the `BuildTriggerCR-Edh-<name>` custom resource that starts the image's AWS CodeBuild build. Both run outside the VPC with 128 MB memory; the trigger has a 1-minute timeout and holds only `codebuild:StartBuild` on its project (when `containers.enabled`) |
| EDH recipe bundle deployment (`Custom::CDKBucketDeployment`, CDK-managed Python runtime)                                        | Uploads each seeded AMI recipe directory and declared asset tree to the artefacts bucket under `addon/edh/amiRecipes/`. Runs outside the VPC, with 128 MB memory for the recipe directories and 1024 MB for the asset trees (when `amiBuilds.enabled`)                                                                      |

The `EdhCatalogRegistration` resource re-runs on every deployment, and each `BuildTriggerCR-Edh-<name>` resource re-runs when its project name, source hash or repository URI changes. Neither acts on stack deletion, so the EDH software stacks and AWS Batch job definitions the registration created outlive the stack — see [Pre-uninstall steps](uninstall.md#pre-uninstall-steps).

### Amazon CloudWatch log groups

:::warning[AWS CodeBuild and EC2 Image Builder log groups are service-created and never expire]
The AWS CodeBuild projects and the EC2 Image Builder infrastructure configurations declare no logging
configuration, so each service writes to its default group on first use: AWS CodeBuild to
`/aws/codebuild/<project name>` for every [image build](#aws-codebuild), and EC2 Image Builder to
`/aws/imagebuilder/<prefix>-<recipeId>` for every [AMI recipe](#ec2-image-builder) that builds. Neither
group is a stack resource, so the retention aspect never visits it, its retention stays at **never
expire**, and `cdk destroy` leaves it in place. The CodeBuild project names are generated by AWS
CloudFormation and do not carry the stack name, so the `/aws/lambda/$STACK` script of [Amazon
CloudWatch](../../architecture/aws-resources.md#amazon-cloudwatch) does not reach these groups. Set their
retention by selecting the deployment's projects by the `vams:stackname` tag and the recipe groups by the
lower-cased EDH prefix:

```bash
STACK=<name>-core-<baseStackName>
EDH_PREFIX=$(echo "<name>-<baseStackName>-edh" | tr '[:upper:]' '[:lower:]')
{
  aws resourcegroupstaggingapi get-resources --tag-filters "Key=vams:stackname,Values=$STACK" \
    --resource-type-filters codebuild:project --query "ResourceTagMappingList[].ResourceARN" \
    --output text | tr '\t' '\n' | sed 's|.*:project/|/aws/codebuild/|'
  aws logs describe-log-groups --log-group-name-prefix "/aws/imagebuilder/$EDH_PREFIX-" \
    --query "logGroups[].logGroupName" --output text | tr '\t' '\n'
} | while read -r g; do
    [ -n "$g" ] && aws logs put-retention-policy --log-group-name "$g" --retention-in-days 365
  done
```

A project that has not built yet has no group, and `put-retention-policy` reports it as not found.
:::

### AWS Secrets Manager

The add-on reads two operator-managed secrets and, with session bootstrap, creates one secret for each launched Linux desktop:

| Resource                 | Created when                                                                   | Removal on teardown                                                                                 | Custom name (redeploy collision)                                                     | Purpose                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **EDH root key secret**  | Referenced by `app.addons.useEdhWorkstations.edhAdminApiKeySecretArn`          | Not a stack resource — operator-managed, untouched by `cdk destroy`                                 | Operator's choice                                                                    | `{ "rootKey": "..." }`; read by the add-on Lambda functions, cached one hour, re-read on `401`. EDH regenerates the key each time its web interface starts, including after every controller reboot, so the operator re-publishes it into this secret each time |
| **EDH CA bundle secret** | Referenced by `edhApiCaBundleSecretArn` when set                               | Not a stack resource — operator-managed                                                             | Operator's choice                                                                    | PEM bundle that verifies the EDH ALB certificate (the self-signed certificate or the private CA that issued it)                                                                                                                                                 |
| **EDH session secrets**  | `sessionBootstrap.enabled`, one per launched Linux desktop, created at runtime | Not stack resources: removed by the add-on when the desktop is deleted or found orphaned; see below | Yes — `<secretNamePrefix><bootstrapId>`, `vams/edh-session/<bootstrapId>` by default | Per-session VAMS API key for the desktop's `vamscli`, encrypted under the `EdhSessionSecretsKey` (see [AWS KMS key](#aws-kms-key))                                                                                                                              |

A session secret is created before the EDH desktop is requested, without a read grant; once the desktop is correlated, its resource policy lets the roles in `sessionBootstrap.workstationInstanceRoleArns` read it only from that desktop's EC2 instance (the policy names each role's `assumed-role/<role name>/<instance id>` session, leaving out a listed role AWS Secrets Manager cannot resolve; the binding fails only when none resolves), and a start, or a renewal that creates the secret, applies the binding. Stopping the desktop revokes every key of the desktop and overwrites the secret's value with `{ "revoked": true }` while keeping the secret, so the pointer on the instance survives a start; deleting the desktop, an administrator's deactivation, or the reconciler finding it gone from EDH, revokes every key of the desktop and deletes the secret without a recovery window. Because the secrets are created at runtime, `cdk destroy` does not remove those still present for desktops that were running; [Remove EDH session secrets](uninstall.md#remove-edh-session-secrets) lists and removes them by prefix. The names are deterministic per `bootstrapId`, so a secret left behind cannot collide with a later deployment's: every `bootstrapId` is a fresh UUID.

### AWS KMS key

| Resource                    | Created when                                                                                            | Removal on teardown                 | Custom name (redeploy collision) | Purpose                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------- |
| **EDH session secrets key** | `app.addons.useEdhWorkstations.sessionBootstrap.enabled = true`, independently of `useKmsCmkEncryption` | Destroyed (30-day pending deletion) | No (no alias, generated key id)  | Customer-managed key for the per-session credentials of the EDH Workstations add-on |

The EDH session secrets key (`EdhSessionSecretsKey`, in the `EdhWorkstationsBuilderNestedStack` nested stack) is deployed when `app.addons.useEdhWorkstations.sessionBootstrap.enabled` is `true`, independently of `useKmsCmkEncryption`. It encrypts only the AWS Secrets Manager secrets the add-on creates at each workstation launch and removes on delete, so it uses a `DESTROY` removal policy: `cdk destroy` schedules it for deletion and it is gone after the 30-day pending window, with nothing left that was encrypted under it. Its key policy grants `kms:Decrypt` and `kms:DescribeKey` to the roles in `sessionBootstrap.workstationInstanceRoleArns` for requests made through Secrets Manager against secrets under `sessionBootstrap.secretNamePrefix`.

### AWS Batch job definitions

The containers feature registers the job definitions of `containers.jobDefinitions` with AWS Batch through its catalog registration function rather than through AWS CloudFormation. They are not stack resources: each is tagged `edh:visibility:<edhClusterId>=true` — the tag EDH lists job definitions by, and the only tag VAMS writes on them — and registering a changed entry deregisters every earlier revision of the same name that carries the tag. An entry removed from `containers.jobDefinitions` stays registered, and `cdk destroy` leaves every one registered — [Deregister EDH job definitions](uninstall.md#deregister-edh-job-definitions) deregisters them by name.

### Amazon ECR repositories

The containers feature (`app.addons.useEdhWorkstations.containers.enabled`) creates one Amazon ECR repository per `containers.buildAndPushImages[]` entry, named `{config.name}-{app.baseStackName}-edh-{name}` (lower-cased; `-kms` is appended when `app.useKmsCmkEncryption.enabled` is `true`) and tagged `edh:visibility:{edhClusterId}=true` so the EDH cluster lists it. Like the pipeline repositories of [Amazon Elastic Container Registry](../../architecture/aws-resources.md#amazon-elastic-container-registry), each scans images on push, retains the last 10 images and uses the `DESTROY` removal policy with `emptyOnDelete`; its [AWS CodeBuild](#aws-codebuild) project pushes the image under a content-addressed tag plus a mutable `latest` alias that seeds the next build's layer cache. These repositories are explicitly named and therefore redeploy-collision relevant. When `containers.imagePullRoleArns` lists the Amazon ECS container instance role of EDH's AWS Batch compute environment, each repository carries a resource policy granting that role `ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer` and `ecr:BatchCheckLayerAvailability`; with the list empty no repository policy is attached and the role pulls on its own identity policy. Like the pipeline repositories, they are encrypted at rest with the VAMS KMS key when `app.useKmsCmkEncryption.enabled` is `true`, and with Amazon ECR's default AES-256 otherwise. Amazon ECR holds its own grant on the key, so neither the build project nor the pull roles need a key permission. A repository's encryption cannot change, so turning the CMK on or off replaces each repository under the other name and starts a build of its image; job definitions registered before that build finishes name an image that is not yet pushed.

### EC2 Image Builder

The AMI builds feature (`app.addons.useEdhWorkstations.amiBuilds.enabled`) creates the EC2 Image Builder objects of each AMI recipe at runtime, from the recipe's content, rather than through AWS CloudFormation. They are not stack resources, so `cdk destroy` leaves them in place — see [Remove EDH AMIs](uninstall.md#remove-edh-amis).

| Object                                                                                                 | Name                                                                                                 | Notes                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Image pipeline**, **image recipe**, **infrastructure configuration**, **distribution configuration** | `{config.name}-{app.baseStackName}-edh-{recipeId}` (lower-cased)                                     | One of each per recipe. The image recipe takes one version per distinct recipe content and parent AMI and sizes a `gp3` root volume deleted on termination; the infrastructure configuration offers the recipe's build instance types, requires IMDSv2 on the build instance with a hop limit of 2, and terminates the build instance on failure as well as on success |
| **Component**                                                                                          | `{config.name}-{app.baseStackName}-edh-{recipeId}-cNN-{slug}` (lower-cased)                          | One per inline component document a recipe defines, versioned from the recipe content; the managed components a recipe references by ARN are not account-owned                                                                                                                                                                                                         |
| **Image**                                                                                              | Named for its image recipe                                                                           | One image build version per build. Deleted with the AMI when an administrator retires the build or pruning removes it                                                                                                                                                                                                                                                  |
| **AMI** and its **Amazon EBS snapshots**                                                               | `{config.name}-{app.baseStackName}-edh-{recipeId}-{{ imagebuilder:buildDate }}` (lower-cased prefix) | Owned by the account. VAMS keeps the recipe's `keepVersions` newest builds that hold an AMI (default `amiBuilds.keepVersionsDefault`, itself 3 by default) and deregisters the AMI and snapshots of older retired or failed builds, and of a build an administrator retires, once no Amazon EC2 instance uses the AMI                                                  |

The components, image recipes, infrastructure and distribution configurations, pipelines, AMIs and snapshots carry three tags: `vams:edhAmiRecipe=<recipeId>`, `vams:edhAmiRecipeHash=<contentHash>` and `vams:deployment=<prefix>`, where the prefix is `{config.name}-{app.baseStackName}-edh` lower-cased. The AMIs and snapshots also carry `edh:visibility:<edhClusterId>=true`, which records the cluster they were built for; EDH offers an image through the software stack registered for it. Select a deployment's objects by `vams:deployment` rather than by `vams:edhAmiRecipe`: the recipe tag is common to every VAMS deployment in the account and Region.

The add-on stack holds the resources the builds run with:

-   **`EdhAmiBuildInstanceRole`** and **`EdhAmiBuildInstanceProfile`** — the build instance's identity. The role is assumed by Amazon EC2, carries the two AWS managed policies EC2 Image Builder documents for a build instance, `EC2InstanceProfileForImageBuilder` and `AmazonSSMManagedInstanceCore`, and reads the artefacts bucket's `addon/edh/amiRecipes/` prefix, from which the recipe components fetch their asset trees.
-   **EDH AMI build security group** — egress only; see [EDH AMI build security group](#edh-ami-build-security-group).
-   **Recipe bundles** — each seeded recipe's directory and declared asset trees, uploaded to the artefacts bucket under `addon/edh/amiRecipes/<bundleHash>/<recipeId>/`. The uploads never prune, and the bucket's root deployment excludes `addon/`, so the bundles of every hash a deployment has produced are retained with the bucket; see [Recipe bundles in the artefacts bucket](#recipe-bundles-in-the-artefacts-bucket).

The role, the instance profile and the security group are deleted with the stack; the recipe bundles are retained with the artefacts bucket.

EC2 Image Builder writes each build's output to `/aws/imagebuilder/<prefix>-<recipeId>`, a log group it creates itself (see [Amazon CloudWatch log groups](#amazon-cloudwatch-log-groups)). It also creates the service-linked role `AWSServiceRoleForImageBuilder` the first time the add-on uses EC2 Image Builder in an account that does not have it yet, which is why the AMI build functions hold `iam:CreateServiceLinkedRole` for that service alone. The role is account-wide rather than a stack resource: `cdk destroy` does not remove it, and any other EC2 Image Builder user in the account shares it.

## Data model

The add-on's two tables are listed under [Amazon DynamoDB tables](#amazon-dynamodb-tables); [Data Model](../../architecture/data-model.md) describes the core tables.

### EDH Session Storage Table

Records EDH workstation sessions launched through VAMS, one row per launch. The partition key is the client-generated `bootstrapId`, which is also the launch idempotency key: a repeated create with the same `bootstrapId` resolves to the existing row.

| Attribute     | Type   | Key           |
| ------------- | ------ | ------------- |
| `bootstrapId` | String | Partition Key |

Each record carries `sessionId` (the EDH session id, absent until EDH has returned it), `userId` (the normalized VAMS user id of the owner), `edhUid` (the derived EDH directory id), `state` (`CREATING`, `ACTIVE`, `STOPPED`, `DELETED`, `ORPHANED`), `edhState` (the raw EDH session state string), `name`, `imageId`, `osFamily`, `instanceType`, `rootSizeGb`, `createdAt`, `updatedAt`, `connectionAvailable` (`true` while EDH reports the desktop `running`; set from EDH's state by every read of the desktop, a reconciler sweep included, and cleared by a stop, an administrative stop or a deactivation), `launchAttempts` (the number of launch-worker starts for the row) and `lastError` (the failure code of an `ORPHANED` launch, or `LEASE_EXPIRED` on a workstation the lease sweep stopped; absent or `null` otherwise). A row whose launch carried a lease also records `leaseExpiresAt` (the instant the lease runs out), `leaseHoursAtLaunch` (the hours it was launched with) and, once the lease sweep has stopped the desktop, `leaseStoppedAt` (the instant it did, from which the grace window runs; cleared by a renewal or a start). Once EDH lists the desktop's EC2 instance the row also records `instanceId`. Once the desktop's EDH schedule is set to stopped all day on every day, by the launch worker or by a later reconciler sweep, the row records `scheduleAppliedAt` (when VAMS set the schedule or found it already set; a reconciler sweep records the time the sweep began, and leaves `updatedAt` as it was), and neither sets the schedule again while the attribute is present. Every start claims the row before its session key is minted by writing `startRequestedAt` (the instant of the claim) conditionally, and the write is refused while another start's value is less than 3 minutes old or a renewal's `credentialClaimedAt` is less than 5 minutes old. The value holds off another start, and the reconciler's revoke of the stopped desktop's key, for 3 minutes while EDH still lists the desktop stopped. The reconciler writes it too when it claims a row it records `STOPPED` to revoke its key, unless a start's claim already holds it, and removes its own value at once when the revoke fails or another write overtakes the clear; a value a sweep that ends part-way through the revoke leaves ages out after 3 minutes. A start that did not happen clears it and one whose outcome EDH did not confirm keeps it; any read that finds the desktop past `stopped` (the workstation routes, the reconciler, the launch worker), a start or stop EDH carries out, an administrative stop or deactivation, and the reconciler once it has revoked the key clear it. A renewal that re-issues the session key of an `ACTIVE` row claims the row first by writing `credentialClaimedAt` (the instant of the claim) conditionally, and the write is refused while another claim is less than 5 minutes old or a start's `startRequestedAt` is less than 3 minutes old. The renewal keeps the claim while it names the new key on the row and writes the secret, and removes it when it is done. While the value is less than 5 minutes old the reconciler revokes nothing on the row and a start is refused; the reconciler also writes it whenever it claims a row to revoke its key, and removes it with the credential, or on its own at once when the revoke fails or another write overtakes the clear; a value a failed request, or a sweep that ends part-way through its revoke, leaves ages out after 5 minutes. Rows written with session bootstrap enabled also carry `apiKeyId` and `keyExpiresAt` (the session key minted last for the desktop), `secretArn`, `secretName` and `secretBoundInstanceId` (empty until the secret is bound to the desktop's instance). No attribute records the keys a renewal replaced: a session key belongs to the row whose `bootstrapId` its name carries. The API projection drops `instanceId`, `startRequestedAt`, `scheduleAppliedAt`, `credentialClaimedAt` and these five. A row that enters `DELETED` with no credential left on it — a delete, an administrative deactivation, or the reconciler recording a desktop EDH no longer lists — is stamped with `expiresAt` (Number, epoch seconds, seven days ahead), the table's DynamoDB TTL attribute, so DynamoDB removes it about a week later; a deleted launch the reconciler re-adopts loses the attribute. The table has no stream.

**Global Secondary Indexes:**

| GSI Name           | Partition Key | Sort Key    | Projection |
| ------------------ | ------------- | ----------- | ---------- |
| `sessionUuidIndex` | `sessionId`   | --          | ALL        |
| `userIdIndex`      | `userId`      | `createdAt` | ALL        |

`sessionUuidIndex` is sparse: a row without a `sessionId` is absent from the index, so a `CREATING` row is reachable only by `bootstrapId` or through `userIdIndex` until EDH has returned the session id.

The table also holds one row that is not a session: the workstation lease policy, under the reserved partition-key value `SETTINGS#lease`. The literal cannot collide with a session row, whose key is always a 36-character UUID, and the row carries no `state`, so the state-filtered scans that read session rows never yield it. It is written once at deployment from `app.addons.useEdhWorkstations.vdi.lease` if no such row exists, and by `PUT /addon/edh/admin/settings` thereafter; it carries `enabled`, `leaseHours`, `forced`, `graceHours`, `updatedAt` and `updatedBy`.

### EDH AMI Recipe Storage Table

Records the AMI recipes of the EDH Workstations add-on and their builds, one partition per recipe. The recipe row and every build row share the partition key `RECIPE#<recipeId>`; the sort key tells them apart, and the build version is zero-padded to six digits so a query on the partition lists builds in version order.

| Attribute | Type   | Key           |
| --------- | ------ | ------------- |
| `pk`      | String | Partition Key |
| `sk`      | String | Sort Key      |

| Row    | `pk`                | `sk`                               |
| ------ | ------------------- | ---------------------------------- |
| Recipe | `RECIPE#<recipeId>` | `RECIPE`                           |
| Build  | `RECIPE#<recipeId>` | `BUILD#<version>` (`BUILD#000001`) |

A recipe row carries the recipe definition — `recipeId`, `displayName`, `kind` (`vdi` or `simulation`), `osFamily`, `baseOs` (`vdi` recipes only), `architecture`, `parentImage`, `buildInstanceType`, `rootSizeGb`, `stackName`, `profileId`, `components` (each an Image Builder component `arn` or an inline `name` and `data` document), `assets` and `assetPrefix` (recipes seeded from the configuration, and `admin` recipes duplicated from any recipe that holds them, which keep the source's), `parameters`, `keepVersions`, `recipeRevision`, `description` and `enabled` — together with `source` (`config` for a recipe seeded from the configuration at deployment, `admin` for one created through the API, from the **AMI Recipes** tab or the CLI), `duplicatedFrom` (the id of the recipe an `admin` recipe was duplicated from; see [Duplicating a recipe](overview.md#duplicating-a-recipe)), `buildOnDeploy`, `contentHash` (see [Content hash and versions](overview.md#content-hash-and-versions)), `latestVersion`, `createdAt`, `updatedAt`, `createdBy` and `updatedBy`, and `deletingAt` while a delete runs (the instant it marked the recipe; a mark older than 30 minutes, from a delete that did not finish, holds nothing off). A recipe is created only where its id is free, and replaced only while its `updatedAt` is the one the writer read. Its `imageBuilder` map records the EC2 Image Builder objects of the latest build: `componentArns`, `recipeArn`, `recipeVersion`, `infrastructureConfigurationArn`, `distributionConfigurationArn`, `pipelineArn` and `buildKey`. A `config` recipe removed from the configuration stays in the table with `enabled` set to `false`.

A build row carries `recipeId`, `version` (Number), `status` (`QUEUED`, `BUILDING`, `REGISTERING`, `AVAILABLE`, `REGISTER_FAILED`, `FAILED`, `RETIRED`; see [Builds](overview.md#builds)), `contentHash`, `requestedBy` (the requesting VAMS user id, or `deploy`), `requestedAt`, `startedAt`, `imageBuildVersionArn`, `resolvedParentAmi` and `buildKey`. A request claims a new version by writing its row only where none exists, and a promotion claims a `QUEUED` row by moving it to `BUILDING`; a claimed row whose pipeline has not started is `BUILDING` with `claimedAt` and no `imageBuildVersionArn`. The row written when the pipeline starts drops `claimedAt`, which stays on a build that went back to `QUEUED` or failed with `launch did not complete`. Once the image reports an AMI the row also records `amiId`, `snapshotIds` and `completedAt`; registration adds `edhStackName`, `edhStackId`, `edhKind`, `registeredAt` and `registerAttempts`; retirement and pruning add `retiredAt`, `amiDeregisteredAt`, `retireWarning` and `pruneWarning`. An AMI kept because an Amazon EC2 instance uses it adds `amiInUseBy` (List of up to 20 instance ids), and a build an administrator retired carries `amiRemovalPending` (Boolean `true`) until its AMI is deregistered; a deregistration removes both, together with `pruneWarning`. A recipe row always carries `updatedAt`; a build row gains it on its first update. `error` holds the reason of a failed or partially completed step, `launch did not complete` on a claimed build the sweep failed because its pipeline start was never recorded. The API projection drops `pk` and `sk`.

**Global Secondary Indexes:**

| GSI Name             | Partition Key          | Sort Key | Projection |
| -------------------- | ---------------------- | -------- | ---------- |
| `imageBuildArnIndex` | `imageBuildVersionArn` | --       | ALL        |

`imageBuildArnIndex` is sparse: only a build row that has started an Image Builder pipeline carries `imageBuildVersionArn`, so recipe rows, `QUEUED` builds and a claimed build whose pipeline has not started are absent from it. The build registrar uses it to find the row an Image Builder state-change event refers to. The table has no stream and no TTL attribute.

### Recipe bundles in the artefacts bucket

With AMI builds enabled, the add-on stack uploads its recipe bundles to the deployment's [artefacts bucket](../../architecture/data-model.md#artefacts-bucket), under a prefix of their own:

```text
addon/edh/amiRecipes/{bundleHash}/{recipeId}/recipe.json and component files
addon/edh/amiRecipes/{bundleHash}/{recipeId}/assets/{assetId}/{asset tree}
```

Where:

-   `addon/edh/amiRecipes/` holds the seeded AMI recipe directories of the EDH Workstations add-on — the shipped ones under `backendAddons/edh/amiRecipes/` (with `amiBuilds.includeShippedRecipes`) and any `predefinedImages.amiRecipes[].recipeDir` — and the repository trees each recipe declares as assets, uploaded when `app.addons.useEdhWorkstations.amiBuilds.enabled` is `true`
-   `bundleHash` is the first 16 hexadecimal characters of a SHA-256 digest over every seeded recipe directory and asset tree, so identical content reaches the same keys and changed content moves them; text files are read with CRLF folded to LF (a file whose first 8 KiB hold a NUL byte is read as is), the rule CDK applies to its asset hash, so a Windows and a Linux checkout of the same content reach the same keys

The upload of `infra/lib/artefacts/` owns the bucket root and prunes any object absent from that directory, but excludes `addon/`, the prefix the add-on stacks upload under, as it does the pipeline registration prefix `vamsSchema/`; each recipe and asset upload runs with pruning disabled, so the bundles of every hash a deployment has produced remain in the bucket until it is emptied. Two readers use `addon/edh/amiRecipes/`: the EDH AMI build instance role, whose components fetch the asset trees during a build, and the EDH catalog registration Lambda, which reads the recipe directories back at deployment to seed the [EDH AMI Recipe Storage Table](#edh-ami-recipe-storage-table).

## Network

![EDH Workstations add-on network topology](/img/addon_edhWorkstations_network.png)

The diagram shows where the EDH Workstations add-on's resources sit in the network: the handler functions and VPC endpoints in the isolated subnets, the AMI build instance in its build subnet, the route to the EDH Application Load Balancer (EDH web UI and REST API) in the same or a connected VPC, and the browser's Amazon DCV path, which passes through no VAMS function, endpoint or load balancer. The DCV path is drawn as EDH's default high-scale layout: a Network Load Balancer in front of the Amazon DCV Connection Gateway, which relays the session to the Amazon EC2 desktops that EDH launches, each from its own AWS CloudFormation stack, into the cluster's private subnets. In EDH's standard layout, the EDH Application Load Balancer is the DCV entry point instead. The container image builds run in AWS CodeBuild outside the VPC.

### Placement

The EDH Workstations add-on places its handler Lambda functions in the isolated subnets whenever `app.addons.useEdhWorkstations.enabled` is `true`, independently of `useForAllLambdas`, because they call the EDH REST API on the EDH cluster's Application Load Balancer. With an internal load balancer that the VPC routes to, the add-on's management path needs no internet egress. An internet-facing load balancer needs a NAT route from the subnets the functions run in, and AMI builds from the shipped recipes need a build subnet with outbound internet access; the diagram above shows the topology. The topologies the add-on is exercised in are listed under [Current limitations](overview.md#current-limitations).

### Network paths

The EDH Workstations add-on (`app.addons.useEdhWorkstations.enabled`) calls the EDH REST API on the EDH cluster's Application Load Balancer over HTTPS (TCP 443, or the port `edhApiEndpoint` names) from the isolated subnets, behind its own [security group](#edh-add-on-lambda-security-group). VAMS does not constrain the load balancer's scheme. An internal load balancer is reached through the VPC's own routing: the EDH cluster shares the VAMS VPC, or the operator connects the two VPCs with peering or a transit gateway and resolves the load balancer's private name from the VAMS VPC. An internet-facing load balancer resolves to public addresses, so the subnets VAMS places the functions in need a NAT route — for example an imported VPC whose `optionalExternalIsolatedSubnetIds` name subnets with a NAT gateway route, as in the [shared-VPC layout](enable.md#step-4-connect-the-networks).

With `useGlobalVpc.addVpcEndpoints = true`, the endpoints of [VPC Endpoints](../../architecture/networking.md#vpc-endpoints) carry the add-on's AWS calls: the AWS Secrets Manager endpoint carries the reads of the EDH root key and the optional CA bundle as well as the calls that create, bind, overwrite and delete the per-session secrets, the common interface endpoints cover AWS Lambda, AWS Systems Manager and Amazon CloudWatch Logs, and the gateway endpoints carry Amazon DynamoDB and Amazon S3 traffic. The containers feature adds the AWS Batch interface endpoint (when no container pipeline already creates it) for the job definitions the add-on registers; AWS CodeBuild builds the container images outside the VPC and EDH compute pulls them, so no Amazon ECR endpoint is created. The AMI builds feature (`app.addons.useEdhWorkstations.amiBuilds.enabled`) adds the EC2 Image Builder and Amazon EC2 endpoints its recipe and build registration functions call, and the AWS Systems Manager Messages and Amazon EC2 Messages endpoints the build instance's Systems Manager agent needs. With `addVpcEndpoints = false`, VAMS creates none of these endpoints and the operator's VPC provides the same paths.

The AMI build instance launches in `amiBuilds.buildSubnetId`, or in the first private subnet, or in the first isolated subnet when the VPC has no private subnet, behind the [AMI build security group](#edh-ami-build-security-group). The shipped recipes download operating-system updates through the AWS-managed `update-linux` or `update-windows` component, and the Linux recipes (`al2023-desktop`, `isaacsim`) also download packages, so the build subnet needs outbound internet access. A VPC that VAMS creates has private subnets and NAT gateways only for the features listed under [VAMS-Managed VPC Configuration](../../architecture/networking.md#vams-managed-vpc-configuration), and the add-on is not one of them, so set `amiBuilds.buildSubnetId` to a subnet with a NAT route, or import a VPC and name a NAT-routed subnet first in `optionalExternalPrivateSubnetIds` (or in `optionalExternalIsolatedSubnetIds` when no private subnets are named), as the [shared-VPC layout](enable.md#step-4-connect-the-networks) does. Every build instance downloads the EC2 Image Builder component manager, AWS Task Orchestrator and Executor (AWSTOE), from Amazon S3, and when a recipe declares asset trees, as the shipped `al2023-desktop` and `isaacsim` recipes do, the build instance also fetches them from the artefacts bucket's `addon/edh/amiRecipes/` prefix; both go through the gateway endpoint from an isolated subnet or through the NAT gateway from a private one, because the gateway endpoints are associated with the isolated subnets only. The build's logs go to Amazon CloudWatch Logs under `/aws/imagebuilder/`, which the CloudWatch Logs interface endpoint carries from inside the VPC.

The desktop path is separate: the browser opens the Amazon DCV connection URL that EDH returns, which points at the EDH cluster's DCV entry point (see [How VAMS integrates with EDH](overview.md#how-vams-integrates-with-edh)). VAMS creates no route, endpoint or Content Security Policy source for that traffic, so the user's browser needs its own network path to the entry point; with an internal EDH load balancer, users reach it over the corporate network or a VPN.

With `app.useGlobalVpc.addVpcEndpoints = true`, the add-on's features add these interface endpoints to the endpoints of [VPC Endpoints](../../architecture/networking.md#vpc-endpoints), which carry the rest of the add-on's AWS calls. With `addVpcEndpoints = false`, VAMS creates none of them, and the operator's VPC provides the same paths.

### EDH add-on Lambda security group

When the EDH Workstations add-on is enabled, its handler Lambda functions are attached to a dedicated security group, `EdhAddonLambdaSecurityGroup`, rather than to the default per-function group the other in-VPC Lambda functions receive. The deployment-time helper functions — the custom-resource provider framework, the container image-build triggers and the recipe bundle uploads — run outside the VPC; the catalog registration handler that the provider invokes runs inside it.

| Direction | Protocol | Port                  | Destination | Purpose                                                                                  |
| --------- | -------- | --------------------- | ----------- | ---------------------------------------------------------------------------------------- |
| Egress    | TCP      | 443                   | 0.0.0.0/0   | HTTPS to the EDH ALB and to the VPC interface endpoints                                  |
| Egress    | TCP      | `edhApiEndpoint` port | 0.0.0.0/0   | HTTPS to the EDH ALB when the endpoint names a port other than 443 (for example `:8443`) |

The group has no ingress rule and no other egress. Its id is exported as the CloudFormation output `EdhAddonLambdaSecurityGroupId` of the add-on's nested stack and published as the SSM parameter `/<name>-<baseStackName>/resourceNames/securityGroups/edhAddonLambda`, in which `<baseStackName>` carries the Region suffix VAMS appends to `app.baseStackName` (for example `prod-us-east-1`). The shared-VPC layout needs no rule on the EDH ALB (see [Load balancer security group](enable.md#load-balancer-security-group)). When VAMS runs in a connected VPC, allow the group as a source on an internal EDH ALB's security group, on the port `edhApiEndpoint` names (443 below), so the management calls are accepted:

```bash
aws ec2 authorize-security-group-ingress \
    --group-id <EDH ALB security group id> \
    --protocol tcp --port 443 \
    --source-group <EdhAddonLambdaSecurityGroupId>
```

The rule can name the group only across a VPC peering connection in the same Region, or a transit gateway with security group referencing turned on for the gateway and its VPC attachments; otherwise allow the VAMS isolated-subnet CIDR ranges instead. An internet-facing ALB receives the calls from the public address of the NAT gateway they leave through, so its rule allows that address rather than the security group.

## Security

The add-on handles three kinds of credential: the EDH cluster root key, which it reads; the VAMS session keys it mints for launched Linux desktops; and the Windows passwords EDH generates, which it relays to each desktop's owner. The core controls are described in [Security Architecture](../../architecture/security.md).

### EDH root key

The EDH Workstations add-on authenticates to the EDH cluster with the cluster root key, and that key is never a configuration value. `app.addons.useEdhWorkstations.edhAdminApiKeySecretArn` names an operator-managed AWS Secrets Manager secret; VAMS imports the secret by ARN, grants `secretsmanager:GetSecretValue` on it to the add-on's Lambda execution roles, and never creates, populates, rotates or logs it. The key does not pass through synthesis, a code asset or a template, so neither exposure described under [Third-Party Credentials Supplied in Configuration](../../architecture/security.md#third-party-credentials-supplied-in-configuration) applies. The root key lets EDH act as any of its users — VAMS relies on that to relay the acting VAMS user as an opaque uid — so it is a cluster-wide administrative credential: keep it under `aws/secretsmanager` or a customer managed key whose policy grants the add-on roles `kms:Decrypt`, scope who else may read it, and audit its reads with AWS CloudTrail. [Credentials](overview.md#credentials) describes the secret's value, how the functions cache it and how the operator re-publishes the key after each [rotation](overview.md#root-key-rotation), until which every EDH call fails closed. The `X-EDH-TOKEN` header, the `rootKey` field, the DCV `connection_string`, the `authToken` key that names its connection token, and the sensitive fields a desktop row carries (`session_token`; `authentication_token` and `broker_session_id`, which in EDH's high-scale layout hold the broker session id; and the password `session_local_admin_password`) are in the logger's redaction key set, and the EDH client logs method, route, status and attempt — never the headers, the secret payload or a successful response body.

Of the three EDH reads VAMS makes of a desktop, only the per-user desktop list that **Connect** and the Windows sign-in read makes EDH issue an Amazon DCV connection token, at most one per request EDH answers, and a token reaches only the connect response; [Desktop reads and connection tokens](overview.md#desktop-reads-and-connection-tokens) lists which request uses which read. The cluster listing that the session reconciler's sweep, the administrative session views, stop and deactivation, and the launch worker's read-back use issues no token but carries the sensitive fields above for every active desktop on the cluster; VAMS keeps none of them. EDH writes each row of that listing to its controller log at its default `INFO` level, so access to that log is access to those credentials.

### EDH session keys

With `app.addons.useEdhWorkstations.sessionBootstrap.enabled`, each Linux desktop launched from VAMS receives its own VAMS API key so the desktop's `vamscli` is signed in as the launching user. The key is minted through the API key service on the user's behalf at launch, at every start and when the owner renews the lease of a running desktop, is named `temporary-session-edh-<bootstrapId>`, with `-r<YYYYmmddHHMMSS>` (the UTC second of the mint) appended to a key a renewal re-issues, expires `sessionKeyTtlMinutes` (480 by default) after it is minted, and is stored by VAMS only in an AWS Secrets Manager secret named `<secretNamePrefix><bootstrapId>`, encrypted under the add-on's dedicated `EdhSessionSecretsKey`. The secret is created without a read grant; once VAMS has correlated the desktop, its resource policy lets the roles in `workstationInstanceRoleArns` read it only from the session's own EC2 instance (`assumed-role/<role name>/<instance id>`). Once the desktop signs in, its `vamscli` also holds the key in owner-only profile files under `~/.config/vamscli/profiles/` in the desktop user's home directory (see [Linux desktop sign-in](overview.md#linux-desktop-sign-in)). Stopping or deleting the desktop, an administrator's stop or deactivation, and the `edhSessionReconciler` sweep every 15 minutes, which also covers desktops stopped by EDH's idle timer, revoke every key of the desktop; a revoked key can keep authorizing for up to about 45 seconds, the sum of the API Gateway authorizer cache and the in-Lambda key cache. A session key carries the user's roles that do not require MFA, and a caller holding one cannot launch or start desktops: the launch and start routes refuse API-key principals. The `temporary-session-` prefix marks every session key as a temporary session key, so API-key create and update refuse a caller holding one with `403` and a desktop cannot mint or extend a key whatever the user's roles grant, and a key name a user creates cannot carry the prefix (see [API Keys](../../architecture/security.md#api-keys)); the add-on's permission templates grant no `/auth/user/api-keys` route either. [Session bootstrap](overview.md#session-bootstrap) describes, with its diagram, how the key is minted, stored, bound to the desktop's instance, re-issued on renewal and revoked, and its [Limits](overview.md#limits) list what else not to grant.

### EDH Windows sign-in

A Windows desktop opens at its Windows lock screen, and VAMS shows the desktop's owner the Windows user name and the password EDH generated for it ([Windows desktops](overview.md#windows-desktops)); a Windows desktop receives no session key. `GET /addon/edh/workstations/{sessionId}/windows-sign-in` answers only the owner, through both authorization tiers, and only while the desktop is running, and the password appears in that response body alone, which carries `Cache-Control: no-cache, no-store`. The route's log line names the session and the caller, never the value; the logger redacts the `password` and `session_local_admin_password` keys, and the EDH listing the route makes is audited as `workstationWindowsSignIn` without the password. The web app requests the password when the owner opens **Show Windows password**, shows it masked until it is revealed, never writes it to the URL or to browser storage, and drops it when the dialog closes. `vamscli` prints it only with `edh workstation connect --show-windows-password`, and its log redactor treats `password` as a credential key. No MCP tool returns it. The `vamscli` client checks every EDH workstation id as a single path segment, the service's own id rule, before any request, so a workstation id passed to a `vamscli edh workstation` command or an EDH workstation MCP tool cannot address the sign-in route. Beneath every client method it also refuses, before sending, a request path with an empty, `.` or `..` segment, raw or percent-encoded, so a path value of any other `vamscli` command or MCP tool cannot climb out of its own route to the sign-in route either. A directory account has no password in VAMS: its owner signs in with their own directory password.

### Session secret encryption

The EDH Workstations add-on's per-session secrets are always encrypted under the add-on's dedicated `EdhSessionSecretsKey`, whatever the `useKmsCmkEncryption` setting, and the operator-managed EDH root key and CA bundle secrets keep the key their owner chose (see [EDH root key](#edh-root-key)). The key, its policy and its removal are described under [AWS KMS key](#aws-kms-key).

### IAM scope

The EDH Workstations add-on's execution roles also hold control-plane grants on objects the add-on creates at runtime. Those objects cannot be named at synthesis, so the grants are scoped by name prefix, tag or service rather than by resource ARN:

-   **Session secrets** — With `sessionBootstrap.enabled`, the workstation service, launch worker, admin service and session reconciler create, describe, tag, overwrite and delete secrets under `secret:<secretNamePrefix>*` in the deployment account and Region, and invoke the API key service function. They may call `secretsmanager:PutResourcePolicy` on those secrets only in requests that set `BlockPublicPolicy`, so a session secret never receives a public policy. The reconciler keeps the invoke, overwrite and delete grants with the flag off, so it can revoke credentials an earlier configuration minted. Because of that, the prefix is validated whenever the add-on is enabled, and configuration validation refuses a prefix that covers the EDH root key or CA bundle secret.
-   **AMI builds** — With `amiBuilds.enabled`, the AMI recipe service, the build registrar and the catalog registration function manage the EC2 Image Builder objects named with the deployment's lower-cased `<name>-<baseStackName>-edh-` prefix. They also hold the Image Builder list actions, `ec2:DescribeImages`, `ec2:DescribeInstances`, `ec2:DescribeInstanceTypes` and `ec2:DescribeSnapshots` on `*`, because those calls take no resource ARN. `ec2:DescribeInstances` finds the instances that use an AMI before it is deregistered; the functions hold no action that stops or terminates an instance. `ec2:DescribeImages` and `ec2:DescribeInstanceTypes` read the architectures of a recipe's parent AMI and build instance types, which are checked against the recipe's architecture. They read the public AMI parameters under `/aws/service/`, pass the build instance role to Amazon EC2 only, and create the EC2 Image Builder service-linked role.
-   **AMI and snapshot cleanup** — The AMI recipe service and the build registrar may call `ec2:DeregisterImage` and `ec2:DeleteSnapshot` only on an AMI or snapshot whose `vams:deployment` tag is the deployment's prefix. The two functions and the catalog registration function may call `ec2:CreateTags` only in a request that writes that same `vams:deployment` value and no keys but the `vams:edhAmiRecipe`, `vams:edhAmiRecipeHash`, `vams:deployment` and `edh:visibility:<edhClusterId>` tags, and on an AMI only when it already carries the deployment's tag. The catalog registration function holds no Image Builder delete, `ec2:DeregisterImage` or `ec2:DeleteSnapshot` action.
-   **AWS Batch job definitions** — With `containers.enabled`, the catalog registration function registers, tags and deregisters only the configured job definitions, every revision of each (`job-definition/<name>` and `job-definition/<name>:*`, where every name begins with `edh-`), and holds `batch:DescribeJobDefinitions` on `*`, which takes no resource ARN.

The reads of the EDH root key and CA bundle are scoped to the two secrets the configuration names (see [EDH root key](#edh-root-key)).

## AWS WAF exemption for AMI recipes

With AWS WAF enabled (`app.useWaf`), the EDH Workstations add-on enabled and its AMI builds on, the regional web ACL overrides two rules of the Common Rule Set (`AWSManagedRulesCommonRuleSet`), **`EC2MetaDataSSRF_BODY`** and **`GenericRFI_BODY`**, to `count` (when the policy runs the Common Rule Set in block mode, as the shipped policy does) and applies a VAMS rule, `VAMS-EdhAmiRecipeBodyRules`, evaluated after every other rule in the web ACL, that blocks a request carrying either rule's label unless the URI path (both as received and once URL-decoded and path-normalized) starts with `/api/addon/edh/admin/ami-recipes`, the `/addon/edh/admin/ami-recipes*` routes as the API Gateway stage receives them. An AMI recipe body carries EC2 Image Builder component scripts, and the shipped Linux recipes read the instance metadata service at `http://169.254.169.254/...`, which those two rules would block. VAMS stores those scripts for the build instance to run and never dereferences a URL in them, and the five `/addon/edh/admin/ami-recipes*` routes are admin-only at both authorization tiers, so relaxing the two rules under the recipe route prefix is acceptable. Every other path continues to block on both rules, and every other managed rule still applies to recipe bodies. With the add-on or its AMI builds off, both web ACLs are what the policy alone builds.

The exemption sits on the regional web ACL alone, because the recipe routes reach AWS WAF only at the API Gateway stage in every fronting mode: clients (web, CLI, MCP) call the stage directly for every route other than `/api/amplify-config` and `/api/version` (see [WAF Protection Scope](../../architecture/networking.md#waf-protection-scope)).

-   **CloudFront deployment**: The `/api/*` behavior forwards with the stage as its origin path and reaches only the stage's own `/api/amplify-config` and `/api/version` routes, so recipe requests go to the stage directly and the CloudFront-scoped web ACL, which takes no exemption, never evaluates them.
-   **ALB deployment**, with a `REGIONAL` or a `PRIVATE` API: The ALB shares the regional web ACL, so the exemption is present there too, but inert: the ALB answers API paths with a redirect to the stage and forwards no API request, or its body, to API Gateway. Recipe requests reach the stage directly, or through the execute-api VPC interface endpoint for a `PRIVATE` API.
-   **No CloudFront or ALB**: Clients call the stage directly.

The exemption follows the policy's own overrides of those two rules. An override to `count` or `allow` is kept, because the policy already relaxes the rule on every path, and `VAMS-EdhAmiRecipeBodyRules` does not re-block it. An override to `block` is replaced by `count`, and `VAMS-EdhAmiRecipeBodyRules` blocks the rule's label off the recipe routes, so the rule still blocks on every other path. A Common Rule Set entry with `block: false` runs in count mode and is left as the policy builds it.

The exemption relaxes those two rules only. Synthesis reports a warning, with the id `VAMS:WafPolicy:VAMS-EdhAmiRecipeBodyRules:unrelaxed:<group>[:<rule>]`, for each rule the policy enforces that a recipe body can still match:

-   `SizeRestrictions_BODY` of `AWSManagedRulesCommonRuleSet`, when the group runs in block mode and the policy does not override the rule to `count` or `allow`; a recipe body commonly exceeds 8 KB.
-   Each of the `AWSManagedRulesLinuxRuleSet`, `AWSManagedRulesUnixRuleSet`, `AWSManagedRulesWindowsRuleSet`, `AWSManagedRulesSQLiRuleSet` and `AWSManagedRulesPHPRuleSet` groups the policy runs in block mode; component scripts carry shell, PowerShell, SQL and PHP patterns.

The shipped policy raises none of these warnings. Where one is reported and recipe requests must pass, override the rule to `count`, or run the group in count mode, in `wafPolicyConfig.json` (see [WAF rule policy](../../deployment/configuration-reference.md#waf-rule-policy-configpolicywafpolicyconfigjson)). The body rules of the Known Bad Inputs group (`AWSManagedRulesKnownBadInputsRuleSet`), which the shipped policy applies in block mode, are neither relaxed nor warned about; the shipped recipes pass them. AWS WAF inspects the first 16 KB of a request body at the API Gateway stage, the API Gateway default, which VAMS does not change. A recipe request that a managed rule still blocks at the stage receives the `WAF_FILTERED` gateway response described under [Requests the web ACL blocks](../../architecture/security.md#requests-the-web-acl-blocks).

## EDH Workstations add-on costs

The EDH Workstations add-on adds cost only when `app.addons.useEdhWorkstations.enabled` is true. The EDH cluster is operator-managed, and the cost of its own infrastructure is outside these estimates; the desktops and container jobs it runs bill to the same AWS account. The following table lists the cost drivers the add-on introduces. Desktop and build costs depend on the instance types and hours used, so consult the Amazon EC2 and EC2 Image Builder pricing pages for your Region. The costs of the core deployment are estimated in [Cost](../../overview/costs.md).

| AWS Service                           | Cost Driver                                          | Notes                                                                                                                                                                                                                                                                   |
| ------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Amazon EC2 and Amazon EBS**         | Desktop instance hours and volume storage            | Usually the largest add-on cost. A stopped desktop accrues no instance charges but still bills for its Amazon EBS volumes until it is deleted. A workstation lease policy stops a leased desktop at lease expiry and deletes it after a grace period.                   |
| **EC2 Image Builder**                 | Build instance hours and retained AMI snapshots      | With AMI builds enabled, each build runs an Amazon EC2 build instance (the shipped recipes use m7i.large or m7i.xlarge). VAMS deregisters retired AMIs beyond a recipe's `keepVersions` (default 3) and deletes their snapshots once no desktop uses them.              |
| **AWS CodeBuild and Amazon ECR**      | Container image builds and image storage             | With containers enabled, AWS CodeBuild builds each image at deployment and pushes it to an Amazon ECR repository that keeps the last 10 images. Container jobs run on the EDH cluster's compute.                                                                        |
| **AWS Secrets Manager and AWS KMS**   | Per-session secrets and the session secrets key      | With session bootstrap enabled, each launch stores one secret, and a dedicated customer managed key encrypts them ($1 per month plus API calls).                                                                                                                        |
| **AWS Lambda and Amazon EventBridge** | Scheduled invocations                                | The session reconciler runs every 15 minutes (about 2,880 invocations per month), and the AMI build sweep runs every 30 minutes (about 1,440 per month) when AMI builds are enabled.                                                                                    |
| **Amazon DynamoDB**                   | Session, lease policy, AMI recipe, and build records | Two on-demand tables; an idle table bills only for its storage.                                                                                                                                                                                                         |
| **VPC Endpoints**                     | Up to 5 additional interface endpoints               | AWS Batch for container jobs (when no pipeline already creates it), and EC2 Image Builder, Amazon EC2, and the AWS Systems Manager `ssmmessages` and `ec2messages` endpoints for AMI builds. About $109.50 per month in commercial Regions across 3 Availability Zones. |

### Workstation runtime

EDH desktop costs scale with the number of desktops, their instance types, and how long they run. Desktops that are stopped but not deleted continue to bill for Amazon EBS storage. An enabled lease policy stops a leased desktop when its lease expires and deletes it after the grace period unless the user renews it, and a forced policy gives every new desktop a lease.

:::tip[Enable workstation leases]
Enable the lease policy on the **Settings** tab of the **Workstation Admin** page so desktops whose lease is not renewed are stopped at expiry and deleted after the grace period. See [Leases](overview.md#leases).
:::
