# Add-ons Overview

An **add-on** is an optional part of VAMS that ships with upstream VAMS, is maintained by upstream, and is off until a deployment enables it in configuration. Add-ons come in two kinds:

-   **Integration with an external solution.** The add-on connects VAMS to a solution that is deployed and run separately from VAMS. The add-on supplies the VAMS-side components that make VAMS work with that solution, or that extend the solution's functionality.
-   **Stand-alone component.** The add-on is a component that is not part of VAMS core and is not deployed externally. When the add-on is enabled, VAMS deploys every component of it.

An add-on is enabled through `app.addons.*` in the deployment configuration or, for a viewer, through the `enabled` flag of its entry in `web/src/visualizerPlugin/config/addonViewerConfig.json`.

Add-ons are different from **custom** code. Custom code is what an organization adds in its own fork of VAMS. Upstream ships every custom file empty and never edits it. An add-on is upstream code that upstream keeps working from release to release. The add-on files sit beside the core lists they extend, so add-on code stays off the path of core changes. [Extending VAMS in a Fork](customizing-vams.md#how-the-extension-points-work) lists the core, add-on and custom files list by list.

## When functionality is an add-on

VAMS core is general-purpose visual asset management built on the tier-1 AWS services listed below. Upstream functionality is built as an add-on when any of these holds:

-   **It integrates an external solution**, a product or service that is deployed and run outside VAMS, from a vendor or from AWS.
-   **It depends on an AWS service outside the tier-1 set**, such as Amazon OpenSearch Service.
-   **It implements a use-case lens for an industry**: data models, workflows, pages or rules built for one industry's use case rather than for visual asset management in general.

The tier-1 services are Amazon S3, Amazon DynamoDB, Amazon API Gateway, AWS Lambda, AWS Identity and Access Management (IAM), Amazon Cognito, Amazon CloudFront, Application Load Balancer, Amazon Route 53, Amazon Virtual Private Cloud (Amazon VPC) and its endpoints, AWS CloudFormation, AWS Key Management Service (AWS KMS), AWS Step Functions, Amazon EventBridge, Amazon Simple Queue Service (Amazon SQS), Amazon Simple Notification Service (Amazon SNS), AWS Secrets Manager, AWS Systems Manager Parameter Store, Amazon CloudWatch, AWS CloudTrail, AWS WAF and AWS Certificate Manager.

These are not add-ons, even when they call an AWS service outside the tier-1 set or a vendor's service:

-   **Viewers.** Each viewer is a plugin with its own `enabled` flag. A licensed viewer, or a viewer that belongs to an add-on, is listed in `addonViewerConfig.json` ([Viewer Plugins](../additional/viewer-plugins.md)).
-   **Processing pipelines.** Each pipeline deploys from its own nested stack and is turned on by its own `app.pipelines.*` setting. The pipeline system that runs them is part of this exception, including the AWS Batch and Amazon SageMaker jobs a workflow can stop ([Pipeline System Overview](../pipelines/overview.md)).
-   **Settings that point core at a deployment's own resources**, such as an external OAuth, SAML or OIDC identity provider, existing asset buckets, a VPC or a KMS key.
-   **Client-side connectors** in `tools/ExternalIntegrations/`, such as the ArcGIS Pro connector and the Isaac Sim integration. They run inside the external application, call VAMS through the CLI, and deploy nothing.

Every add-on has an on/off setting in the deployment configuration and is off by default.

Three core features run on AWS services outside the tier-1 set and are the exceptions to this rule: search and indexing on Amazon OpenSearch Service (`app.openSearch`), the maps on Amazon Location Service (`app.useLocationService`), and the AWS Deadline Cloud pipeline execution type (`app.pipelines.deadlineCloudExecutionTypeEnabled`, off by default). Other new functionality that needs one of these services is an add-on, unless an exemption above covers it: a new pipeline that runs on the Deadline Cloud execution type is a pipeline, not an add-on.

An add-on that adds feature switches lists them on its own pages, linked in the **Details** column.

A deployment that has not enabled an add-on shows nothing of it. Its API routes are not registered, and the access control constraint editor offers none of the add-on's object types, web routes or API routes; the route listings and the allowed-route checks behind each page load leave its routes out, so a role is never checked, and no denial is audited, for a route that is not deployed. A new constraint or permission template naming one of its object types is refused, saying the add-on is not enabled, while a constraint stored earlier with such a type is kept, can be opened and deleted, and takes effect again once the add-on is enabled. Its web pages are not reachable (their address shows **Page not found**), and `vamscli --help` and the MCP server list none of its commands or tools once `vamscli auth login` has read the deployment's feature switches. Enabling the add-on brings all of these back; signed-in CLI and MCP users run `vamscli auth login` again, and restart the MCP server, to see them.

The VNTANA and VEERUM viewers run entirely inside the VAMS web application and call no separately deployed service. What they need from the vendor is a license and the vendor's viewer package, which the install script fetches and bundles when the viewer is enabled. Both ship disabled. See [Partner Integrations](../additional/partner-integrations.md) for licensing.

## Adding an add-on to upstream VAMS

An add-on contributed to upstream VAMS uses the add-on files: its routes in `backend/backend/common/addonApiRoutes.py`, its handlers and models in `backend/backend/handlers/addon/` and `backend/backend/models/addon/`, its CDK resources in a nested stack under `infra/lib/nestedStacks/addon/`, its feature switch in `infra/common/addonAppFeatures.ts`, and its web, viewer and CLI entries in the add-on files listed in [Extending VAMS in a Fork](customizing-vams.md#how-the-extension-points-work). Its configuration goes under `app.addons` and it is off by default. A feature that an organization adds only in its own fork uses the custom files instead.
